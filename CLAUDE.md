# CLAUDE.md

Personal medical document archive running on a Raspberry Pi. Uploads PDFs, uses AI to split, extract, and index content, and generates scoped share links for doctors.

## Conventions

- **No AI attribution in git history.** Do not add `Co-Authored-By`, `Claude-Session`, or any similar trailer to commit messages or PR descriptions. This overrides the default Claude Code attribution behaviour.
- **Commit when a unit of work is complete**, not per exchange. Leave in-progress work in the working tree and say what is pending instead of sealing a draft.
- **Do not hard-wrap prose** in docs or Markdown. A paragraph or list item is one line; the editor wraps it, and a diff shows the sentence that changed.
- **Structure is checked, not judged.** `docs/structure-rules.md` defines what "clean" means here (rules S1-S13, two known exceptions, E1 and E2); `core/src/__tests__/architecture.test.ts` and `server/scripts/smoke-entrypoints.mjs` enforce it. A change that needs an exception edits the test and that page in the same commit. "Done" for a structural change means those, `check:browser` and `check:app` pass, not only the unit tests.

## Common commands

```bash
# Everything, first time (asks for what is not in the environment)
sudo SPINE_DOMAIN=spine.example.com ./install.sh -a

# Install deps (first time, needs sudo)
sudo ./install.sh -d

# Write .env (and relay.env, given ANTHROPIC_API_KEY) with generated secrets; an existing file is left alone
./install.sh -e

# Build everything (server TS + React)
./install.sh -b

# Install and start systemd services
sudo ./install.sh -s

# The relay on this machine (needs relay.env and SPINE_RELAY_DOMAIN)
sudo ./install.sh -r

# Issue Let's Encrypt cert and install nginx config (the relay's too when SPINE_RELAY_DOMAIN is set)
sudo ./install.sh -n

# Restart after code changes
./install.sh -b && sudo systemctl restart spine-web

# Accounts (the operator creates them, or SPINE_REGISTRATION=open lets people sign up)
cd server && npm run cli -- create-user you@example.com      # prints a password once
cd server && npm run cli -- set-password you@example.com     # an account with no vault only; ends that user's sessions
cd server && npm run cli -- reset-link you@example.com       # one-time link; works with no mailer
cd server && npm run cli -- disable-2fa you@example.com      # lost phone and recovery codes
cd server && npm run cli -- delete-user you@example.com      # shows what it would remove; --yes to do it
cd server && npm run cli -- list-users

# Install and build (npm workspaces: one install at the root; core is built first because server and web use it)
npm ci && npm run build

# Tests (core: the units; server: the tests that drive the composed app; the tests run on core's source, not its build)
npm test -w spine-core
npm test -w spine-server
npm run test:accounts -w spine-server   # the server's own tests on the accounts-only database (M-37); core has one too
npm run test:shim -w spine-server       # the same on the WebAssembly SQLite the browser uses; core has one too
npm run test:coverage -w spine-server

# The checks CI runs (tests, typecheck, dependency audit, gitleaks, semgrep): needs `brew install gitleaks semgrep` for `scan`
./scripts/check.sh [server|web|scan|all]
```

## Architecture

What it must do (the `FR-`, `TR-` and `CR-` IDs cited around the repo): [docs/requirements.md](docs/requirements.md). Target architecture, trust boundaries, interfaces/adapters and the migration path: [ARCHITECTURE.md](ARCHITECTURE.md). Security principles, current controls and known gaps: [SECURITY.md](SECURITY.md) — read it before touching routing, auth, share links, storage, providers or static serving.

**The sections below describe what runs today:** multi-user with local accounts (CLI or open signup with email verification), a store interface (SQLite only), an LLM interface with Anthropic and Vertex adapters, a mailer interface (`none`, `brevo`). Hosting stays on a Pi; GCP is inference only.

**Request flow:** records: page → core (Web Worker) → `LocalApp` → route → store → SQLite in WebAssembly, on the device. Accounts, the vault, shares and the relay's pass: browser → nginx (TLS) → Fastify (port 3000) → the accounts database and `data/vault/`. Model calls: core → relay → provider.

**Ingestion flow** (a photo skips `rasterize.ts` and the text reader: `photo.ts` makes it an upright PNG page and the model parser reads it, and it is accepted only with `SPINE_MULTIMODAL_ENABLED`): Upload → `source-files.ts` keeps the original as a file in the device's store (saved to the vault sealed) → `pipeline.ts` (fire-and-forget) → `rasterize.ts` (PDF→PNG) → `pdf-text.ts` (PDF.js text layer) → `continuation.ts` (Claude Haiku, per page pair) → SQLite as pages and unread documents (`needs_reading`), held back until the owner confirms the grouping → on confirm, `read-upload.ts`: `extraction.ts` (Claude Haiku, per logical doc) → `grounding.ts` (bbox matching) → stamps and signatures → the documents appear

**PDF text layer** (`ingestion/pdf-text.ts`): PDF.js, in the device's core, returns per-page paragraph elements with bounding boxes in PDF points. There is no sidecar any more; what the retired Python/Unstructured one offered is in `docs/sidecar.md`.

**AI model:** configuration, not code. `SPINE_LLM_PROVIDER` (`anthropic` | `vertex`) and `SPINE_LLM_MODEL`, defaulting to `claude-haiku-4-5-20251001` for both continuation detection and field extraction. Everything provider-specific is behind the LLM interface in `core/src/llm/`, which knows one provider, `relay` (a device's); `anthropic` and `vertex` are the relay service's, in `server/src/llm/adapters/`, registered by `server/src/providers.ts`. **No vendor package may be imported outside `server/src/llm/adapters/`, and `core` imports no native library at all** (`boundary.test.ts`).

## Key design decisions

- **All data access goes through the store interface** — `getStore()` returns a `Store` of repositories. **No SQL and no `better-sqlite3` import may exist outside `core/src/store/sqlite/`** (the repositories are written against `driver.ts`'s small `Database` interface; the native module is imported by `server/src/driver-native.ts` (and by `core/src/testing/driver-native.ts` for core's own tests), and a process says which driver it uses with `useDriver`, and `npm run test:shim` runs the whole suite on the WebAssembly driver the browser will use); there are currently zero `.prepare()` calls elsewhere. Every repository method takes the acting user's id as its first parameter, with exactly five exceptions enumerated in `store/types.ts` (reads scoped by a share link's owner, the owner device's record of an open, the public side of a sealed share, boot-time maintenance, the users repository). Every statement on a user-owned table filters by `user_id`; a method called without a user throws; a record that is not the caller's answers 404. `__tests__/isolation.test.ts` checks all of it as a second user.
- **New tables carry `user_id` and new queries list explicit columns** — `SELECT *` on a table with `user_id` sends it to the client, including to share recipients. `response-shape.test.ts` scans whole responses.
- **Parsing goes through the parser interface** — one entry per page image, in order, with boxes in that image's pixel space (the text-layer adapter scales from the page's size in points).
  - PDF.js reads only the PDF's own text layer: no OCR, no layout model. A page with no text layer returns no elements. (`auto` is one decision for the whole file, and its `ocr` label is never set.)
  - `hybrid` goes cheapest first per page: text layer (what the text layer held, at least `SPINE_TEXT_LAYER_MIN_CHARS`) → local Tesseract if its confidence is good → the model. It never sends a page that has a text layer, and fails the upload if the file cannot be opened rather than treating every page as scanned.
  - Images leave the host only via `readPage` (a page; `multimodal`/`hybrid`, or a photo) and `readStamps` (small signature-stamp crops from a PDF's last page, `ingestion/signatures.ts`), and only with `SPINE_MULTIMODAL_ENABLED`. If the model fails, the page keeps local OCR, and a failed stamp read adds no doctors and never fails the upload.
  - "Read page with AI" (`ingestion/ai-reading.ts`) sends only that page through the same parser and switch, then extracts only the documents that contain it again; "Read whole document" (`strategy: "configured"` on the same route) reads all of a document's visible pages in one call with the configured parser, as an upload does (text layer, then OCR, then a model, depending on `SPINE_PARSER`), keeps the grouping, and extracts again; it sends an image only if that parser does, so it needs the switch only then. A page that comes back unread keeps its earlier text.
  - Model-read pages are stored as `multimodal` with text and **no boxes** (a model's estimate of where text sits was unreliable, so it is not asked for): a field read from one keeps its source page and gets no highlight, and the UI draws none on such a page. Exact boxes come only from the PDF's text layer and from local OCR.
- **Verification and reset links** — tokens are hashed at rest, spent by one atomic `UPDATE`, carried in the URL **fragment** (never sent to the server, so not in nginx's log) and spent by a `POST`. Requests that name an address answer identically whether or not it has an account, and mail is sent after the response. Mail has no attachment field and neutral wording; a test fails on clinical words.
- **Schema changes need an empty database, except a new column with a default** — `CREATE TABLE IF NOT EXISTS` cannot alter a table, and startup refuses an old-shape database. A new defaulted column is added on open by `addColumnsInPlace` in `store/sqlite/connection.ts` (with a test against a database made without it); anything else (rename, remove, retype) needs a migration runner, which does not exist.
- **Two-factor** — optional TOTP per user (`totp.ts`, `routes/totp.ts`). With it on, the right password only starts a *pending* login in the session; `POST /api/auth/login/second-factor` completes it. The secret is AES-GCM encrypted under a key derived from `SESSION_SECRET` (rotating that secret orphans every enrolment); the last used step blocks replay; recovery codes are sha256-hashed and single use. Tables are new (`user_totp`, `user_recovery_codes`), because a new table needs no migration and a new column would.
- **Auth** — email + argon2id password; `requireAuth` re-resolves the session to a live user on every request and sets `req.userId`, which handlers pass to the store. A changed password bumps `auth_version`, ending that user's other sessions. An unknown email and a wrong password are indistinguishable in answer and time.
- **Repository methods are all async** even though SQLite is synchronous: the interface spans drivers, and a networked store is async. `transaction(fn)` uses explicit `BEGIN`/`COMMIT` with `SAVEPOINT` for nesting, because `db.transaction()` throws on an async callback.
- **Pages can be moved** — `page_number` is a page's place in the upload (ranges and the UI use it), `source_page` its immutable index in the file, which is what the parser and the stamp reader count: **anything that re-reads a page asks for `source_page`**, never `page_number`. A move (`ingestion/move-page.ts`, `POST /api/pages/:id/move`) rewrites a list of lists in one transaction and renumbers; document order never changes. Screens about the whole upload (cards, search, review, the grouping screen) show the file's number; a document's own screen numbers its pages from 1 and gives the file's number as a tooltip.
- **Values to check** — extraction scores each field and result 0–1 (the prompt defines it as certainty that the value is exactly what is printed); below `LOW_CONFIDENCE` (0.7, `confidence.ts`) and not edited by the owner a row is `needs_check`, and a document's `to_check` counts them until it is reviewed. The document card, the review queue and the document page mark them "check". FR-EXT-04.
- **Pages can be turned** — `POST /api/pages/:id/rotate` (90, 180, 270 clockwise) rewrites the stored page image in place (through a staged file), swaps `image_width`/`image_height`, adds to `pages.rotation`, and moves every box drawn on it (`pages.elements`, `extracted_fields` and `measurements` bboxes: `geometry.ts`'s `rotateBox`) in one store call. A reading of the PDF's text layer comes back in the file's orientation, so `pages.updateReading` turns the `native_text` boxes by the stored rotation; OCR boxes are of the image as it is and a model's reading has none. The image route is `no-cache` with `Last-Modified` (304 on a match) and the web adds `?r=<rotation>` to the URL, because a turned image must not be shown from a copy. Re-reading never rasterizes the PDF again, it reads the stored image, so a turn survives it.
- **Documents are read after the grouping is confirmed, not before** — the pipeline only parses and groups (`documents.needs_reading = 1`); `POST /api/source-files/:id/grouping/confirm` runs `read-upload.ts` (one extraction per document, then stamps and signatures, then confirms, embeds and looks for links); a change to a document's pages marks it again; `/extract` (Done) only marks while the upload is unconfirmed. Anything that read at upload time (tests, integration flows) now calls `readUpload()` first. SECURITY.md **M-29**.
- **The grouping is confirmed before documents are shown** — the pipeline sets `source_files.grouping_confirmed = 0` when it finishes; until the owner confirms (`POST /api/source-files/:id/grouping/confirm`) the upload's documents are held back by the same fragment as set-aside ones (`VISIBLE = NOT_SET_ASIDE AND UPLOAD_CONFIRMED`, `store/sqlite/visibility.ts`) and cannot be marked reviewed; confirming schedules embeddings and links. The column defaults to 1: old uploads, restores and tests are confirmed. `includeUnconfirmed` (upload screens) or `includeHidden` (regrouping) list them anyway. **Every new query over the owner's documents uses `VISIBLE`.** ARCHITECTURE.md **Confirming the grouping**.
- **What the owner edits is sticky** — `documents.owner_edited` (headline columns), `extracted_fields.owner_edited`, `measurements.owner_edited` and `removed_readings`; a re-reading (`applyReading`/`storeReading`) keeps them, deletes only unedited values (`deleteUnedited`) and does not bring back what was removed. Tags and doctors are still replaced. The owner's notes go into the extraction prompt as context only. ARCHITECTURE.md **What the owner edits stays edited**.
- **Hidden pages and set-aside documents** — `pages.hidden` sets a page aside (kept, but out of the document's view, search and reading); a document with pages and none shown is *set aside* (`store/sqlite/visibility.ts`'s one SQL fragment) and is left out of the timeline, search, review, shares, doctors' lists and trends (through `VISIBLE`) unless `includeHidden` is passed (the regrouping screen only). Regrouping saves with `defer`, and Done reads the changed documents once (a fully hidden one is `skipped`).
- **SQLite** — the server's `data/spine.db` (WAL; accounts only) and, on the device, an in-memory database saved as sealed objects. No migration runner: schema is idempotent `CREATE TABLE IF NOT EXISTS`, which cannot alter an existing table, so a schema change other than a new defaulted column (see above) means editing the schema files (`schema-accounts.ts`, `schema-records.ts`) and deleting `data/spine.db*` — **only safe while the archive is empty**; startup refuses an old-shape database and says how many records it holds. A runner is needed before the first change to a populated database. Back up `data/spine.db` + `data/vault/`.
- **In-memory SQLite for tests** — `SPINE_DB_PATH=:memory:` is set in `vitest.config.ts`, not in test files. `resetStore()` is called in `buildTestApp()` between test files, and fixtures are built through the interface via `__tests__/helpers/seed.ts` rather than raw SQL (P10 — and it is what proves the interface is complete).
- **Ingestion pipeline is fire-and-forget** — `startIngestionJob(sourceFileId, userId)` returns immediately; status tracked in an in-memory registry, polled by the browser.
- **Structured extraction** — per-type guides in `llm/doc-types.ts`; numeric results are `measurements` (parsed and flagged in `ingestion/measurements.ts`), people are a per-user `doctors` directory (`doctors.ts` matches names), related fields share a `group_no`. Edits to all of these go through the one atomic `PATCH /api/documents/:id`.
- **Page images are authenticated** — served by `GET /api/pages/:id/image` (by the device's `LocalApp`), streamed from the file store. The server never mounts `DATA_DIR` statically: it holds `spine.db` and the sealed vault.
- **Bbox grounding** — fractional coordinates (0–1). Exact string containment first, then LCS fuzzy match (threshold: 60% of needle length).
- **LLM access goes through the interface** — `getChatLlm()`, which reads the LLM config on first use and memoizes. No init step: `index.ts` just calls it once at startup so a bad provider stops the process there rather than at the first upload. Adding a provider is a map entry in `llm/index.ts` plus a file in `llm/adapters/`, never a new conditional. The two tasks are defined in `llm/tasks.ts` (budget + schema, both fixed at startup) and an adapter returns one bound LangChain `Runnable` per task. **No provider package (`ChatAnthropic`, `ChatVertexAI`) may be imported outside `llm/adapters/`**; `@langchain/core` above that line is fine — it is the shared abstraction, and the seam type. Every response is validated with zod before it reaches the database; a validation failure logs and degrades to a reviewable fallback rather than killing the upload.
- **Vertex residency is configuration, not code inspection** — endpoint, region and project must all be stated (nothing defaults to a global endpoint), and startup fails if `GOOGLE_API_KEY`/`GEMINI_API_KEY`/`GOOGLE_GENAI_API_KEY` is present at all, because that makes the library ignore both and call the global host. Residency itself is verified against the provider's request logs, not asserted from a URL's shape — that would only hold for one provider.
- **Share links** — a share is a random id and a scope (`all` / `tag` / `document_ids` / `date_range` / `episode`, default 7-day expiry); there is no token, and the key that opens it is in the address after the `#`. A recipient sees the timeline and document pages read-only, can open one document (details, not source text), sees values over time for the shared documents only (`/api/share/:link/trends*`, filtered to `listForShare` ids), and, **only if the link has `include_scans`**, its page images; all of it is answered in the recipient's own browser from the sealed copy (`routes/public-share.ts`), which holds one link and only what it shares, so the scope and the hidden-document rule apply and anything outside is one 404. Those routes are not a control against the reader, who runs them: counts, limits and logs live at the server (`routes/shared.ts`) and the relay.
- **A share link can require approval** — `share_links.require_approval`; the key is then not in the address: a visitor's browser makes a key pair and asks the server (`POST /api/shared/:id/access-request`), the owner approves from their account (`POST /api/share-requests/:id/decision`, never a GET; mailed once per request when a mailer exists), and the owner's device answers with the share key wrapped to that browser's key. SECURITY.md **M-19**, **M-36**.
- **A link is inspected and changed at `/share-links/:id`** — `GET`/`PATCH /api/share-links/:id`; a change uses `checkScope` (the one place a scope is validated, for creating and changing), records what changed in `share_link_events` (small values, never ids or text), refuses a revoked link, and drops held requests when approval is switched on. SECURITY.md **M-22**.
- **A share link can let its recipient ask questions** — `share_links.allow_chat`; `POST /api/share/:link/chat` runs `askSharedAgent` in the recipient's browser with a `Scope` (the link's `listForShare` documents) that **every tool must respect**: a new agent tool either filters by `scope?.ids` or is not built for `shared` (the care-chain tool is not). It stores nothing and passes through `openLink` (scope). Its model calls go through a relay pass for `share:<id>`, counted apart from any account (`SPINE_RELAY_SHARE_DAILY_CALLS`, default 200 a day): that count is the bound, since a limit in the recipient's browser binds nobody. The owner's chat stays owner only. SECURITY.md **M-20**.
- **`GET /share/:id` must return the app shell** — the SPA fallback excludes `/share/`, so this route is the only thing answering a recipient's URL. Returning JSON there (S-15) meant doctors saw `{"ok":true}` instead of the documents.
- **Backups** — `spine-backup.timer` daily: `VACUUM INTO` for the DB (never a file copy, WAL makes that unsafe) and a mirror of the vault's sealed objects `data/vault/` (size and mtime; an object is overwritten when it changes). Shares (`data/shares/`) are not backed up on purpose.
- **Languages** — the web interface is English, Romanian, French and German: strings are English literals in `t()`/`tn()`/`tx()`/`msg()` and the dictionaries are `web/src/i18n/{ro,fr,de}.json`; `i18n-coverage.test.ts` fails on a missing, stale or mis-placeholdered entry, so **a new screen string needs an entry in all three**. Document content is translated on demand by `translation.ts` and cached in `document_translations`, validated by a digest of the translated text (no manual invalidation); shared pages translate through public routes bounded by language, once-per-document caching and a rate limit (SECURITY.md **M-13**). Server error messages stay English.
- **Light and dark** — every colour is a CSS variable generated in `web/tailwind.config.js` from one definition (the dark theme is each scale read the other way), so a screen uses `bg-white`, `gray-*`, `brand-*` and the state hues and needs no `dark:` class. `white` is a surface and inverts (so white text on a strong button turns dark with the button); `snow` stays white for what is dark in both themes (the page viewer, the camera, handles over a photo); an SVG takes a colour as a `fill-*`/`stroke-*` class, never a hex attribute, or it stays light. `web/public/theme.js` sets `data-theme` on `<html>` before the page is drawn (a file, because the content security policy allows no inline script) from `spine.theme` in localStorage (`light` or `dark`; absent follows the device); `ThemeSwitcher` (sun and moon) toggles, and choosing the device's own look clears the choice (`web/src/theme.ts`).
- **Export and import** — `GET /api/documents/:id/export` (trimmed to its own pages with the device's PDF tool, pdf-lib; poppler's `pdfseparate`/`pdfunite` in the Node tests) and `GET /api/export` (every finished upload as it is) give a zip of the files plus `manifest.json` (`archive/manifest.ts`: pages with text and word boxes, documents, fields, results, doctors, tags, notes). Uploading a zip goes through the ordinary upload route: a `manifest.json` in the export format means **restore** (`import-file.ts`: rasterize the file, write the rows from the manifest, **no model call**, every id made again, one transaction); any other zip's PDFs and photos are uploaded one by one. Duplicates: a file with a known sha256 is skipped; a document whose page text matches one already held (`documentFingerprint`) is skipped, or if its file also holds new documents, restored but set aside. The whole archive also carries the links between documents (`manifest.links`, naming documents by place in the manifest; written back by `import-links.ts` when the last file is restored); a single document's export has none. Share links, translations, conversations and vectors are not exported. SECURITY.md **M-14**.
- **Similarity** — related documents come from the data first (shared tests by canonical name, doctors; `documents.relatedSignals`) and from meaning second (`embedding/` + `similarity/`, Vertex only, off by default). Vectors live in `document_embeddings` keyed `(document, model)` with a digest of the exact card: stale when the card changes, never compared across models, pruned when a new model is complete, deleted with the document, **never exported or returned by a route**. Comparison is in-memory over one person's vectors (no vector index). `scheduleSync` brings them up to date in the background. ARCHITECTURE.md **Similarity**.
- **Chat** — a panel on every page (`ChatPanel`, state in `ChatProvider` above the routes). `chat/agent.ts` is a LangGraph agent (agent → tools → agent, then `finish`) with **read-only** tools (including `read_pages`, the text read from named pages of an upload: SECURITY.md **M-18**), defined once, that read the signed-in user's id and the question's labels from the graph's state (`ToolRuntime`), never from an argument the model writes; the model passes labels (`D1`) this request gave it, never ids; capped at eight rounds (five for a share recipient), 12k characters a result, 120k a question, 90 s. `TOOL_KINDS` declares each tool `read` or `action` and a test holds all `read`: **an action tool must return a proposal the owner confirms, never execute**. Each question carries `screen` (pointers: page, ids, search text, filters, selected id; no text), resolved by `chat/screen.ts`; the document on screen is `D1` in sections (`D1.results` …) and an answer's `[D1.results]` becomes a link to `/documents/:id?section=results`, which `DocumentPage` scrolls to (`#section-…`). The fixed pipeline (`chat/index.ts`) is the fallback. The reply streams (`stream: true`: NDJSON `step`/`delta`/`reset`/`done`/`error`); only `done` is trusted and stored, and a stopped question keeps nothing. Conversations are stored per user (`chat_conversations`, `chat_messages`; History in the panel; capped; deleted with the account; not exported) and the history the model sees is read from the store with citation markers stripped, never sent by the browser; owner only; `SPINE_CHAT=off` removes it. If the model cannot take tools, or the agent throws, the question is answered by the fixed pipeline (`chat/index.ts`). ARCHITECTURE.md **Ask your records**.
- **Chat actions are proposals** — `chat/actions.ts`: a `propose_*` tool validates like the route Confirm will call, names things by labels the request gave (`D3`, `F2`, `P4`, `L1`), and returns a `Proposal` in `reply.proposals`; it **never writes** (a test holds that). `ProposalCard` writes the words from the data and, on Confirm, sends the proposal's requests to the ordinary routes (`api.chat.run` allowlists the shapes). Security options of a share are the person's to set on the card, never the model's. Proposals are not stored. A new action tool needs: a `TOOL_KINDS` entry of `action`, a card, an allowlist entry in `api.chat.run` if it calls a new route, and a test that its requests are accepted by the real route. SECURITY.md **M-21**.
- **Mixed uploads are sorted by `regroup/`** — signals (no model) propose groups, the `grouping` model task validates each, the plan is stored and nothing changes until the owner confirms the card, which calls `POST /api/source-files/:id/regroup` (`applyRegroup`, one transaction; fields and results follow their pages). Thresholds in `regroup/` are first guesses: tune from the `regrouping analysed` log line. SECURITY.md **M-24**.
- **Possible duplicates are asked, never merged by guess** — `matching/` finds, for what an upload introduced, entries that may be the same as ones already held (names only, no model) and the upload's report asks yes/no; yes goes through the ordinary merge routes, no is remembered in `match_decisions`. Exact matches (name key, code, alias) are the only ones made while reading. SECURITY.md **M-26**.
- **A file can be attached in the chat** — `POST /api/chat/attachments` reuses `acceptParts` (never a second upload path), refuses a conversation that is not the owner's before saving anything, and sets `source_files.chat_conversation_id`, so `announceUpload`/`announceRegroup` add their report to that conversation (`appendNotice`). SECURITY.md **M-25**.
- **The app starts conversations** — `chat/notices.ts`: when an upload finishes the pipeline writes an unread conversation whose message is data (`kind: 'upload'`), not model text; the page draws it in the owner's language and the badge/note come from `GET /api/chat/unread`. A reply keeps the upload on screen for the assistant (`list_uploads`/`get_upload`, the one path by which an unconfirmed upload's documents reach it). SECURITY.md **M-23**.
- **Care chains** (the interface says "Connected documents"; the computed list is "Similar documents") — `document_links` (`from` earlier, `to` later; `requests` | `follow_up` | `same_episode`; `auto`/`owner`; `proposed`/`confirmed`/`dismissed`). `linking/` finds candidates from the data with no model (no candidate, no call), then one `linking` call judges the cards; **a model's answer is only ever a `proposed` link, and it gives no reason**: what is shown as one is the signals the data gave (`linking/why.ts`: shared tests, doctors, tags, provider, days apart, closeness in meaning), stored as JSON in `document_links.reason`, anything else there reads as none; a suggestion is worded "possibly connected" and names no relation until the owner confirms it (FR-ORG-07, FR-ORG-08), and code drops a request or follow-up that runs backwards in time. Re-searching replaces only the proposals for the pairs it judged again, and never a confirmed or dismissed link; the owner's notes go into the linking cards and into the extraction prompt (as context, never as a source of values); links are looked for only once the upload's grouping is confirmed (and after a re-reading); a dismissed pair is never proposed again. Restore calls no model, so it does not look for links; the whole-archive export carries the ones that exist (all states, so the owner's decisions survive) and a restore writes them back once every file is restored, those whose two documents were both restored. Owner only, except that a share recipient sees the confirmed links between documents the link shares (`GET /api/share/:token/documents/:id/connections`, SECURITY.md **M-28**); deleted with the document, the upload and the account. ARCHITECTURE.md **Care chains**.
- **Passkeys** — `routes/passkeys.ts`, `passkeys.ts`, table `user_passkeys` (SECURITY.md **M-33**): WebAuthn with user verification required; a passkey sign-in is two public rate-limited calls (`/api/auth/passkey/options`, `/login`), takes the single-use challenge out of the session before verifying, and is the **second caller of `startSession`** (guard in `second-factor.test.ts`). It stands in for the password and the code. Managing needs a recent password and is mailed. `core/src/testing/authenticator.ts` is a software authenticator, so the real verification runs in tests.
- **Model calls from the device go through the relay** — `routes/relay.ts` (pass and settings for a signed-in account), `relay/` (the service: a neutral protocol in `protocol.ts`, a task name and messages in, a parsed result, message or stream out; it runs the task through the provider adapter its own `SPINE_LLM_PROVIDER` names, so a provider is one file in `llm/adapters/`; it **stores nothing and logs no content**, but does see the plaintext, so say "does not store or log", never "cannot see"), `llm/adapters/relay.ts` and `embedding/adapters/relay.ts` (the device's `relay` provider, whose pass comes from `useRelayHooks`, set in `web/src/core/native/relay-auth.ts`). - **Share links are sealed copies** — `routes/shared.ts` and `shared-files.ts` (the server's part: sealed bytes, end time, the approval handshake, where in the world it was opened; it cannot open a share), `store/slice-policy.ts` (the **allow-list** of what a copy holds, as data every store shares: a new column or table is out of a share until it is named there, and `slice-policy.test.ts` fails until it is; `store/sqlite/slice.ts` only chooses the rows), `web/src/core/share/` (keys, the owner's host `host.ts`, the recipient's `access.ts`), `core/boot-share.ts` (the recipient's core: the same `publicShareRoutes` over the copy). The key is in the address after the `#`; approval mode has none and wraps it to the visitor's key. SECURITY.md **M-36**.
- **The shared code asks the machine for what it cannot do** — `core/src/native-tools.ts` (`NativeTools`: render a PDF, OCR, cut pages out of one, turn and shrink a picture, find stamps and signatures, write a PDF, read and write a zip, say where an address is). The files that used to hold the Node versions (`ingestion/rasterize.ts`, `parser/ocr.ts`, `archive/pdf-pages.ts`, `ingestion/image-ops.ts`, `ingestion/signatures.ts`, `ingestion/text-pdf.ts`, `archive/zip-read.ts`, `archive/zip-write.ts`, `geo.ts`) keep their names and signatures and pass the call to the tool registered with `useNativeTools`, or say that none is. - **The vault and the device core** — the encryption redesign is staged (`docs/crypto-design.md` has the plan and a status table, SECURITY.md **M-34** to **M-36**). Stages 1a to 4 are built: keys made on the device (`web/src/crypto/`, libsodium; the server never receives a password), the server's code running in the browser as a core in a Web Worker (`web/src/core/`: SQLite in WebAssembly, `LocalApp` router (it implements core's `HttpApp`), the in-memory files `shims/fs.ts`, libsodium hashing `native/digests.ts`, browser versions of the native tools in `native/`, saved as sealed pieces by `persist.ts`), model calls through the relay, search on the device, and sealed share links. **Stage 5 is mostly done**: the server registers no record route (`index.ts`; the route files stay because the device's core runs them, SECURITY.md **M-37**) and backs up the vault's ciphertext; the server's database is made from `schema-accounts.ts` alone (the server's store is a type of its own, `AccountsStore`, made by `createAccountsStore` from `schema-accounts.ts`, so server code cannot reach a record: there is no repository to call. `server/src/store.ts` `useAccountsStore()` is called first by every entry point, and a process that does not has no store at all (`getAccountsStore()` fails); the device and the test setup files (`core/src/testing/use-records-store.ts`, `use-accounts-store.ts`) make the store that holds records. `boundary.test.ts` fails if the server's own code calls `getStore` or `createStore`), and the device builds `schema-accounts.ts` + `schema-records.ts`; `npm run test:accounts` runs the server's tests on the accounts-only database. **Saving is never silent** (`web/src/core/boot.ts`, `persist.ts`): the change log forgets what it hands over, so `Persistence` keeps drained changes (`unsent`) until the vault has them and sends them first next time; the core's dirty marker moves only after a save succeeds, so a failed save is retried every couple of seconds; `saveState()` (from `store.changes.pending()`, not SQLite's change counter) says whether anything is unsaved and the page shows `SaveStatus` while a save is failing and asks before the page is left; `close(force)` refuses to lock (code `unsaved`, `UnsavedChangesError` on the page) over changes the vault does not have, and sign-out asks the person. **The worker is one file** (`worker.rollupOptions.output.inlineDynamicImports` in `web/vite.config.ts`): the Node polyfills read `process` as soon as they are evaluated and `src/core/shims/globals.ts` sets it, so a bundler that splits chunks and runs one first leaves the core unable to start (a newer Rollup did exactly that). **Several devices**: the device saves its records as sealed segments of row changes and a snapshot (the rules in `store/sync.ts`, shared by every store, and SQLite's part in `store/sqlite/changes.ts`; `web/src/core/persist.ts`; SECURITY.md **M-38**), not as a database file; a key that was the engine's counter is random now (`store/ids.ts`) and a tag or doctor made on two devices becomes one. A new table of records must be added to `REPLICATED` in `store/sync.ts` (a test fails if the schema and the list disagree). Checks in a real browser: `cd web && npm run check:browser` (each native piece) and `npm run check:app` (the whole app against a real server).
- **Scanning with the camera** — `/scan` (`pages/Scan.tsx`, `web/src/scan/`, FR-ING-06/08/09/10): everything that looks at the picture runs in the browser. `detect.ts` wraps [scanic](https://github.com/marquaye/scanic) (MIT, classical edge detection and contours in WebAssembly, loaded on this screen only; its optional neural detector fetches a model from a CDN, so it is not used) for finding the corners and straightening, and keeps `steady` (steady-frame test for auto-capture) and `defaultQuad`; the library's own detection is tried by hand on real photos, not in tests, because it needs a browser; `enhance.ts` flattens shadows by dividing by a blurred max-filter background and stretches levels (no thresholding, so handwriting survives) and `greyscale` adds contrast in greys; each page is kept in four versions (original, clean, grey, black and white) and the person picks one per page; black and white is one cut-off on the cleaned page and can lose pale print, so it is never the default; `CornerEditor` is the manual fix. Pages are reviewed, reordered, corrected and saved through `/api/source-files/upload-photos` as a photo set (one PDF, a page each) **plus the photos as taken, sent as `originals`**, kept in `<id>.raw/` beside the PDF (`ingestion/raw-originals.ts`, `source_files.raw_count`, owner-only `GET /api/source-files/:id/originals/:n`, removed with the upload and its backup copy). A photo set is read by **local OCR** when the parser is `ocr` or hybrid with Tesseract on (`localOcrReadsPhotoSets()`), else by a model if image reading is allowed, else refused. Algorithms are tested with `cd web && npm test`.
- **Consent and the legal texts** — `core/src/consent.ts`: `HEALTH_CONSENT_VERSION` and `TERMS_VERSION` (the device creates its own user with them), `server/src/legal.ts` the texts; `users.health_consent_*`/`terms_*` record each act apart with the version shown (GDPR Art. 9(2)(a) is not folded into the terms). Sign-up (`open`) requires both booleans; an account the operator made, or any account when a version is raised, is held by `requireAuth` (403 `consent_required`; only `/api/auth/`, `/api/account/consent` and `/api/account/delete` pass) until `POST /api/account/consent`; the web shows `ConsentGate`. `GET /api/legal/:doc` (public) serves `docs/legal/{privacy,terms,purpose}.md` (`SPINE_LEGAL_DIR` replaces them; `{{operator}}`/`{{contact}}` from `SPINE_OPERATOR_NAME`/`_CONTACT`). **Change a text → raise its version.** `POST /api/account/delete` (password again + the address typed) deletes the account, records and files. Model-written text is labelled `AiLabel` (summaries) and the chat says so (AI Act Art. 50). Drafts for the lawyer: `docs/compliance/`.
- **Sample records** — `POST /api/demo` (`demo/`, FR-ACC-03) writes five invented documents (English or Romanian; consultation, two lab reports with the same five tests, a prescription, a chest X-ray; dates counted back from today) into the caller's own archive through the restore path (`startRestore`, so no model and nothing leaves the host), marked `source_files.sample`; `DELETE /api/demo` removes exactly those uploads; a second load is 409. They are ordinary records of that account, not a shared account. The timeline offers them on an empty archive and shows a banner while they are there. **The demo** (Try the demo on the front page) loads the same records into a core started with no vault and no share host: no account, nothing saved, gone on a reload (SECURITY.md **M-39**). With `SPINE_DEMO_UPLOADS=on` the visitor may also read a few files of their own, after agreeing to it: the core is given the server's settings and the demo's pass, `demo/limits.ts` refuses a file past the limit or a zip and the pipeline keeps the first pages only (the stored file too), and "Keep them in an account" holds the demo's export in IndexedDB (`web/src/demo-carry.ts`, a day at most) until the signed-in account restores it (`DemoCarryOver`, no model call). The device registers each route file with `LocalApp.register`, which keeps a file's hooks to its own routes, as Fastify does.
- **Episodes** — `episodes`/`episode_documents` (store `episodes`, `routes/episodes.ts`, `episodes/index.ts`): groups of documents the owner confirms (FR-ORG-01). The app proposes from data only (links, same provider within 14 days), with an **empty title** shown as provider and dates, so no title can state a clinical inference; a proposal for the same documents keeps its id; a document is in one live episode (`fill` in one transaction); `ON DELETE CASCADE` on the document. `/api/documents` filters by `episode`, `provider` (facility) and `specialty`. A share scope `episode` resolves the confirmed episodes' documents whenever the copy is built, at creation and at each refresh while the owner's device is open (SECURITY.md **M-32**, **M-36**). Exported in manifest version 3 and restored by `LinkRestore`.
- **Library** — tags, providers (`documents.provider`) and tests (`measurements.canonical` + `measurement_aliases`) are managed in `/library` (and doctors on their own page): rename (an existing name merges), remove. Tags always go through `cleanTag`; a tag rename/merge rewrites share links' tag scope in the same transaction. Extraction is given the person's tags and test names to prefer. ARCHITECTURE.md **The Library**.
- **Share scoping is fail-closed** — `share-scope.ts` is the single place a scope is validated. Creation rejects a scope it cannot fully resolve; the read path re-resolves the stored row and serves nothing if it cannot. No branch there may widen a query (SECURITY.md **P2**).
- **A sign-in is a row the owner can end** — `user_sessions` makes the cookie valid (`authenticate` checks it every request: idle 24 h, absolute 14 days); `startSession` is the only place `session.userId` is assigned and only the two login steps call it (a test fails otherwise); `requireRecentAuth` (password typed in the last ten minutes, `POST /api/auth/reauth`; the web `req()` opens the dialog on a `reauth_required` 403) guards the server's own sensitive routes (account deletion, passkey management, making a vault or changing a credential). On the device it is always satisfied (`useRequestAuth` in `web/src/core/boot.ts`: the vault being open means the password was just typed), so the whole-archive export and a share link with `include_scans` ask for nothing more there. SECURITY.md **M-27**.
- **Limits keyed on `req.ip` need a trusted proxy list, not `true`** — `trust-proxy.ts`, and nginx overwrites `X-Forwarded-For` with `$remote_addr`; either alone makes it safe. SECURITY.md **S-31**.
- **Every model request is counted** — `spendModelCall()` in `llm/budget.ts` runs in `invokeValidated` and in the agent's `callStreaming`; a new path to a model must call it. **S-35**.
- **Login is rate limited** — per source via `@fastify/rate-limit`, plus an instance-wide cap written by hand because the plugin only applies its first hook per request. Both are options on `authRoutes` so tests drive the real limiter.
- **Interpolated SQL identifiers come from a whitelist** — `PATCH /api/documents/:id` builds its `SET` clause from column names, so request-body keys are checked against `UPDATABLE_COLUMNS` first. A `Body` type is not a runtime guard.

## Tests

`npm test` runs the suite; `npm run test:coverage` reports coverage (above 90% for statements and branches). **`npm run test:integration`** (server/) runs the flows against the real model in `.env` and poppler (`src/__integration__/`, `*.it.ts`, `docs/testing.md`): it is never part of `npm test` (which blanks the provider key so a unit test cannot call a model), forces an in-memory database, a temporary data directory and no mailer, and asserts what must hold whatever the model says. Run it after changing a prompt, a tool, the pipeline or the model; when it fails and the unit tests pass, add a unit test for the real state first. A new user-facing flow needs a scenario in `docs/scenarios.md` and, if it depends on what a model returns, an integration flow.

Intentionally uncovered (integration tests would need real PDFs or live provider credentials):
- `rasterize.ts` — PDF rasterizer
- the `invoke` paths in `llm/adapters/*` — they need live provider credentials. Their configuration refusals (missing endpoint/region/project, stray Google API key) are covered, and the interface is tested through fake task clients built with `RunnableLambda.from`, not a mocked vendor SDK
