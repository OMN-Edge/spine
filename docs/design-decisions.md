## Records and the store

- **All data access goes through the store interface** — `getStore()` returns a `Store` of repositories. **No SQL and no `better-sqlite3` import may exist outside `core/src/store/sqlite/`** (the repositories are written against `driver.ts`'s small `Database` interface; the native module is imported by `server/src/driver-native.ts` (and by `core/src/testing/driver-native.ts` for core's own tests), and a process says which driver it uses with `useDriver`, and `npm run test:shim` runs the whole suite on the WebAssembly driver the browser will use); there are currently zero `.prepare()` calls elsewhere. Every repository method takes the acting user's id as its first parameter, with exactly seven exceptions enumerated in `store/types.ts` (reads scoped by a share link's owner, the owner device's record of an open, the public side of a sealed share, a new device's enrolment, boot-time maintenance, the users repository, the cookie session's state). Every statement on a user-owned table filters by `user_id`; a method called without a user throws; a record that is not the caller's answers 404. `__tests__/isolation.test.ts` checks all of it as a second user.
- **New tables carry `user_id` and new queries list explicit columns** — `SELECT *` on a table with `user_id` sends it to the client, including to share recipients. `response-shape.test.ts` scans whole responses.
- **Schema changes need an empty database, except a new column with a default** — `CREATE TABLE IF NOT EXISTS` cannot alter a table, and startup refuses an old-shape database. A new defaulted column is added on open by `addColumnsInPlace` in `store/sqlite/connection.ts` (with a test against a database made without it); anything else (rename, remove, retype) needs a migration runner, which does not exist.
- **Repository methods are all async** even though SQLite is synchronous: the interface spans drivers, and a networked store is async. `transaction(fn)` uses explicit `BEGIN`/`COMMIT` with `SAVEPOINT` for nesting, because `db.transaction()` throws on an async callback.
- **SQLite** — the server's `data/spine.db` (WAL; accounts only) and, on the device, an in-memory database saved as sealed objects. No migration runner: schema is idempotent `CREATE TABLE IF NOT EXISTS`, which cannot alter an existing table, so a schema change other than a new defaulted column (see above) means editing the schema files (`schema-accounts.ts`, `schema-records.ts`) and deleting `data/spine.db*` — **only safe while the archive is empty**; startup refuses an old-shape database and says how many records it holds. A runner is needed before the first change to a populated database. Back up `data/spine.db` + `data/vault/`.
- **In-memory SQLite for tests** — `SPINE_DB_PATH=:memory:` is set in `vitest.config.ts`, not in test files. `resetStore()` is called in `buildTestApp()` between test files, and fixtures are built through the interface via `__tests__/helpers/seed.ts` rather than raw SQL (P10 — and it is what proves the interface is complete).
- **Interpolated SQL identifiers come from a whitelist** — `PATCH /api/documents/:id` builds its `SET` clause from column names, so request-body keys are checked against `UPDATABLE_COLUMNS` first. A `Body` type is not a runtime guard.

## Reading an upload

- **Parsing goes through the parser interface** — one entry per page image, in order, with boxes in that image's pixel space (the text-layer adapter scales from the page's size in points).
  - PDF.js reads only the PDF's own text layer: no OCR, no layout model. A page with no text layer returns no elements. (`auto` is one decision for the whole file, and its `ocr` label is never set.)
  - `hybrid` goes cheapest first per page: text layer (what the text layer held, at least `SPINE_TEXT_LAYER_MIN_CHARS`) → local Tesseract if its confidence is good → the model. It never sends a page that has a text layer, and fails the upload if the file cannot be opened rather than treating every page as scanned.
  - Images leave the host only via `readPage` (a page; `multimodal`/`hybrid`, or a photo) and `readStamps` (small signature-stamp crops from a PDF's last page, `ingestion/signatures.ts`), and only with `SPINE_MULTIMODAL_ENABLED`. If the model fails, the page keeps local OCR, and a failed stamp read adds no doctors and never fails the upload.
  - "Read page with AI" (`ingestion/ai-reading.ts`) sends only that page through the same parser and switch, then extracts only the documents that contain it again; "Read whole document" (`strategy: "configured"` on the same route) reads all of a document's visible pages in one call with the configured parser, as an upload does (text layer, then OCR, then a model, depending on `SPINE_PARSER`), keeps the grouping, and extracts again; it sends an image only if that parser does, so it needs the switch only then. A page that comes back unread keeps its earlier text.
  - Model-read pages are stored as `multimodal` with text and **no boxes** (a model's estimate of where text sits was unreliable, so it is not asked for): a field read from one keeps its source page and gets no highlight, and the UI draws none on such a page. Exact boxes come only from the PDF's text layer and from local OCR.
- **Ingestion pipeline is fire-and-forget** — `startIngestionJob(sourceFileId, userId)` returns immediately; status tracked in an in-memory registry, polled by the browser.
- **Structured extraction** — per-type guides in `llm/doc-types.ts`; numeric results are `measurements` (parsed and flagged in `ingestion/measurements.ts`), people are a per-user `doctors` directory (`doctors.ts` matches names), related fields share a `group_no`. Edits to all of these go through the one atomic `PATCH /api/documents/:id`.
- **Page images are authenticated** — served by `GET /api/pages/:id/image` (by the device's `LocalApp`), streamed from the file store. The server never mounts `DATA_DIR` statically: it holds `spine.db` and the sealed vault.
- **Bbox grounding** — fractional coordinates (0–1). Exact string containment first, then LCS fuzzy match (threshold: 60% of needle length).
- **Documents are read after the grouping is confirmed, not before** — (an upload of exactly one page has no grouping to check: `pipeline.ts` starts `startReadingUpload(..., true)` for it) the pipeline only parses and groups (`documents.needs_reading = 1`); `POST /api/source-files/:id/grouping/confirm` runs `read-upload.ts` (one extraction per document, then stamps and signatures, then confirms, embeds and looks for links); a change to a document's pages marks it again; `/extract` (Done) only marks while the upload is unconfirmed. Anything that read at upload time (tests, integration flows) now calls `readUpload()` first. SECURITY.md **M-29**.
- **The grouping is confirmed before documents are shown** — the pipeline sets `source_files.grouping_confirmed = 0` when it finishes; until the owner confirms (`POST /api/source-files/:id/grouping/confirm`) the upload's documents are held back by the same fragment as set-aside ones (`VISIBLE = NOT_SET_ASIDE AND UPLOAD_CONFIRMED`, `store/sqlite/visibility.ts`) and cannot be marked reviewed; confirming schedules embeddings and links. The column defaults to 1: old uploads, restores and tests are confirmed. `includeUnconfirmed` (upload screens) or `includeHidden` (regrouping) list them anyway. **Every new query over the owner's documents uses `VISIBLE`.** `docs/architecture/ingestion.md` **Confirming the grouping**.
- **Hidden pages and set-aside documents** — `pages.hidden` sets a page aside (kept, but out of the document's view, search and reading); a document with pages and none shown is *set aside* (`store/sqlite/visibility.ts`'s one SQL fragment) and is left out of the timeline, search, review, shares, doctors' lists and trends (through `VISIBLE`) unless `includeHidden` is passed (the regrouping screen only). Regrouping saves with `defer`, and Done reads the changed documents once (a fully hidden one is `skipped`).
- **Pages can be moved** — `page_number` is a page's place in the upload (ranges and the UI use it), `source_page` its immutable index in the file, which is what the parser and the stamp reader count: **anything that re-reads a page asks for `source_page`**, never `page_number`. A move (`ingestion/move-page.ts`, `POST /api/pages/:id/move`) rewrites a list of lists in one transaction and renumbers; document order never changes. Screens about the whole upload (cards, search, review, the grouping screen) show the file's number; a document's own screen numbers its pages from 1 and gives the file's number as a tooltip.
- **Pages can be turned** — `POST /api/pages/:id/rotate` (90, 180, 270 clockwise) rewrites the stored page image in place (through a staged file), swaps `image_width`/`image_height`, adds to `pages.rotation`, and moves every box drawn on it (`pages.elements`, `extracted_fields` and `measurements` bboxes: `geometry.ts`'s `rotateBox`) in one store call. A reading of the PDF's text layer comes back in the file's orientation, so `pages.updateReading` turns the `native_text` boxes by the stored rotation; OCR boxes are of the image as it is and a model's reading has none. The image route is `no-cache` with `Last-Modified` (304 on a match) and the web adds `?r=<rotation>` to the URL, because a turned image must not be shown from a copy. Re-reading never rasterizes the PDF again, it reads the stored image, so a turn survives it.
- **Values to check** — extraction scores each field and result 0–1 (the prompt defines it as certainty that the value is exactly what is printed); below `LOW_CONFIDENCE` (0.7, `confidence.ts`) and not edited by the owner a row is `needs_check`, and a document's `to_check` counts them until it is reviewed. The document card, the review queue and the document page mark them "check". FR-EXT-04.
- **What the owner edits is sticky** — `documents.owner_edited` (headline columns), `extracted_fields.owner_edited`, `measurements.owner_edited` and `removed_readings`; a re-reading (`applyReading`/`storeReading`) keeps them, deletes only unedited values (`deleteUnedited`) and does not bring back what was removed. Tags and doctors are still replaced. The owner's notes go into the extraction prompt as context only. `docs/architecture/ingestion.md` **What the owner edits stays edited**.
- **Mixed uploads are sorted by `regroup/`** — signals (no model) propose groups, the `grouping` model task validates each, the plan is stored and nothing changes until the owner confirms the card, which calls `POST /api/source-files/:id/regroup` (`applyRegroup`, one transaction; fields and results follow their pages). Thresholds in `regroup/` are first guesses: tune from the `regrouping analysed` log line. SECURITY.md **M-24**.
- **Possible duplicates are asked, never merged by guess** — `matching/` finds, for what an upload introduced, entries that may be the same as ones already held (names only, no model) and the upload's report asks yes/no; yes goes through the ordinary merge routes, no is remembered in `match_decisions`. Exact matches (name key, code, alias) are the only ones made while reading. SECURITY.md **M-26**.
- **Export and import** — `GET /api/documents/:id/export` (trimmed to its own pages with the device's PDF tool, pdf-lib; poppler's `pdfseparate`/`pdfunite` in the Node tests) and `GET /api/export` (every finished upload as it is) give a zip of the files plus `manifest.json` (`archive/manifest.ts`: pages with text and word boxes, documents, fields, results, doctors, tags, notes). Uploading a zip goes through the ordinary upload route: a `manifest.json` in the export format means **restore** (`import-file.ts`: rasterize the file, write the rows from the manifest, **no model call**, every id made again, one transaction); any other zip's PDFs and photos are uploaded one by one. Duplicates: a file with a known sha256 is skipped; a document whose page text matches one already held (`documentFingerprint`) is skipped, or if its file also holds new documents, restored but set aside. The whole archive also carries the links between documents (`manifest.links`, naming documents by place in the manifest; written back by `import-links.ts` when the last file is restored); a single document's export has none. Share links, translations, conversations and vectors are not exported. SECURITY.md **M-14**.

## Models and the relay

- **LLM access goes through the interface** — `getChatLlm()`, which reads the LLM config on first use and memoizes. No init step: `index.ts` just calls it once at startup so a bad provider stops the process there rather than at the first upload. Adding a provider is a map entry in `llm/index.ts` plus a file in `llm/adapters/`, never a new conditional. The two tasks are defined in `llm/tasks.ts` (budget + schema, both fixed at startup) and an adapter returns one bound LangChain `Runnable` per task. **No provider package (`ChatAnthropic`, `ChatVertexAI`) may be imported outside `llm/adapters/`**; `@langchain/core` above that line is fine — it is the shared abstraction, and the seam type. Every response is validated with zod before it reaches the database; a validation failure logs and degrades to a reviewable fallback rather than killing the upload.
- **Vertex residency is configuration, not code inspection** — endpoint, region and project must all be stated (nothing defaults to a global endpoint), and startup fails if `GOOGLE_API_KEY`/`GEMINI_API_KEY`/`GOOGLE_GENAI_API_KEY` is present at all, because that makes the library ignore both and call the global host. Residency itself is verified against the provider's request logs, not asserted from a URL's shape — that would only hold for one provider.
- **Model calls from the device go through the relay** — `routes/relay.ts` (pass and settings for a signed-in account), `relay/` (the service: a neutral protocol in `protocol.ts`, a task name and messages in, a parsed result, message or stream out; it runs the task through the provider adapter its own `SPINE_LLM_PROVIDER` names, so a provider is one file in `llm/adapters/`; it **stores nothing and logs no content**, but does see the plaintext, so say "does not store or log", never "cannot see"), `llm/adapters/relay.ts` and `embedding/adapters/relay.ts` (the device's `relay` provider, whose pass comes from `useRelayHooks`, set in `web/src/core/native/relay-auth.ts`). The agent graph (LangGraph, `chat/agent.ts`) runs on the device and binds its tools to the relay agent model, which sends their declarations; the relay's model answers with tool calls the device runs. SECURITY.md **M-35**, `docs/relay.md`.
- **Every model request is counted** — `spendModelCall()` in `llm/budget.ts` runs in `invokeValidated` and in the agent's `callStreaming`; a new path to a model must call it. **S-35**.

## Organising documents

- **Similarity** — related documents come from the data first (shared tests by canonical name, doctors; `documents.relatedSignals`) and from meaning second (`embedding/` + `similarity/`, Vertex only, off by default). Vectors live in `document_embeddings` keyed `(document, model)` with a digest of the exact card: stale when the card changes, never compared across models, pruned when a new model is complete, deleted with the document, **never exported or returned by a route**. Comparison is in-memory over one person's vectors (no vector index). `scheduleSync` brings them up to date in the background. `docs/architecture/ingestion.md` **Similarity**.
- **Care chains** (the interface says "Connected documents"; the computed list is "Similar documents") — `document_links` (`from` earlier, `to` later; `requests` | `follow_up` | `same_episode`; `auto`/`owner`; `proposed`/`confirmed`/`dismissed`). `linking/` finds candidates from the data with no model (no candidate, no call), then one `linking` call judges the cards; **a model's answer is only ever a `proposed` link, and it gives no reason**: what is shown as one is the signals the data gave (`linking/why.ts`: shared tests, doctors, tags, provider, days apart, closeness in meaning), stored as JSON in `document_links.reason`, anything else there reads as none; a suggestion is worded "possibly connected" and names no relation until the owner confirms it (FR-ORG-07, FR-ORG-08), and code drops a request or follow-up that runs backwards in time. Re-searching replaces only the proposals for the pairs it judged again, and never a confirmed or dismissed link; the owner's notes go into the linking cards and into the extraction prompt (as context, never as a source of values); links are looked for only once the upload's grouping is confirmed (and after a re-reading); a dismissed pair is never proposed again. Restore calls no model, so it does not look for links; the whole-archive export carries the ones that exist (all states, so the owner's decisions survive) and a restore writes them back once every file is restored, those whose two documents were both restored. Owner only, except that a share recipient sees the confirmed links between documents the link shares (`GET /api/share/:token/documents/:id/connections`, SECURITY.md **M-28**); deleted with the document, the upload and the account. `docs/architecture/ingestion.md` **Care chains**.
- **Episodes** — `episodes`/`episode_documents` (store `episodes`, `routes/episodes.ts`, `episodes/index.ts`): groups of documents the owner confirms (FR-ORG-01). The app proposes from data only (links, same provider within 14 days), with an **empty title** shown as provider and dates, so no title can state a clinical inference; a proposal for the same documents keeps its id; a document is in one live episode (`fill` in one transaction); `ON DELETE CASCADE` on the document. `/api/documents` filters by `episode`, `provider` (facility) and `specialty`. A share scope `episode` resolves the confirmed episodes' documents whenever the copy is built, at creation and at each refresh while the owner's device is open (SECURITY.md **M-32**, **M-36**). Exported in manifest version 3 and restored by `LinkRestore`.
- **Library** — tags, providers (`documents.provider`) and tests (`measurements.canonical` + `measurement_aliases`) are managed in `/library` (and doctors on their own page): rename (an existing name merges), remove. Tags always go through `cleanTag`; a tag rename/merge rewrites share links' tag scope in the same transaction. Extraction is given the person's tags and test names to prefer. `docs/architecture/ingestion.md` **The Library**.

## Sharing

- **Share links** — a share is a random id and a scope (`all` / `tag` / `document_ids` / `date_range` / `episode`, default 7-day expiry); there is no token, and the key that opens it is in the address after the `#`. A recipient sees the timeline and document pages read-only, can open one document (details, not source text), sees values over time for the shared documents only (`/api/share/:link/trends*`, filtered to `listForShare` ids), and, **only if the link has `include_scans`**, its page images; all of it is answered in the recipient's own browser from the sealed copy (`routes/public-share.ts`), which holds one link and only what it shares, so the scope and the hidden-document rule apply and anything outside is one 404. Those routes are not a control against the reader, who runs them: counts, limits and logs live at the server (`routes/shared.ts`) and the relay.
- **A share link can require approval** — `share_links.require_approval`; the key is then not in the address: a visitor's browser makes a key pair and asks the server (`POST /api/shared/:id/access-request`), the owner approves from their account (`POST /api/share-requests/:id/decision`, never a GET; mailed once per request when a mailer exists), and the owner's device answers with the share key wrapped to that browser's key. SECURITY.md **M-19**, **M-36**.
- **A link is inspected and changed at `/share-links/:id`** — `GET`/`PATCH /api/share-links/:id`; a change uses `checkScope` (the one place a scope is validated, for creating and changing), records what changed in `share_link_events` (small values, never ids or text), refuses a revoked link, and drops held requests when approval is switched on. SECURITY.md **M-22**.
- **A share link can let its recipient ask questions** — `share_links.allow_chat`; `POST /api/share/:link/chat` runs `askSharedAgent` in the recipient's browser with a `Scope` (the link's `listForShare` documents) that **every tool must respect**: a new agent tool either filters by `scope?.ids` or is not built for `shared` (the care-chain tool is not). It stores nothing and passes through `openLink` (scope). Its model calls go through a relay pass for `share:<id>`, counted apart from any account (`SPINE_RELAY_SHARE_DAILY_CALLS`, default 200 a day): that count is the bound, since a limit in the recipient's browser binds nobody. The owner's chat stays owner only. SECURITY.md **M-20**.
- **`GET /share/:id` must return the app shell** — the SPA fallback excludes `/share/`, so this route is the only thing answering a recipient's URL. Returning JSON there (S-15) meant doctors saw `{"ok":true}` instead of the documents.
- **Share links are sealed copies** — `routes/shared.ts` and `shared-files.ts` (the server's part: sealed bytes, end time, the approval handshake, where in the world it was opened; it cannot open a share), `store/slice-policy.ts` (the **allow-list** of what a copy holds, as data every store shares: a new column or table is out of a share until it is named there, and `slice-policy.test.ts` fails until it is; `store/sqlite/slice.ts` only chooses the rows), `web/src/core/share/` (keys, the owner's host `host.ts`, the recipient's `access.ts`), `core/boot-share.ts` (the recipient's core: the same `publicShareRoutes` over the copy). The owner's `routes/share.ts` calls `shareHost()` (set by the device) to publish, revoke, collect what visitors did and answer a request; a process without one answers every owner share route with 503 (`no_share_host`). The key is in the address after the `#`; approval mode has none and wraps it to the visitor's key. SECURITY.md **M-36**.
- **Share scoping is fail-closed** — `share-scope.ts` is the single place a scope is validated. Creation rejects a scope it cannot fully resolve; the read path re-resolves the stored row and serves nothing if it cannot. No branch there may widen a query (SECURITY.md **P2**).

## The assistant

- **Chat** — a panel on every page (`ChatPanel`, state in `ChatProvider` above the routes). `chat/agent.ts` is a LangGraph agent (agent → tools → agent, then `finish`) with **read-only** tools (including `read_pages`, the text read from named pages of an upload: SECURITY.md **M-18**), defined once, that read the signed-in user's id and the question's labels from the graph's state (`ToolRuntime`), never from an argument the model writes; the model passes labels (`D1`) this request gave it, never ids; capped at eight rounds (five for a share recipient), 12k characters a result, 120k a question, 90 s. `TOOL_KINDS` declares each tool `read` or `action` and a test holds all `read`: **an action tool must return a proposal the owner confirms, never execute**. Each question carries `screen` (pointers: page, ids, search text, filters, selected id; no text), resolved by `chat/screen.ts`; the document on screen is `D1` in sections (`D1.results` …) and an answer's `[D1.results]` becomes a link to `/documents/:id?section=results`, which `DocumentPage` scrolls to (`#section-…`). The fixed pipeline (`chat/index.ts`) is the fallback. The reply streams (`stream: true`: NDJSON `step`/`delta`/`reset`/`done`/`error`); only `done` is trusted and stored, and a stopped question keeps nothing. Conversations are stored per user (`chat_conversations`, `chat_messages`; History in the panel; capped; deleted with the account; not exported) and the history the model sees is read from the store with citation markers stripped, never sent by the browser; owner only; `SPINE_CHAT=off` removes it. If the model cannot take tools, or the agent throws, the question is answered by the fixed pipeline (`chat/index.ts`). `docs/architecture/ingestion.md` **Ask your records**.
- **Chat actions are proposals** — `chat/actions.ts`: a `propose_*` tool validates like the route Confirm will call, names things by labels the request gave (`D3`, `F2`, `P4`, `L1`), and returns a `Proposal` in `reply.proposals`; it **never writes** (a test holds that). `ProposalCard` writes the words from the data and, on Confirm, sends the proposal's requests to the ordinary routes (`api.chat.run` allowlists the shapes). Security options of a share are the person's to set on the card, never the model's. Proposals are not stored. A new action tool needs: a `TOOL_KINDS` entry of `action`, a card, an allowlist entry in `api.chat.run` if it calls a new route, and a test that its requests are accepted by the real route. SECURITY.md **M-21**.
- **A file can be attached in the chat** — `POST /api/chat/attachments` reuses `acceptParts` (never a second upload path), refuses a conversation that is not the owner's before saving anything, and sets `source_files.chat_conversation_id`, so `announceUpload`/`announceRegroup` add their report to that conversation (`appendNotice`). SECURITY.md **M-25**.
- **The app starts conversations** — `chat/notices.ts`: when an upload finishes the pipeline adds a message to the owner's one Activity conversation (`origin = 'activity'`, unread again with each report; the conversation a file was attached in gets it instead), data (`kind: 'upload'`), not model text; the page draws it in the owner's language and the badge/note come from `GET /api/chat/unread`. A reply keeps the upload on screen for the assistant (`list_uploads`/`get_upload`, the one path by which an unconfirmed upload's documents reach it). SECURITY.md **M-23**.
- **Helping a person start** — `core/src/help.ts` (fixed answers about Spine, translated through the dictionaries; `i18n-coverage.test.ts` reads it), `routes/guide.ts` (`guide_marks`: what was shown, a records table, synced, never shared or exported), `web/src/guide.tsx` (the chat opens on a welcome the first time only, a note offers it three more times, then nothing), `GuideTip` (a tip once, until "Got it") and `GetStarted` on the timeline. `POST /api/chat/help` writes an answer into the conversation or Getting started without a model; the agent's `explain_spine` reads the same text, and the agent runs on an empty archive so it can. **A change to sharing, reading or the keys that makes a sentence in `help.ts` false changes it there.** SECURITY.md **M-42**.

## Accounts and sign-in

- **Verification and reset links** — tokens are hashed at rest, spent by one atomic `UPDATE`, carried in the URL **fragment** (never sent to the server, so not in nginx's log) and spent by a `POST`. Requests that name an address answer identically whether or not it has an account, and mail is sent after the response. Mail has no attachment field and neutral wording; a test fails on clinical words.
- **Two-factor** — optional TOTP per user (`totp.ts`, `routes/totp.ts`). With it on, the right password only starts a *pending* login in the session; `POST /api/auth/login/second-factor` completes it. The secret is AES-GCM encrypted under a key derived from `SESSION_SECRET` (rotating that secret orphans every enrolment); the last used step blocks replay; recovery codes are sha256-hashed and single use. Tables are new (`user_totp`, `user_recovery_codes`), because a new table needs no migration and a new column would.
- **Auth** — email + argon2id password; `requireAuth` re-resolves the session to a live user on every request and sets `req.userId`, which handlers pass to the store. A changed password bumps `auth_version`, ending that user's other sessions. An unknown email and a wrong password are indistinguishable in answer and time.
- **A device can be let in by one that is signed in** — `routes/enrolment.ts`, `web/src/crypto/enrolment.ts`, table `device_enrolments` (SECURITY.md **M-41**): the signed-in device makes a one-time code (never sent anywhere), seals the account key under a key the code makes and leaves it under an id the code also makes; the new device asks (`/api/enrol/request`), the owner approves what asked (`/api/enrol/decision`, `requireRecentAuth`), and it collects the sealed key with a sign-in (`/api/enrol/claim`), once, in ten minutes. It is the **third caller of `startSession`** (guard in `second-factor.test.ts`) and passes `passwordTyped: false`, so the server's sensitive routes still ask for the password there. The new device opens the vault through the passkey path (`unlockWithPasskey`, credential id `enrol:<id>`).
- **Passkeys** — `routes/passkeys.ts`, `passkeys.ts`, table `user_passkeys` (SECURITY.md **M-33**): WebAuthn with user verification required; a passkey sign-in is two public rate-limited calls (`/api/auth/passkey/options`, `/login`), takes the single-use challenge out of the session before verifying, and is the **second caller of `startSession`** (guard in `second-factor.test.ts`). It stands in for the password and the code. Managing needs a recent password and is mailed. `core/src/testing/authenticator.ts` is a software authenticator, so the real verification runs in tests.
- **A sign-in is a row the owner can end** — the cookie session's state is in the accounts database (`cookie_sessions` by the sha256 of its id, `server/src/session-store.ts`), so a restart or a deploy signs no one out (S-16); `user_sessions` makes the cookie valid (`authenticate` checks it every request: idle 24 h, absolute 14 days); `startSession` is the only place `session.userId` is assigned and only the two login steps, the passkey login and the enrolment of a device call it (a test fails otherwise); `requireRecentAuth` (password typed in the last ten minutes, `POST /api/auth/reauth`; the web `req()` opens the dialog on a `reauth_required` 403) guards the server's own sensitive routes (account deletion, passkey management, making a vault or changing a credential). On the device it is always satisfied (`useRequestAuth` in `web/src/core/boot.ts`: the vault being open means the password was just typed), so the whole-archive export and a share link with `include_scans` ask for nothing more there. SECURITY.md **M-27**.
- **Limits keyed on `req.ip` need a trusted proxy list, not `true`** — `trust-proxy.ts`, and nginx overwrites `X-Forwarded-For` with `$remote_addr`; either alone makes it safe. SECURITY.md **S-31**.
- **Login is rate limited** — per source via `@fastify/rate-limit`, plus an instance-wide cap written by hand because the plugin only applies its first hook per request. Both are options on `authRoutes` so tests drive the real limiter.
- **Consent and the legal texts** — `core/src/consent.ts`: `HEALTH_CONSENT_VERSION` and `TERMS_VERSION` (the device creates its own user with them), `server/src/legal.ts` the texts; `users.health_consent_*`/`terms_*` record each act apart with the version shown (GDPR Art. 9(2)(a) is not folded into the terms). Sign-up (`open`) requires both booleans; an account the operator made, or any account when a version is raised, is held by `requireAuth` (403 `consent_required`; only `/api/auth/`, `/api/account/consent` and `/api/account/delete` pass) until `POST /api/account/consent`; the web shows `ConsentGate`. `GET /api/legal/:doc` (public) serves `docs/legal/{privacy,terms,purpose}.md` (`SPINE_LEGAL_DIR` replaces them; `{{operator}}`/`{{contact}}` from `SPINE_OPERATOR_NAME`/`_CONTACT`). **Change a text → raise its version.** `POST /api/account/delete` (password again + the address typed) deletes the account, records and files. Model-written text is labelled `AiLabel` (summaries) and the chat says so (AI Act Art. 50). Drafts for the lawyer: `docs/compliance/`.

## People, family and the emergency card

- **People (profiles)** — an account keeps records for several people: `profile` vault objects each with their own key, one core open at a time (`web/src/core/core.worker.ts`: `profiles`, `createProfile`, `switchProfile`; `web/src/profiles.ts`; `pages/Profiles.tsx`); `PROFILE_CHANGED` remounts what holds records; the choice is remembered per account in `localStorage`. The list of people is read from the server once, at start. The plan's `profiles` (trial 6, free 1, Premium 1) is enforced at `PUT /api/vault/objects/:id` for kind `profile`. SECURITY.md **M-48**.
- **The family plan** — `PlanId` `family` in `core/src/billing/plans.ts` (six people, others let in, 12,000 pages a month), `subscriptions.plan`, read from the prices on a subscription (`planOfItems`); sold only where both `SPINE_PADDLE_PRICE_FAMILY_*` are set; no founding price. SECURITY.md **M-45**.
- **Promotion at eighteen** — `VaultSession.promote` (the person's device) and `POST /api/delegations/:id/promote` / `DelegationRepository.promote` (one transaction over two vaults; sealed files copied first, old ones removed after); the other grants become `paused` with the new key sealed to them; exempt from the plan's limits. The age is the page's rule. SECURITY.md **M-51**.
- **Children and teenagers** — a child's profile has `kind: 'child'` and `born` in its sealed record (`VaultSession.createProfile(name, { kind, born })`, `ProfileSummary`); `core/src/family.ts` is the ages (16 for an account of their own, 18 for the records being theirs) and runs on the device; the `self` delegation role is the person themselves (one account, writes as a guardian); the page offers it only from sixteen. The server cannot check an age. SECURITY.md **M-50**.
- **Letting another account into a profile** — `server/src/routes/delegation.ts` (invitations, grants, `/api/delegated/:grant/objects…` reusing `routes/vault.ts`'s `listObjects`/`getObject`/`putObject`/`deleteObject` with an `ObjectScope`, and the key rotation), tables `profile_invites`/`delegations`, `web/src/crypto/delegation.ts` (a code makes an id, a key and a proof), `VaultSession.invite`/`accept`/`revoke`/`rotateProfile`/`delegated`, the worker's `grant:<id>` people and `reloadKeys`, `ProfileAccess.tsx`, `/invite`. Ending access rotates the profile key and ends the owner's other sign-ins. The plan's `delegation`. SECURITY.md **M-49**.
- **The emergency card** — a yearly review (`reviewed_at`; `review_due` on `GET /api/emergency`; `POST /api/emergency/reviewed`; the server's `remindCardReviews` mails once a year and sees only dates) and `POST /api/emergency/replace` (old bundle off first, then a new id and key; the offline code cannot be replaced); official details (`details`, each `on_card` or not) are kept in the same record and **everything outward is built from `publicCard(card)`** (the sealed card, the offline text, the printed copy); `PrintCard.tsx` is the bank-card-sized print (`printCard()` marks the body and `index.css` shows only it when printing); `VaultSession.updateProfile` corrects a person's name and a child's birth date. `core/src/emergency.ts`, `routes/emergency.ts`, tables `emergency_cards`/`emergency_scans` (synced, never in a share, not exported), the share host's `publishCard`/`revokeCard`, a `card` kind of `shared_bundles` (no end, one for each person up to ten, outside the plan's share limits, 64 KB), the viewer `web/src/pages/CardView.tsx` at the same `/share/<id>` address (`ShareRouter`). The key is in the address after the `#`; every opening is logged and the owner mailed at most every fifteen minutes; an offline code holds the card as plain text and says it cannot be turned off. SECURITY.md **M-47**.

## The device and the vault

- **The shared code asks the machine for what it cannot do** — `core/src/native-tools.ts` (`NativeTools`: render a PDF, OCR, cut pages out of one, turn and shrink a picture, find stamps and signatures, write a PDF, read and write a zip, say where an address is). The files that used to hold the Node versions (`ingestion/rasterize.ts`, `parser/ocr.ts`, `archive/pdf-pages.ts`, `ingestion/image-ops.ts`, `ingestion/signatures.ts`, `ingestion/text-pdf.ts`, `archive/zip-read.ts`, `archive/zip-write.ts`, `geo.ts`) keep their names and signatures and pass the call to the tool registered with `useNativeTools`, or say that none is. The device registers its own when the core starts (`web/src/core/native/index.ts`: PDF.js, Tesseract.js, canvas, pdf-lib, fflate); the server's Node ones (`server/src/native/`: poppler, Tesseract, sharp, pdfkit, yauzl, yazl, maxmind) exist so the whole app can run on Node in the tests that drive it and in the real-model suite, and the production server registers none (it keeps no records), only using `server/src/geo.ts` (maxmind) for where a share was opened. A process that registers none fails at the first use, in words. Providers and the SQLite driver work the same way (`registerLlmProvider`, `useDriver`).
- **The vault and the device core** — the encryption redesign is staged (`docs/crypto-design.md` has the plan and a status table, SECURITY.md **M-34** to **M-36**). Stages 1a to 4 are built: keys made on the device (`web/src/crypto/`, libsodium; the server never receives a password), the server's code running in the browser as a core in a Web Worker (`web/src/core/`: SQLite in WebAssembly, `LocalApp` router (it implements core's `HttpApp`), the in-memory files `shims/fs.ts`, libsodium hashing `native/digests.ts`, browser versions of the native tools in `native/`, saved as sealed pieces by `persist.ts`), model calls through the relay, search on the device, and sealed share links. **Stage 5 is mostly done**: the server registers no record route (`index.ts`; the route files stay because the device's core runs them, SECURITY.md **M-37**) and backs up the vault's ciphertext; the server's database is made from `schema-accounts.ts` alone (the server's store is a type of its own, `AccountsStore`, made by `createAccountsStore` from `schema-accounts.ts`, so server code cannot reach a record: there is no repository to call. `server/src/store.ts` `useAccountsStore()` is called first by every entry point, and a process that does not has no store at all (`getAccountsStore()` fails); the device and the test setup files (`core/src/testing/use-records-store.ts`, `use-accounts-store.ts`) make the store that holds records. `boundary.test.ts` fails if the server's own code calls `getStore` or `createStore`), and the device builds `schema-accounts.ts` + `schema-records.ts`; `npm run test:accounts` runs the server's tests on the accounts-only database. **Saving is never silent** (`web/src/core/boot.ts`, `persist.ts`): the change log forgets what it hands over, so `Persistence` keeps drained changes (`unsent`) until the vault has them and sends them first next time; the core's dirty marker moves only after a save succeeds, so a failed save is retried every couple of seconds; `saveState()` (from `store.changes.pending()`, not SQLite's change counter) says whether anything is unsaved and the page shows `SaveStatus` while a save is failing and asks before the page is left; `close(force)` refuses to lock (code `unsaved`, `UnsavedChangesError` on the page) over changes the vault does not have, and sign-out asks the person. **The worker is one file** (`worker.rollupOptions.output.inlineDynamicImports` in `web/vite.config.ts`): the Node polyfills read `process` as soon as they are evaluated and `src/core/shims/globals.ts` sets it, so a bundler that splits chunks and runs one first leaves the core unable to start (a newer Rollup did exactly that). **Several devices**: the device saves its records as sealed segments of row changes, folded into partial parts and now and then a snapshot (the rules in `store/sync.ts`, shared by every store, and SQLite's part in `store/sqlite/changes.ts`; `web/src/core/persist.ts`; SECURITY.md **M-38**), not as a database file; a key that was the engine's counter is random now (`store/ids.ts`) and a tag or doctor made on two devices becomes one. A new table of records must be added to `REPLICATED` in `store/sync.ts` (a test fails if the schema and the list disagree). **Unlocking is arranged around round trips and a slow phone** (`vaultState.prefetch`, `deriveKey`, `core.worker.ts`'s `start`): the unlock screen warms the worker and fetches the KDF parameters and sealed keys while the password is typed, Argon2id runs in the worker (`device.derive`), and the worker asks for the listing once; built files with a hash in their name are `immutable` (`server/src/static-cache.ts`). **The device keeps a sealed copy of the vault's write-once objects in IndexedDB** (`web/src/crypto/sealed-cache.ts`, SECURITY.md **M-43**): ciphertext only, best effort, cleared at sign-out, and the index is never in it; a page image is fetched ahead of its request (`Persistence.ensure`) because a synchronous read stops the core. Checks in a real browser: `cd web && npm run check:browser` (each native piece) and `npm run check:app` (the whole app against a real server).
- **Scanning with the camera** — `/scan` (`pages/Scan.tsx`, `web/src/scan/`, FR-ING-06/08/09/10): everything that looks at the picture runs in the browser. `detect.ts` wraps [scanic](https://github.com/marquaye/scanic) (MIT, classical edge detection and contours in WebAssembly, loaded on this screen only; its optional neural detector fetches a model from a CDN, so it is not used) for finding the corners and straightening, and keeps `defaultQuad`; the library's own detection is tried by hand on real photos, not in tests, because it needs a browser; `enhance.ts` flattens shadows by dividing by a blurred max-filter background and stretches levels (no thresholding, so handwriting survives) and `greyscale` adds contrast in greys; each page is kept in four versions (original, clean, grey, black and white) and the person picks one per page; black and white is one cut-off on the cleaned page and can lose pale print, so it is never the default; `CornerEditor` is the manual fix. Pages are reviewed, reordered, corrected and saved through `/api/source-files/upload-photos` as a photo set (one PDF, a page each) **plus the photos as taken, sent as `originals`**, kept in `<id>.raw/` beside the PDF (`ingestion/raw-originals.ts`, `source_files.raw_count`, owner-only `GET /api/source-files/:id/originals/:n`, removed with the upload and its backup copy). A photo set is read by **local OCR** when the parser is `ocr` or hybrid with Tesseract on (`localOcrReadsPhotoSets()`), else by a model if image reading is allowed, else refused. Algorithms are tested with `cd web && npm test`.

## The interface and the demo

- **Languages** — the web interface is English, Romanian, French and German: strings are English literals in `t()`/`tn()`/`tx()`/`msg()` and the dictionaries are `web/src/i18n/{ro,fr,de}.json`; `i18n-coverage.test.ts` fails on a missing, stale or mis-placeholdered entry, so **a new screen string needs an entry in all three**. Document content is translated on demand by `translation.ts` and cached in `document_translations`, validated by a digest of the translated text (no manual invalidation); shared pages translate through public routes bounded by language, once-per-document caching and a rate limit (SECURITY.md **M-13**). Server error messages stay English.
- **Light and dark** — every colour is a CSS variable generated in `web/tailwind.config.js` from one definition (the dark theme is each scale read the other way), so a screen uses `bg-white`, `gray-*`, `brand-*` and the state hues and needs no `dark:` class. `white` is a surface and inverts (so white text on a strong button turns dark with the button); `snow` stays white for what is dark in both themes (the page viewer, the camera, handles over a photo); an SVG takes a colour as a `fill-*`/`stroke-*` class, never a hex attribute, or it stays light. `web/public/theme.js` sets `data-theme` on `<html>` before the page is drawn (a file, because the content security policy allows no inline script) from `spine.theme` in localStorage (`light` or `dark`; absent follows the device); `ThemeSwitcher` (sun and moon) toggles, and choosing the device's own look clears the choice (`web/src/theme.ts`).
- **Home screen** — `web/public/manifest.webmanifest` (standalone, scope `/`) and `web/public/icons/` (an opaque 180 px `apple-touch-icon.png` for iOS, which ignores an SVG and fills transparency with black; 192, 512 and a 512 maskable for the rest), named in `web/index.html`'s head; `src/build/home-screen.test.ts` fails if they disagree. There is deliberately no service worker: Spine needs the server and the relay anyway, and one would put a cache that can serve an old core in front of every route, share links included. Regenerate the PNGs from `favicon.svg` when the logo changes.
- **Sample records** — `POST /api/demo` (`demo/`, FR-ACC-03) writes five invented documents (English or Romanian; consultation, two lab reports with the same five tests, a prescription, a chest X-ray; dates counted back from today) into the caller's own archive through the restore path (`startRestore`, so no model and nothing leaves the host), marked `source_files.sample`; `DELETE /api/demo` removes exactly those uploads; a second load is 409. They are ordinary records of that account, not a shared account. The timeline offers them on an empty archive and shows a banner while they are there. **The demo** (Try the demo on the front page) loads the same records into a core started with no vault and no share host: no account, nothing saved, gone on a reload (SECURITY.md **M-39**). With `SPINE_DEMO_UPLOADS=on` the visitor may also read a few files of their own, after agreeing to it: the core is given the server's settings and the demo's pass, `demo/limits.ts` refuses a file past the limit or a zip and the pipeline keeps the first pages only (the stored file too), and "Keep them in an account" holds the demo's export in IndexedDB (`web/src/demo-carry.ts`, a day at most) until the signed-in account restores it (`DemoCarryOver`, no model call). The device registers each route file with `LocalApp.register`, which keeps a file's hooks to its own routes, as Fastify does.

## Operations

- **Backups** — (with `SPINE_OBJECTS=gcs` the vault mirror is skipped: the bucket's own versioning is it) `spine-backup.timer` daily: `VACUUM INTO` for the DB (never a file copy, WAL makes that unsafe) and a mirror of the vault's sealed objects `data/vault/` (size and mtime; an object is overwritten when it changes). Shares (`data/shares/`) are not backed up on purpose.
