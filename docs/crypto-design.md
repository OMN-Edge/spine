# Encryption redesign: build plan and decisions

This is the engineering plan for [key-hierarchy.md](key-hierarchy.md) (the public design). It says how the code gets there, in what order, and what each step changes. Requirements: FR-ACC-01/02, TR-CRY-01..07, TR-SHC-01..05, TR-AI-01..15, TR-INF-04. Status of each stage is kept in the commit history and in the table at the end.

## The shape of the change

The server used to read documents: it rasterized, extracted, searched, chatted, linked and translated. It now holds ciphertext, so all of that runs where the plaintext is, in the browser. (This page is the plan that was followed; the status table at the end says what is built.)

The decision that keeps this tractable: **the browser runs the same core the server runs today, against the same store interface, and the server becomes a ciphertext store.**

- **Auth stays on the server and keeps its shape.** Sign-in, rate limits, sessions, TOTP and the mail flows are unchanged. The only difference is that the "password" the server receives is an *authentication value* the browser derives, not the password.
- **Two derivations from one Argon2id run** (TR-CRY-01). The browser runs Argon2id over the master password with a per-account salt, then derives from the result, with libsodium's key-derivation function (`crypto_kdf`, BLAKE2b-based, two contexts), a **master key** (never leaves the device) and an **authentication value** (sent as the password; the server hashes it again with its own argon2id). The server cannot go from the authentication value to the master key.
- **Keys** (TR-CRY-02, 06): a random 32-byte **account key** is wrapped twice, under the master key and under the **recovery key**. An X25519 **account key pair** has its private half wrapped by the account key. Each **profile** has a random **profile key** wrapped by the account key. Each **sealed object** (a segment of changes, a part of a snapshot, a file) has a random **data key** wrapped by the profile key. Content is sealed with XChaCha20-Poly1305 (libsodium), the object id and kind bound in as associated data so a blob cannot be swapped for another.
- **What the server stores** (TR-CRY-03, TR-INF-04): `vault_keys` (salt, KDF parameters, the wrapped account key twice, the public key, the wrapped private key) and `vault_objects` (opaque id, owner, profile id, a coarse kind, revision, size, timestamps, the wrapped data key, and the ciphertext). Nothing else about a record.
- **The unit of storage is an upload bundle.** The export manifest already describes one uploaded file with its pages' text and boxes, documents, fields, results and edits, and `archive/import-file.ts` restores it without a model. (As built, the unit of storage is a sealed change segment or snapshot part, not an upload bundle: see Syncing devices below.) That code is the serializer: a bundle is sealed JSON of one manifest file entry; page images and the original file are separate sealed blobs under the same data key. A **library** object carries what is shared across uploads (doctors, tags, test aliases, decisions, links, episodes). An **embedding** object carries one document's vector.
- **The browser holds a working database.** On unlock it downloads and opens the objects into an in-memory SQLite (the existing store adapter over a WebAssembly driver), so the existing queries, filters, trends, linking and search run unchanged on the device. Changes are written back as new object revisions.
- **Work that needs native tools moves to the browser's equivalents:** the PDF text layer and page images (pdf.js), OCR (Tesseract compiled to WebAssembly), trimming a PDF for export (pdf-lib), conversion of HEIC and DOCX (already in JavaScript). The Python sidecar and poppler leave the product.
- **Model calls** (TR-AI): the browser calls the relay with the decrypted content; the relay holds the credential, checks the session and the per-user quota, runs the task through the configured provider adapter and writes nothing. The existing LLM interface and prompts move to the browser; the relay is a small pass-through service in this repository. A self-hosted install could point the relay at its own model endpoint (TR-AI-07); an OpenAI-compatible adapter is not built.

## Decisions

**Passkeys.** A passkey proves who is signing in, and with the WebAuthn PRF extension it can also open the vault. Registration asks for the extension; the owner, with the vault open, turns on "Open my records with it" for a passkey: the device asks the authenticator for its PRF output on a fixed input (a hash of a label), makes a key from it, seals the account key under that key and sends only the sealed copy, which the server keeps on the passkey's row (`user_passkeys.wrapped_key`). A later passkey sign-in (or the unlock screen after a reload) gets the sealed copy back with the session, asks for the PRF output again and opens the account key on the device; the PRF output is cut from what is sent to the server, which verifies the sign-in without it. A passkey without the extension, or one not turned on, signs in as before and the vault asks for the master password. Because the account key does not change with the password, the sealed copy stays valid through a change of password; removing the passkey removes it. The consent gate and the lists of sessions are unaffected.

**Password reset.** A reset link can set a new authentication value, but it cannot restore access to the data: the server never held what is needed. Resetting with the recovery kit re-wraps the account key under the new master key, so nothing is lost. Resetting without it creates an empty vault, and the interface says so before the person confirms. `set-password` in the operator CLI refuses an account that has a vault, for the same reason (it still works for an account that has none, which has nothing to lose).

**Operator-created accounts.** The CLI cannot choose a password for someone. `create-user` creates the account without a vault and prints a temporary password that only gets the person to the screen where they agree to the texts, set their own master password and receive their recovery kit; Spine keeps no copy of the one they choose.

**Recovery kit.** A 256-bit recovery key shown once at sign-up as a printable sheet, Base32 in groups, with a short check value so a typing error is caught. The sign-up screen states that the operator cannot recover an account. The person must confirm they have kept it before the vault opens. The kit can be regenerated while signed in, which re-wraps the account key under the new recovery key.

**What the server learns.** The email, that an account exists, the number and size of its objects, when they changed, the coarse kind of each (`profile`, `bundle`, `blob`, `library`, `embedding`, `log`), and share metadata. Titles, dates, tags, doctors, fields, summaries and embeddings are inside sealed objects.

**Account export.** Unchanged for the person: the zip is built in the browser from the decrypted vault, and the importer reads the format that exists (manifest version 3). The server no longer builds it.

**Multiple devices.** Sign in with the master password; the wrapped keys come down with the account, so no separate enrolment step is needed. A device that is already signed in can also let a new one in with a one-time code (SECURITY.md **M-41**): it seals the account key under a key the code makes and leaves it at the server under an id the code also makes; the new device asks with the id, the person approves it, and it collects the sealed key with a sign-in that does not count as the password typed.

## Order of work and acceptance

Each stage ends with the suite green, the documents updated, and a commit. Nothing is switched on for users until the stage before it is complete.

| Stage | What | Done when |
| --- | --- | --- |
| 1a | Crypto primitives, key hierarchy, derivation, recovery kit, `vault_keys`, `vault_objects` and their routes, sign-up and sign-in through the derived value, the browser's vault client | A new account signs up with a derived value, a vault round-trips sealed objects, a recovery kit restores access, the server never sees the password or a key |
| 1b | The core in the browser: SQLite in WebAssembly, bundle serialization, sync, ingestion without the sidecar | An upload is read on the device and stored only as ciphertext; the timeline works from the local database |
| 2 | Model calls through the relay; extraction, summaries, chat, linking, translation on the device | No route on the server receives plaintext content |
| 3 | Search and embeddings on the device | Hybrid search runs locally; no vector index on the server |
| 4 | Share links with a key in the fragment, approval mode, emergency card (built with the reintroduction of the cut features, **M-47**) | A recipient reads a shared bundle the server cannot open |
| 5 | Ciphertext-only backups, deletion by destroying keys, removal of the old plaintext tables and routes | A backup contains no plaintext; the old tables are gone |

## Syncing devices

Records are not saved as a database file any more (SECURITY.md **M-38**). The source of truth is a set of sealed objects: segments of changes, a snapshot and the files, and the store that answers the routes is built from them.

- **A change** is one row after a write (`{t: table, k: key columns, r: row or null, h: clock, c?: columns it changed}`), made by a trigger (an update notes the row before it too, to find the columns) and stamped when it was written; its form names tables and columns, not an engine's pages. `Store.changes` has three operations: `drain` (what was written here), `apply` (what other devices wrote; the newest write of each column wins) and `dump` (every row and deletion, for a snapshot or a new device).
- **A save** seals the files written since the last (one `blob` object each, listed in the `vault_files` table), then the drained changes as one `log` object, then looks at the vault for other devices' segments and applies them. It never rewrites an object.
- **Compaction**: when 10 segments wait, a device folds them into one small **partial part** (a sealed `bundle` of those segments' own changes, which it already holds, so nothing is downloaded again), adds it to the snapshot's parts in the index (`library`, written over with the sequence number it was read at; a second device compacting at once gets a conflict and retries) and deletes the segments. A part names the segments it holds (`of`), so a device that has applied them all does not read it. When six partial parts have gathered, or a segment's changes are not at hand, the device writes a new snapshot of everything (sealed `bundle` parts of a dump) in their place and deletes the old parts. A device that opens the vault and finds three or more loose segments folds them on its first save, so each load after that has fewer to read. A device that was away reads the parts it lacks, or applies the new snapshot over its own records. The index only ever names more parts: a device that does not know about partial parts reads them as it reads any part, so devices of different versions share one vault.
- **Opening**: the snapshot's parts, then every segment not folded, then the file list. A new vault gets the starter tags once. Applying the changes sets the search triggers aside and rebuilds the index once at the end (`store/sqlite/changes.ts`, `merging`): each insert of a field or a result used to rebuild its document's whole row of the index, which made the apply grow faster than the archive (600 invented documents of three pages, 30 fields and 20 results: 24 s, then 1.7 s). The console says where the time went (`[core] vault loaded`: objects, bytes and milliseconds for the snapshot and the segments, the time to apply them, and the tables that hold most of the text).
- **Opening quickly** (a phone's connection and processor are the case it is for): while the password is typed, the unlock screen starts the core's worker (its script is 7 MB), the cryptography library, and the two requests that need no password (`/api/auth/kdf`, the derivation's parameters, which are public by address, and `/api/vault/keys`, the sealed keys, which need only the sign-in), so after Enter only the derivation and the opening are left. **Argon2id runs in the core's worker** (`device.derive`, falling back to the page where there is no worker), so the screen keeps moving while it does and the password reaches only a worker of the same page; the parameters are unchanged. The worker is given the keys the page fetched (not fetched again), asks for the listing once and passes it on, and fetches the model settings, the profile and the index together; each was a round trip after the one before it. Keys fetched ahead that turn out to be old (the password was changed on another device) are fetched again once before the password is called wrong. The console says where the time went (`[unlock]`). Built files whose names carry a content hash are kept by the browser for a year (`server/src/static-cache.ts`), so a reload asks about the page and nothing else; the sealed copy below takes no more than a tenth of what the browser says the site may use.
- **Keeping a copy on the device** (SECURITY.md **M-43**): every object but the index is written once and never changed, so the device keeps the sealed bytes it fetched or wrote in IndexedDB (`web/src/crypto/sealed-cache.ts`, one database, a scope per profile) and opening the vault again fetches only the index, the profile, the listing and what is new. What is kept is what the server holds, ciphertext and the key it is sealed under, never a record's text; a copy that does not open is dropped and fetched again; a listing of everything drops what the vault no longer holds; the least recently used go past about 300 MB; and it is best effort, so the app works with none (a private window, a browser that cleared it, Safari's removal of storage after a week unused). Signing out and deleting the account clear it. A file is fetched ahead of the request that reads it (`Persistence.ensure`, for a page image), asynchronously and in parallel, because the read the file layer makes when nobody asked first is a synchronous request that stops the core until the file is here.
- **Conflicts**: per column of a row, the later write (a change without `c`, made before columns were told apart, is of every column; a deletion is of the row, and an edit later than it brings the row back);  per natural key (a tag's or doctor's name) one row and an alias for the other key; per unique place (a page's number) the newer change. What is merged cannot lose a record that only one device wrote.
- **Clocks**: "later" is read from the stamp, and a stamp is made on the server's clock, not the device's. Every request to the vault carries the server's `Date`; the device keeps the offset from the quickest of its last eight round trips, and forgets them when a new one disagrees by more than the requests could (the device's clock was set or jumped). Three rules keep a wrong clock from deciding a conflict. (1) **The server's clock is read right before changes are stamped**: a save with changes waiting makes a request first (`Persistence.sendChanges`), so a clock set a few seconds ago does not stamp them. (2) **A write is never stamped later than the moment it is stamped** (`createChangeLog`), so a write that seems to come from the future, because the clock was set back since, is stamped at the present. (3) **Out of reach of the vault, nothing is stamped**: the changes stay in the log, which is not forgotten, and are stamped when the vault is back, from the time each was written on the clock then read; the save fails and is tried again like any save the vault did not take. What is left: a device whose clock steps while it is out of reach, between a write and the moment it reconnects. If the clock went forward the write is stamped too early, which only loses a conflict it might have won; if it went back it is stamped too late, by at most the time since the write, because of (2). A stamp is not rejected or lowered by the device that receives it: that needs a reference every device sees identically (the time the server stored the segment), and the device that made the stamp would have to lower its own, or it would hold a different row from the others. A device that has seen a later stamp stamps its next write later still (that is what lets a person correct what they have seen), so one bad stamp costs a conflict at most, not the device's clock.
- **Not synced**: the accounts tables (they are the server's), the search index (rebuilt), the scratch directory.
- **Shares** are the same form: the owner's device builds the allow-listed copy in a store of its own and seals its changes (`{v, owner, changes}`); the recipient's browser applies them to an empty store. Nothing about a share is a database file.
- **Shares follow the records**: 15 seconds after the records change, each live link's copy is built again and sent only if it would hold something different (`POST /api/share-links/refresh`, a keyed digest in `share_link_keys`), under the same key. A closed device cannot refresh; the copy shows what it last held.
