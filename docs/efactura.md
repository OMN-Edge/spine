# Spine's own e-Factura link

`SPINE_INVOICING=efactura` makes the operator's invoices without a service between Spine and ANAF: Spine numbers the invoice in the operator's series, writes it as the e-Factura XML, keeps it, sends it to ANAF with the operator's authorisation, asks ANAF what it decided and keeps the signed answer. The other choice is Billyou (`SPINE_INVOICING=billyou`, docs/billing.md, "Invoices when the provider is not the seller"). Both sit behind the same interface (`InvoiceIssuer`, `packages/billing/src/invoicing/issuer.ts`), so the queue, the webhook, the refund storno and the operator's tools are the same for either.

The code is a workspace package, `packages/anaf/` (`spine-anaf`), with one door (`index.ts`) that a check holds (S15). It asks the rest of Spine for the eight store methods named in its `AnafStore` and for the settings in `AnafConfig`, and for nothing else of Spine's, so it can be run as a service of its own by giving it a small HTTP face (issue, status, PDF) without rewriting any of it. What is Spine's stays outside: `packages/billing/src/invoicing/efactura.ts` gives it the National Bank's rate and the path a PDF is served at, and turns its `AnafError` into the `InvoiceError` the queue decides by.

## What each file is

| File | What it does |
|---|---|
| `ubl.ts` | The XML: UBL 2.1 in CIUS-RO 1.0.1, an Invoice or a CreditNote. Pure, in whole cents. |
| `anaf.ts` | The authorisation (sign-in URL, the exchange of the code, refreshing the tokens) and the calls: validare (ANAF's own check of a file before it is sent), upload, uploadb2c, stareMesaj, descarcare; and the Ministry's PDF converter (the operator's "ANAF's view", to compare). |
| `issuer.ts` | The numbered documents and what ANAF is told about each; the signed links to a PDF. |
| `document.ts` | The invoice as a person reads it: an A4 PDF made with pdfkit from the stored document, the one the XML is written from. |
| `seal.ts` | AES-256-GCM, under a key that is in the environment and never in the database. |
| `zip.ts` | Reads ANAF's answer (a zip of the invoice and the Ministry's signature). |
| `index.ts` | `makeEfactura`: puts them together from the settings. |

## How an invoice goes

1. A payment reaches the queue (`invoice_queue`) as for any issuer. `issue` reserves the next number of the series for the payment (`efacturaReserve`, one transaction, so no number is given twice or lost), writes the XML and keeps it with what it was made from (`efactura_documents`). It only touches the database, so asking again for the same payment returns the same invoice.
2. `sendToAnaf` uploads it. A buyer in Romania with a tax number is a business (`upload`, B2B); a person is `uploadb2c`, which ANAF requires for sales to people since 31.03.2025 (the Ministry's technical page), identified by thirteen zeros where no CNP was given, as ANAF's test platform accepts. A buyer abroad is not sent: e-Factura is for Romania (the account's invoice history has the document).
3. ANAF decides within seconds to hours. The queue asks every five minutes for up to a day (`stareMesaj`); on `ok` the signed answer is downloaded and kept (ANAF has it for 60 days only), on `nok` its errors are downloaded and shown in `/admin`. The operator's "Try again" makes the XML again from what it was made from (in case the writer was mended) and sends it as new.
4. A refund makes a credit note (381, `standard=CN`) numbered in the same series, naming the invoice.
5. The PDF is Spine's own (`document.ts`), made when it is asked for from the stored document, so it says what the XML says and needs no request to ANAF. The labels are English with the language of the buyer's country beneath (Romanian, French or German; English alone for any other country), the values are never translated, and the header carries Spine's name and mark. It holds what Codul fiscal art. 319 alin. (20) asks of a sale like this one: the number in the series and the date, the seller's name, address, tax id and register number (and every bank account saved with the seller), the buyer's name and address (and tax id for a company), the service and its amount before VAT, the VAT rate and amount, and for another currency the National Bank's rate and the VAT in lei; a credit note names the invoice it reverses. The account's invoice history opens it at a signed link that lasts ten minutes. The Ministry's converter is kept for the operator to compare (`GET /api/admin/efactura/:id/anaf-pdf`).
6. When the document is made the buyer gets a short mail (`invoice-mail.ts`: its number and a link to the account page, in the account's language, nothing attached), once for each document, where the issuer sends nothing itself.

**The seller is not a VAT payer** (the accountant's word, to be confirmed): the class is "not subject to VAT" (`O`, which ANAF's guide to the codes, v2.9, section 3.4, says is used only by taxable persons not registered for VAT), the invoice carries no VAT identifier for anyone (BR-O-02), and the seller is named by its registration number alone (BR-CO-26). A VAT payer saves a VAT id with the seller and sets a rate. **The mention:** the accountant's word for a line with no VAT is "scutit de TVA" (2026-11-19), so each such invoice carries "Scutit de TVA conform art. 310 din Codul fiscal" in its line of text (the regime for companies not registered for VAT, which Omni Edge SRL is, by the owner's word of 2026-11-19; BT-22, which ANAF's guide allows for the reason in class `O`) and on the PDF; `SPINE_INVOICING_VAT_NOTE` words it otherwise or turns it off. The class is `O`, since the company is not registered for VAT; a company that is would use `E` with a reason code (`SPINE_INVOICING_ZERO_VAT=E` and `SPINE_INVOICING_EXEMPTION_CODE`). The mention is the same for every buyer; the cases that differ are in the next section.

**What the accountant answered** (2026-11-19, summarised): a person with no CNP is written with thirteen zeros (what the XML does); the rate is the National Bank's for the day of the invoice, whatever day it was paid (`bnr.ts`: the newest published on or before the invoice's date, from the bank's file for that year, so a late invoice keeps its own day's rate); a refund is invoiced with a credit note dated the day of the refund (`reverse(…, on)`: the day the refund reached Spine, which a retry does not move); and the accountant would like one file with all the month's invoices, uploaded in the first week of the next month, which is the summary below.

## The authorisation, and what the operator does

ANAF identifies the person who signed in with the qualified certificate, not the application (`oauth-procedura-inregistrare-aplicatii.txt`): the tokens are for the certificate's serial, and the certificate must be registered in SPV with a right for the company (legal representative, designated representative or authorised person).

Once, by the operator:

1. Have the certificate registered in SPV for the company.
2. At `www.anaf.ro/InregOauth` (Servicii Online, Inregistrare utilizatori, Dezvoltatori aplicatii, Inregistrare pentru API-uri) create the developer account, then register the application: a name, the callback `https://<domain>/api/admin/efactura/callback` (it must be `https`, and the same as `SPINE_EFACTURA_REDIRECT_URI`), the service E-Factura. ANAF gives a client id and a client secret.
3. Put them in the environment (`ANAF_CLIENT_ID`, `ANAF_CLIENT_SECRET`), with `SPINE_EFACTURA_KEY` (`openssl rand -base64 32`), and `SPINE_EFACTURA_MODE=test`; save the seller on `/admin/invoices`.
4. In `/admin/invoices`, "e-Factura": **Sign in to ANAF with the certificate**. The browser goes to ANAF, asks for the certificate (the USB token plugged in, or its software running), and comes back; Spine exchanges the code within the 60 seconds ANAF allows.
5. **Test the connection** (shown once authorised) calls ANAF's own `TestOauth` service (`api.anaf.ro/TestOauth/jaxrs/hello`, in the OAuth procedure): it takes nothing for e-Factura and answers 200 if ANAF accepts the token, and says whether it saw a certificate with it. A 403 there means the token is not accepted, which for a certificate that signs in fine is usually a certificate with no SPV right for the company. What the service echoes (the token, the certificate's serial) is not kept or shown.

After that no certificate is needed until the refresh token ends (a year): the access token (90 days) is refreshed by itself when it has less than two weeks left, ANAF giving a new pair each time. `/admin` shows when each ends and whether a refresh is due; if the access token cannot be refreshed it keeps being used while it is good, and an invoice waits for the operator rather than failing when there is no authorisation at all.

`test` is ANAF's test platform (`api.anaf.ro/test/FCTEL/rest`): the same sign-in and the same certificate, files that are checked as real ones and registered nowhere. Move to `prod` only after the invoices the test platform takes are the ones the accountant approves.

## What is kept, and what protects it

- `efactura_auth`: the access and refresh tokens, sealed (`seal.ts`). Reading the database gives nothing without `SPINE_EFACTURA_KEY`; both secrets are stripped from the relay's environment.
- `efactura_documents`: each invoice and credit note, its XML, ANAF's index and state, and the signed answer. **Kept after an account is deleted**: an invoice is a fiscal record (ten years), and the buyer's name and address are in it. The privacy notice says so (`docs/legal/privacy.md`).
- `efactura_series`: the next number of each series. `efactura_pending`: the authorisation being asked for.
- The callback is reachable by ANAF's redirect, which carries no session (the cookie is `SameSite=strict`), so it trusts one thing: the one-time `state` that a signed-in administrator with a recently typed password asked for, ten minutes long, spent on first use, and not spent by a wrong guess.
- The PDF link is signed with a key made from the sealing key, for one document and ten minutes.

## What an invoice says for each buyer

Spine is sold to people, not businesses (businesses are dealt with outside the platform), and the subscription is an electronically supplied service. Omni Edge SRL is not registered for VAT: it applies the special regime for small enterprises (art. 310 of the Fiscal Code: no VAT charged or deducted while the yearly turnover stays under 395,000 lei, the ceiling since 1 September 2025 by OG 22/2025; the invoice that takes it over carries VAT and the company applies for registration on that day). What differs with the buyer is where the service is taken to be supplied (art. 278) and the mention the invoice needs (art. 319 alin. (20) lit. l: for an exemption, "trimiterea la dispozițiile aplicabile ... sau orice altă mențiune din care să rezulte că ... prestarea de servicii face obiectul unei scutiri"). Read in the text of the Code on legislatie.just.ro (the text as published in 2015, so before the amendments: the ceiling and art. 278^1 and 310^1 are from ANAF's notes on OG 22/2025 and on the special scheme for electronic services of 27.08.2021, `static.anaf.ro`), on 2026-11-19; for the accountant to confirm against the consolidated text.

| Buyer, a person | Where the service is supplied | The invoice | Counts towards the 395,000 lei |
|---|---|---|---|
| In Romania | Romania (art. 278 alin. (3)) | no VAT, "Scutit de TVA conform art. 310 din Codul fiscal" | yes |
| In another EU country, while the year's electronic services to persons in other EU countries (all of them added) stay under 10,000 EUR (46,337 lei), this year and the last (art. 278^1 alin. (5)) | the seller's country, Romania | the same | yes |
| In another EU country, past that | the buyer's country (art. 278 alin. (5) lit. h) | VAT of that country, which Romania's art. 310 does not remove: the company needs the EX scheme, OSS or a registration there (below) | no |
| Outside the EU | the buyer's country (art. 278 alin. (5) lit. h) | no VAT, "neimpozabil în România conform art. 278 alin. (5) lit. h) din Codul fiscal" | no |

"Scutit" and "neimpozabil" are not the same: an exempt supply has its place in Romania, a not-taxable one elsewhere. A company that is not registered for VAT still keeps the sales and purchases journals (art. 321) and an invoice in another currency carries the lei equivalent (art. 319 alin. (23), the National Bank's rate of the day).

**Past 10,000 EUR from persons in other EU countries**, the sales are taxed in each buyer's country. Three ways to deal with it, for the accountant to choose: the special scheme for small enterprises in other member states (art. 310^1: a notification to ANAF, which gives the company's tax code with the suffix "EX" within 35 working days, while turnover in the whole EU is under 100,000 EUR this year and last and the sales in a country stay under that country's own small-enterprise ceiling; each quarter the sales are reported by country; passing 100,000 EUR is told to ANAF within 15 working days and the code is cancelled); the One Stop Shop (OSS), which is declared in Romania each quarter and which the sources say needs a normal VAT registration (art. 316); or a registration in each country. The sales are totalled against the 10,000 on `/admin`.

What the code does today: the first row for every buyer, so a person outside the EU is given the art. 310 mention where the table has "neimpozabil". A buyer outside Romania is not sent to e-Factura. The billing details ask for an optional company tax id, which a buyer that is a person leaves empty.

## The month's summary for the accountant

`/admin/invoices` has "Monthly summary for the accountant" (administrators only: it names every buyer of the month): a month, opening on the one that has just ended, and two downloads, a CSV a Romanian spreadsheet opens and a PDF to print and sign (`GET /api/admin/invoices/export?month=YYYY-MM&format=csv|pdf`, `server/src/billing/invoicing/journal.ts`, drawn by `packages/anaf/src/journal.ts`). It lists every invoice and credit note dated in the month, from Spine's own e-Factura documents and from the copies kept of a service's invoices (an invoice a service made before a seller was saved has no copy and is not listed), in date order: the kind, number and date, the buyer's name, country and tax id (thirteen zeros for a person in Romania with none), the currency, the amount without VAT, the VAT and the total (a credit note's negative), the National Bank's rate of the day and the total in lei (empty where the bank could not be asked), the invoice a credit note reverses, the payment's reference and what ANAF said. The PDF adds the totals for each currency and a line for the signature. Nothing is kept of it: it is drawn from the documents each time, and the export is logged with the account, the month and the number of lines, never a buyer.

**Why it is lawful.** OMFP 2634/2015 (Monitorul Oficial 910 of 9.12.2015), annex 1, the general norms: point 20 says entries in the books are made from supporting documents "fie document cu document, fie pe baza unui centralizator în care sunt înscrise mai multe documente justificative al căror conținut se referă la operațiuni de aceeași natură și din aceeași perioadă"; point 45 lets operations of the same kind be recapitulated in an auxiliary journal that is the basis of the entry in the Registrul-jurnal; point 10 says what an accounting document that sums up others must show: the entity's name, the date it was drawn up, the kind, number and date of each supporting document, the amounts, the accounts and the signature of the person who drew it up. So a monthly list of the invoices is a centralizer in the sense of the order, and the invoices stay the supporting documents (an invoice is one under point 25, and its drawing up, use and archiving are the Fiscal Code's, point 26). The summary has all of point 10 but the accounts (conturile sintetice și analitice), which are the accountant's to put against each line. Read from the order's text at `static.anaf.ro/static/10/Anaf/legislatie/OMFP_2634_2015.pdf` on 2026-11-19; whether the accountant wants it in this form, and whether they want the XML or the PDF of each invoice with it, is for them to say.

## What is known, and what is not

Read from ANAF's own papers (`docs/reference/efactura/`, fetched 2026-11-16): the OAuth flow and lifetimes, the four calls and their parameters, the limits (1000 a minute; a message may be asked about 100 times and downloaded 10 times a day), the status words, the Schematron 1.0.9 and the two examples. The XML is checked in the tests against the OASIS UBL 2.1 schemas (`xmllint`, where it is installed); **the Schematron itself is not run here** (it needs XSLT 2 and Java): ANAF's test platform is the check, and it is the first thing to do with a real authorisation.

Not confirmed by running it:

- That ANAF accepts these files: the first upload to the test platform is the proof. Its error messages are kept and shown, and an upload can be tried again after the writer is mended.
- Whether the authorisation URL takes a `state` (the reference flow leaves it empty). Spine sends one and refuses a callback without it; if ANAF's sign-in drops it, that check needs another bearer.
- ANAF's check before the upload (`validare/FACT1` or `FCN`): its API presentation documents the production address only, so it is asked there in either mode, with the same token. A file is held back only on ANAF's clear word (`stare` `nok`, with its messages, kept as the document's message); an answer that cannot be had or read lets the upload go on, since the upload says the same. The answer's shape (`stare`, `Messages[].message`) is read from another library's code and has not been seen here.
- The upload's content type: ANAF's own swagger says any, and its converter's says `text/plain`, which is what is sent.
- The refresh round trip with real tokens (ANAF documents it; nothing here has run it).
- Where a person's identifier goes in the XML (`PartyIdentification`, thirteen zeros): the accountant's answer is yes to the zeros; ANAF's test of where they go in the file is still to come. The wording of the mention for each kind of buyer (see above): for the accountant to confirm.
- A partial refund still needs a credit note by hand (a storno is the whole invoice), and VAT is one rate for everyone, as with Billyou.
- One company: the seller saved on `/admin/invoices` is on the invoices, the footer and the terms, so a buyer reads one name everywhere. With none saved an invoice is numbered and waits (retried by the hourly job, and reported with the other waiting invoices), and is made once one is.
- The invoice's total can differ by a cent from what the card was charged: the XML's rules make the VAT the net amount times the rate, rounded, and a price that includes VAT does not always divide that way (49.00 at 21% gives 40.50 and 8.51). The document says what the XML says.

Left out of the repository for size, and kept with the session's notes: ANAF's offline validators (`roefacturavalidator_12122024.zip`, `verifstandalone.zip`) and the XML-to-PDF applications (`GenerareFactura.zip`), all from `https://mfinante.gov.ro/ro/web/efactura/informatii-tehnice`.
