# Security

Spine holds complete medical histories and exposes part of them to the public internet through share links. It is self-hosted, multi-user, and runs on hardware as small as a Raspberry Pi.

This document states the posture it is **supposed** to hold, records which controls actually exist, and lists the gaps between the two.

It is written to be enforced: every principle is phrased so a change can be judged against it, and every gap names the principle it violates. See [ARCHITECTURE.md](ARCHITECTURE.md) for the component and trust-boundary model.

> **Status.** Built and tested: the records are made and kept on the owner's device and reach the server only as sealed objects it cannot open (M-34 to M-38); accounts with argon2id-derived sign-in, open signup with email verification, recovery links, optional TOTP and passkeys; sealed share links; a relay that runs a device's model calls and stores nothing (M-35); hybrid parsing with image egress behind two switches. **Nothing here has been audited.** Every defect found so far is fixed or accepted ([Known gaps](#known-gaps)). Nothing here claims compliance with any regulation. The 2026-10-18
> [review](#review-attacks-on-sign-in-and-access-and-on-agent-built-software) found six things (a forgeable client address, dependency advisories, a 30-day stolen-cookie window, a length-only password check, no model spend ceiling, no independent check on agent-written code) and fixed the first five; the sixth is open (**S-36**).

> **Where the code runs.** Since stage 5 the server runs only accounts, the vault, sealed shares and the relay's pass; everything about a record (reading, storing, searching, scoping, sharing) runs on the owner's device and, as the same code, in the Node tests. Entries below that name routes, the store, the parser or ingestion describe that code: the controls hold there, and the server has none of it (**M-37**). Entries written before stage 5 still say "the server" where they mean the core; ARCHITECTURE.md says how to read them.

## Reporting a vulnerability

Email **alexandru@cocinda.net** with what you found, how to reproduce it, and which version or commit you ran. The same address is published at `/.well-known/security.txt` on a deployed instance ([RFC 9116](https://www.rfc-editor.org/rfc/rfc9116)). Please do not open a public issue for a vulnerability, and do not use a real person's records to demonstrate one: Spine holds medical data, so test against your own instance with invented records.

What to expect:

- An acknowledgement within 5 working days, and a first assessment (confirmed, not reproducible, or out of scope) within 15.
- A fix and a published advisory for anything confirmed, with credit if you want it. The default disclosure window is 90 days from the report, shorter if the fix ships sooner, longer only by agreement.
- No legal action against good-faith research that stays inside your own instance and accounts, does not read or change other people's data, and does not degrade a service for others.

In scope: this repository, and the hosted service run by the author. Out of scope: an instance run by someone else (report to its operator, who is the data controller, see below), denial of service by volume, and findings that need a compromised host or an operator who has chosen an unsafe setting the software warns about. Known and accepted gaps are listed under [Known gaps](#known-gaps); a new angle on one is welcome.

How the author handles a report, which is also the record the EU Cyber Resilience Act asks a manufacturer to keep:

1. Log it privately with date received, reporter, affected component and severity.
2. Reproduce it against a running instance, not by reading code (the method of the reviews below).
3. Fix it with a test that fails without the fix. Add or move the entry in [Known gaps](#known-gaps), and add the control to [Controls in place](#controls-in-place).
4. Publish an advisory on the repository with the affected versions, the fix, and what an operator must do (rotate a secret, revoke links). If users' data may have been exposed, follow the breach steps in [Operational response](#operational-response): the controller notifies the supervisory authority within 72 hours (GDPR Art. 33).
5. Check the dependency audit (`scripts/check.sh`) so a fixed advisory does not return.

For the hosted service the operator cannot read patient data: the server holds sealed objects and keys it cannot open ([docs/key-hierarchy.md](docs/key-hierarchy.md), **M-34** to **M-38**). It sees the account email, the size and time of the sealed objects, share metadata, and, in the relay, the plaintext of a model call while it is run (**M-35**).

## Distribution and who owns the risk

The primary deployment is the author's family. Others may self-deploy, or pay the author to set up an instance. In every case **the operator of an instance is the data controller for its contents and owns the risk.** The author is not a processor for other people's medical data.

Operators will not be security experts, so:

- Insecure configurations must be **unreachable by default**, not merely documented against. A default that works but is unsafe is a defect (**P3**).
- Anything that sends data off-host must be an explicit, reversible choice (**P8**).
- The software should refuse to start rather than run in a state the operator would not have chosen knowingly.

## What we are protecting

| Asset | Why it matters |
|---|---|
| Document text, summaries, extracted fields | Medical history. On the owner's device while it is open; on the server only inside sealed objects. |
| Original scans | Same, plus signatures, ID numbers, letterheads. Sealed files in the vault (`data/vault/`). |
| Page images | The full document rather than an extract — the most sensitive egress. |
| `data/spine.db` and `data/vault/` | The database holds every account's email and credential hash, the vault's wrapped keys and the shares' metadata, and no record. The vault holds the sealed objects. |
| User credentials and the master password | Account takeover and, with the vault's wrapped keys, the records. The server sees only a value derived from the password, never the password, except for an account the operator made with the CLI and that has no vault yet, which signs in once with the password it was given (**M-34**). |
| Share keys (the part of a link after the `#`) | Read access to the copy a link shares, with no account and no second factor. The server never has one in a form it can use (in approval mode it holds the key only wrapped to an approved browser's key). |

### Adversaries we design against

1. **Untargeted internet traffic** — scanners, credential stuffers, crawlers. Constant and automated. Reaches login, registration, and share URLs.
2. **Another user of the same instance.** New with multi-user and the boundary most easily broken by a careless change. A family member is not an attacker, but the control must hold regardless of intent — a query missing an owner filter leaks silently and nobody notices.
3. **A share-link recipient exceeding their scope** — a doctor, or whoever the link was forwarded to, reaching data outside what was shared.
4. **A leaked share link.** Forwarded email, shared screen, clinic browser history. Assume links leak eventually.
5. **An attacker who obtains `spine.db` or the vault** — stolen backup, misconfigured static mount, lost SD card. They get credential hashes and sealed objects, not records; the wrapped keys open only with a master password, a recovery key or a passkey that can open the vault.

### Explicitly out of scope

- **An operator with shell access to their own instance.** They can read the database and the sealed objects, and they can serve a different web app to users (see the limits in docs/key-hierarchy.md); they cannot read records from the server's disk. This is inherent to self-hosting and is stated plainly rather than designed around. It is also why there is no in-app admin role: no *application* path reads another user's records.
- An attacker with physical possession of the host, or root on it. Disk encryption is the host's job.
- Targeted attack on the chosen inference provider or on Let's Encrypt.

## Principles

A change that breaks one of these is a defect, whether or not a test catches it.

**P1 — Deny by default.** A route is private unless deliberately and visibly public. "Public" means living in a route file with no `requireAuth` preHandler, so **adding a route to the wrong file silently publishes it**. `isolation.test.ts` fails on any route of its test app that answers without a session and is not on its allow-list; that app is not the real server (it registers more, and not the trust-anchors or share-shell routes, **M-37**), and every public route must be justified in this document.

**P2 — Scoping fails closed.** If a share link's scope cannot be fully resolved, return nothing. A missing, malformed or unrecognised scope is an error, never "return everything".

**P3 — No fallback secrets, no unsafe defaults.** The service must refuse to start rather than run with an absent, default or weak secret — one committed to the repo as a fallback is a published secret. `SESSION_SECRET` is checked at startup for being absent, under 32 characters or one of the two placeholders this repository has published (a longer guessable value passes); the relay refuses to start on a `SPINE_RELAY_SECRET` under 32 characters, while the app server given such a secret treats the relay as not configured (`relaySettings`), so devices cannot call a model, and still starts. Extended for self-hosting: any default an unaware operator would not have chosen is treated the same way. This is a rule for choosing defaults, not something one check enforces: the endpoint of a Vertex model, its region and project have no default, the server binds loopback, and registration defaults to `operator`; the Anthropic endpoint does default to `api.anthropic.com`.

**P4 — Medical content is served only by authenticated, auditable handlers, and never from a static mount.** `DATA_DIR` holds `spine.db` and the vault, so a mount rooted there is one flag from publishing sealed objects (which would still not be records, but is not a thing to rely on). The only static mount is the built web app (`web/dist`, `server/src/index.ts`); the sealed bytes the server holds are served by the vault routes (a session) and the shared routes (the random id of a share, which is its capability).

**P5 — Every unauthenticated endpoint that can be guessed at or that costs something is rate limited.** Login and its second step, the passkey sign-in, a device's request to be let in and its collection of what the owner approved, registration, verification, forgot and reset, the key-derivation call, a visitor's request to open a share and every public read of a share, the pass for a share's model calls. Not limited: the cheap public reads that answer the same for everyone or only about the caller's own session (`GET /api/auth/options`, `/api/auth/me`, `/api/legal/:doc`, `/api/trust-anchors`, `POST /api/auth/logout`), which nginx does not limit either (its limit is on `/share/`).

**P6 — Secrets that are stored are hashed or sealed.** Verification, reset and recovery tokens are hashed at rest; a share has no token (its key is in the address after the `#` and the server never has it); the relay's pass is signed and short lived. Possession of the database must not confer the ability to use any of them.

**P7 — A non-owner's access is recorded where the server can see it.** The server cannot see what a recipient reads (the copy is opened in the recipient's browser), so it records what it does see: that a share was opened, when, from which country (**M-36**), and each request for approval. The relay counts calls per account and per share. What a recipient did inside a copy is not logged and cannot be.

**P8 — Egress is minimal, enumerated, explicit and disableable.** The only third parties are the configured inference provider and, for account links, the mail provider. Four rules:

- Every egress path is listed in [ARCHITECTURE.md](ARCHITECTURE.md). A new one is a change to that document first.
- **Page images leaving the host requires an explicit opt-in**, and the deployment must be able to disable that path entirely and accept weaker OCR.
- **Residency is a property of the endpoint, not the model.** An adapter that can fall back to a global endpoint, or authenticate in a way known to ignore the configured location, is a defect.
- **Email carries no medical content — ever.** The mail path exists only for account messages (verifying an address, a reset link, a notice of a sign-in from a new browser or of a changed security setting, a request waiting for approval): a recipient address, a single-use link or a link to a page that asks to sign in, and when the event happened (a sign-in, a changed setting, a request). No document text, no summary, no extracted field, no attachment. This is what keeps a mail provider from becoming a processor of health data, and the mailer interface has no attachment parameter precisely so the capability cannot be reached. The subject and body say nothing clinical either. The sender name is the operator's choice: it can be the company or the product, which tells the provider and anyone seeing the inbox that the recipient uses that service, and no more. An operator who wants less visible than that picks a more neutral name.

**P9 — Least privilege at the OS layer.** Services run unprivileged with `ProtectSystem=strict`, `NoNewPrivileges`, write access narrowed to `data/` (the backup unit also writes `backups/`). The server parses no file at all now (the device does, in the browser's sandbox), and there is no parser service: the old sidecar's unauthenticated, path-reading listener ([docs/sidecar.md](docs/sidecar.md)) no longer exists.

**P10 — Tests exercise the real path.** A control is untested unless the test drives it the way production does. A fixture that builds state directly, bypassing the handler that encodes it, proves nothing.

**P11 — Recoverable by design.** `data/spine.db` and `data/vault/` must be restorable (the backup mirrors both; shares are not backed up on purpose). A person's records are recoverable only with their master password or recovery kit: the operator cannot recover them (**M-34**).

**P12 — Isolation is structural, not remembered.** On the device, every read and write is scoped by owner **in the store layer**; on the server, the store has no repository of records at all (**M-37**). A repository method that does not take an acting user id, or that can return a row the acting user does not own, is a defect. Route handlers must not be able to write queries, so isolation cannot be forgotten in one. The exceptions are listed in **M-1**.

**P13 — Credentials are stored with a memory-hard KDF and are never recoverable.** argon2id, per-user salt, fixed parameters (19 MiB, 2 passes, 1 lane: **M-3**). No password in a log or error, and no reset path that reveals the old value. Changing a password invalidates that user's existing sessions. The one reversible secret is a TOTP seed, which has to be read back to check a code; it is encrypted at rest and is a recorded exception (**S-21**), and recovery codes and tokens are hashed. A second factor, where enabled, applies to every way of obtaining a session with a password (**M-12**); a passkey is both factors at once (**M-33**).

## Known gaps

Defects in the code as it stands. Severity: **High** = unauthorised access to medical data or account takeover. **Medium** = weakens a control or widens blast radius given a precondition. **Low** = hygiene and defence in depth.

One item is open (S-36, from the [2026-10-18 review](#review-attacks-on-sign-in-and-access-and-on-agent-built-software), which also found S-31 to S-35 and fixed them the same day); everything else is fixed or explicitly accepted, and the next review should expect to add to the list. The original findings were confirmed against a running instance, not inferred. [Closed](#closed) keeps the ids resolvable, since they are cited from [ARCHITECTURE.md](ARCHITECTURE.md).

### Open

**S-36 — Code written with an agent is checked by the tests the same agent wrote** (**Low to Medium**, process, **P10**). The studies behind the [2026-10-18 review](#review-attacks-on-sign-in-and-access-and-on-agent-built-software) find that AI-written code carries the usual classes (missing authorisation, injection, weak randomness, hard-coded secrets, unsafe defaults) at a rate that rises, not falls, with more refinement rounds, and that a model reviewing its own output shares its blind spots. This codebase's answer is structural (the store takes the user id, one visibility fragment, a route allow-list test, response-shape scans), and it has held. **Partly closed**: `scripts/check.sh` runs the typecheck, the tests, `npm audit` (high and critical fail), `gitleaks` on the tree and its history, and `semgrep` (TypeScript, Node.js and security-audit rules) on `core/src`, `server/src` and `web/src`; `.github/workflows/ci.yml` and `.gitlab-ci.yml` run the same and the two real-browser checks (`check:browser`, `check:app`), and `install.sh -b` runs the audit. **First run, locally on 2026-10-18**: gitleaks found one hit, a fixed `SESSION_SECRET` in the integration-test setup (a throwaway for an in-memory database, never a deployment's); it is now random per run and the historical hit is listed in `.gitleaksignore` with the reason. Semgrep found eight: one real (`createDecipheriv('aes-256-gcm')` without an explicit tag length in `totp.ts`; the tag was already sliced to 16 bytes, but the length is now stated, so a shorter forged tag is refused), six false positives of an Express rule (`direct-response-write`) on `reply.send(object)`, which Fastify serialises as JSON, with the only HTML sent being a constant page and the built app shell (excluded by name in `check.sh`, with that reasoning beside it; re-check if a route sets `text/html`), and one in a test that asserts a `<script>` string is returned as text. Tests are not scanned. **Still open**: the GitLab pipeline has not run (no remote yet); there is no second human reader on a change to auth, scoping or a prompt; and the integration tests (`npm run test:integration`) have been run against the real model once. Needed: push, confirm the pipeline passes, and a human read of every diff that touches the checklist's first dozen items.

### Accepted

**S-9 — The audit log trusts `X-Real-IP`.** No longer applies. The server's only record of a reader is where in the world a share was opened (`routes/shared.ts`), taken from `req.ip`, which Fastify believes only from the trusted proxy (**S-31**); no route reads `X-Real-IP`.

**S-16 — Sessions lived in memory** (fixed). Restarting the server signed everyone out, which every deploy did. The cookie session's state is now in the accounts database (`cookie_sessions`, `server/src/session-store.ts`), keyed by the sha256 of the cookie's random id, so a copy of the database opens no session; it is written only when a session changes, so a visitor who has not signed in leaves no row; rows end with the cookie and are swept with the sign-in rows; deleting the account deletes them. A process that reaches the same database shares them. `sessions.test.ts` signs in, starts a second server over the same database and is still signed in.

**S-17 — The instance-wide login cap can lock everyone out.** 50 login attempts (every `POST /api/auth/login` counts, whether it succeeds or not) in ten minutes from anywhere stops all logins for the rest of the window, including the owner's. That is the trade for throttling a distributed guess; the per-source limit runs first so one noisy host does not spend it alone. Existing sessions are unaffected.

**S-19 — nginx's access log held raw share tokens.** Fixed by the sealed shares (**M-36**): the log now holds a share's random id, which opens nothing without the key in the address after the `#`, and a fragment is never sent to a server. A link with scans is still a decision to make per link, because a scan shows what extraction drops on purpose, the patient's ID number and phone, so "include scans" is off by default.

**S-20 — Two-factor is optional.** Each user turns TOTP on for their own account (M-12); an instance cannot require it, so on an `open` instance a user who never enables it is protected by their password alone. A `SPINE_REQUIRE_2FA` switch is the obvious next step; it is not built.

**S-21 — The TOTP key derives from `SESSION_SECRET`.** A TOTP seed has to be read back to check a code, so unlike a password it cannot be hashed; it is encrypted at rest under a key derived from `SESSION_SECRET`. Someone holding both `.env` and the database could generate valid codes (they could also forge sessions, so this adds nothing new). **Changing `SESSION_SECRET` makes every enrolled seed unreadable**, so authenticator codes stop working. Recovery codes still do (they are hashed, not encrypted), so each user can sign in, turn it off and enrol again; failing that, the operator runs `disable-2fa`.

**S-22 — Whoever has the password can enrol their own authenticator.** Enrolment needs the password and a session, nothing else. An attacker who has both can switch two-factor on with their own app and lock the owner out: a reset link and `set-password` do not remove it. That is denial rather than disclosure (holding the password already exposed the archive), and the operator's `disable-2fa` undoes it. Built since: the account is emailed when two-factor is turned on or off (`routes/totp.ts`, `notify.ts`), so a lock-out is noticed when a mailer is set up.

**M-30 — Editing the doctors of a document keeps how each is tied to it.** **P12.** `PATCH /api/documents/:id` with `doctors` replaces the document's list, as before, but a doctor who stays keeps where they were read (text, a stamp, a signature) and the code the document printed for them, which the clash question of **M-26** depends on. The page sends the directory entry's id with a row the owner chose from the directory (a searchable list, `Combobox`); the route accepts it only as a hint (it must be the user's own entry, found through the store, and the name's key must still match), then uses exactly that entry, so a spelling-neutral edit stays the same person even when another doctor shares the name. A name that is not an entry makes a new one with no code (the code belongs to the person, not to the name), and `new: true` makes another person even though the name is held. Two people can share a name: `doctors.key` is an identity (`ion popescu`, `ion popescu#2`), not the name, so the unique index and the schema are unchanged; reading a name picks the namesake with no code, then the oldest, and a professional code that differs is still only asked about (**M-26**), except in a restore, whose codes are exact. Renaming on the Doctors page no longer refuses a name another entry has. The owner's pages now show the entry's code; a share recipient's list never carries it. `document-edit.test.ts`.

**S-23 — A doctor read from a document is a label, not a proof.** Text, a stamp and a digital signature all name a doctor, and anyone who can get a file into the archive (a forwarded PDF, a clinic's mail) can make one say anything. A signature is checked for being intact. **Chain check**: with `SPINE_TRUST_ANCHORS_DIR` naming certificates (`.pem`, `.crt`, `.cer`, `.der`; served as `GET /api/trust-anchors`), the device also follows the certificates in the file from the signer to one of them, each link signed by the next, every certificate in date at the signing time and every issuer a CA (`signatures-cms.ts`, `signatures-cms.test.ts` with invented chains), and files the doctor as `verified_signature`; the document page says "Digital signature verified". Revocation is **never looked up** (the lookup would tell a third party whose certificate was used, and the page's policy allows no request out), but the revocation lists (CRLs) **inside the signature** are read: each must be signed by the issuer of the certificate it is about, and a certificate such a list shows as revoked on or before the signing makes the signer not verified; a list issued after the signing that does not name it, or names it only later, shows it held. With no usable list the state is `unknown` and the signer stays verified as before, which is the gap: OCSP responses and PAdES document security stores are not read, and the page does not yet show the difference. The signing time is the one the file states, so a signer can claim a time. With no anchors, or a chain that does not reach one, a self-signed certificate naming a real doctor is still filed as that doctor, as a label. Nothing is decided from it (no scope, no access, no share); it puts a name in the owner's own directory, where Review can remove it and Duplicates can show it. A stamp or signature is not evidence of who wrote a document and the interface never says so.

**S-24 — Uploaded files are parsed by readers that could have a memory-safety flaw.** Closed on the server by stage 5: it parses no file, and poppler and sharp run only in the Node tests. The same class of risk now sits in the browser: PDF.js, Tesseract.js, the HEIC and Word converters and fflate read what a stranger could craft, in the owner's own Web Worker, where a flaw reaches that person's open session and vault but not the server or another account (**M-31**). Keep those packages up to date (the dependency audit stops a build on a high advisory).

**M-26 — What an upload may have duplicated is put to the owner as questions; nothing is merged because a name looks alike.** **P12.** Reading an upload merges only what is exact: a doctor by the same name key (case, accents, titles and word order ignored) or the same professional code, a tag cleaned to the same form, a test by a remembered alias. Everything else is left as it was made and **asked about** (`matching/`, `GET /api/source-files/:id/matches`, drawn in the upload's report): for a doctor, a test, a tag and a clinic or laboratory that this upload introduced, compared with everything else held, the page asks "is this the same?" with the reason (the same surname and an initial; a longer form; differing only in punctuation or a company suffix; spelled almost the same; one name inside the other; one begins with the other) and what helps decide (specialty, clinic, code; the units of a test, with a warning when they differ, since merging them would mix the values). **Yes** is the merge itself, made through the ordinary merge route into the entry that stays (the fuller doctor name; when they are as full, the one with more documents), so every check that route makes applies; **No** is remembered (`match_decisions`, per user, deleted with the account) and the pair is not asked again. Two doctors with different professional codes are never suggested together, two tests that sit in one document are never suggested, and a name told apart by a number or a lone letter ("Spital A", "Vitamin B6") is not suggested. **A code that differs**: the directory keeps one code per doctor and a name match leaves it as it is, so a document that prints another code used to be dropped silently; the code a document printed is now kept on the link (`document_doctors.printed_code`) and the difference is asked about (use the printed code, keep the directory's, or open the doctor; two people of one name are two entries, `doctors.key` being an identity and not the name, **M-30**, and the owner tells them apart on the doctors page). The questions are worked out when the report is shown, from the current state, so an answered or merged pair is not there. **What leaves the host**: nothing; this is all local string and directory comparison, with no model. It only suggests, from names: it cannot know that "Hb" is "hemoglobin", which is what the assistant's merge cards are for (**M-21**).

**M-25 — A file attached in the chat is the ordinary upload, tied to the conversation it came in, and reported there.** **P8, P12, M-7, M-9.** `POST /api/chat/attachments` (multipart; a `conversation_id` field sent before the files names the conversation, otherwise one is started) is not a second way to upload: it calls the same `acceptParts` as the Upload page (`ingestion/accept-parts.ts`), so the same checks apply to every file: the type is detected from the bytes and not the name, a photo is refused unless the operator allowed AI reading (**M-7**), the size caps, de-duplication by checksum, the zip limits (**M-14**), the original kept as a device file and saved to the vault sealed (**M-9**), and the same pipeline with the same egress (**P8**). What it adds is `source_files.chat_conversation_id`, so what happens to the file is reported in that conversation. A conversation that is not the owner's (or is full) is refused **before the first file is saved** (404/409, nothing written); the route is owner only. The conversation holds the owner's message (the file names, kind `attachment`, drawn by the page) and, when reading ends, the app's report (kind `upload`, **M-23**), added to it and unread until seen, instead of starting a new conversation. The report now says what reading added: the doctors the upload introduced (a doctor is new if its directory entry was made while the upload was being read) and how many it found already there; pairs that may be one person, where one is new (the app never merges them itself: the owner confirms a merge card, **M-21**); the tests no other document has; and whether the pages look cut from mixed pages. That last is a cheap local look at the pages' own text with no model and nothing sent (**M-24** is the model-validated analysis, started by the owner pressing "Check the pages with AI", whose disclosure is beside the button). The names in the report are medical text and are stored with the conversation, so they are handled as conversations are (**M-18**): scoped by `user_id`, deleted with the account, not exported.

**M-24 — Sorting a mixed upload sends the pages' text to the model, once, because the owner confirmed it; the model proposes, the owner applies.** **P8, P12.** For a bulk export whose pages are side by side from many documents, `POST /api/source-files/:id/regroup/analyze` (the chat proposes it as a card; Confirm sends it) compares the pages on the device and then asks the configured model, per candidate group, whether those pages form one coherent document and, if not, how they divide (`judgeGrouping`, the `grouping` task, schema-validated; a label it makes up names no page we sent, and a page it leaves out is put back). **What leaves the host**: the text read from the pages of that one upload, a page or so each, to the chat provider with its residency refusals: the same text that already went to read the documents (**P8**, ARCHITECTURE.md **Egress: what leaves the host**), and, where `SPINE_EMBEDDINGS=vertex`, the pages' text to the embedding provider with the refusals of **M-15**. Never an image. It is bounded: at most 60 model calls for an upload, groups of at most 8 pages, 4 at a time, one at a time per upload, and nothing runs without the owner's confirmation. The page text is data, not instructions (the prompt says so), and a page that tries to steer the verdict can at most make a group look coherent, which is shown to the owner with the pages themselves. **The signals are ours, not the model's**: reference numbers, dates, "page 2 of 4" markers and word weights make candidates; the model validates; a group without a verdict is `unchecked`, and `uncertain` or `unchecked` groups are off by default on the card. **Nothing is changed by the analysis**: the plan (page ids, page numbers, a title, a verdict and a one-sentence reason; no page text) is stored per upload (`regroup_plans`, replaced when the analysis is run again and deleted with the upload and when a regrouping is applied, since its pages would then be in other documents; a re-reading keeps it, since the page ids stay) and the app says it is ready in the conversation it was asked in, or in Activity (**M-23**). **Applying** is `POST /api/source-files/:id/regroup`, an owner route that takes groups of page ids and validates them against the upload (a page of another upload or user is a 400/404, a page in two groups a 400; the upload must not be processing or being analysed), then in one transaction makes the new documents, moves what was read from a page with it, folds a document no group kept into where most of its pages went, numbers the pages again and marks the changed documents unreviewed. A group keeps the identity (and so the owner's edits) of a document only if each is at least half of the other. Pages not named stay where they were. The card then reads the changed documents again from their text (`/extract`, as after any regrouping). The thresholds are first guesses and the analysis logs counts (never text) to tune them from.

**M-23 — The app starts a conversation when an upload has been read; the assistant can then review it with the owner, and the documents of an unconfirmed upload reach it by that route.** **P8, P12.** When the pipeline finishes an upload (or fails) it adds a message to the owner's Activity conversation (`chat/notices.ts`, `origin = 'activity'`, one for all the app's reports, unread until opened and again with each report; a file attached in a conversation is reported there instead, **M-25**) whose content is **not written by a model**: it is a fact about the upload stored as data the page draws in the owner's language, plus the same facts in English for the model to read when the owner replies. Nothing leaves the host to make it, and it is skipped when `SPINE_CHAT=off`. The failure message does not copy the reason the file failed (it can quote the file). Conversations are medical text and are handled as such: scoped by `user_id`, a 404 for anyone else's, deleted with the account, not exported (**M-18**); `GET /api/chat/unread` and `POST /api/chat/conversations/:id/read` are owner routes. When the owner replies in such a conversation, the upload named by the app's latest notice in it is put on screen for the assistant (the browser does not send it), so "is this right?" has an answer. **The exception this widens**: **M-17** keeps the documents of an upload whose grouping is not confirmed away from the assistant, except the one document the owner has open and an upload's own screen. The tools `list_uploads` and `get_upload` add one more path: the documents of an upload the owner asks about, by label, for exactly the owner who is checking them. They are still the owner's own, through the store, by labels the request gave; they cannot be shared (a share needs documents *shown*, `resolve(…, shown)`) and the searches still do not find them. **What it can propose** on top of **M-21**: confirming the grouping (the ordinary route; documents then appear in the timeline, search, shares and are embedded, **M-17**) and reading pages again (`POST /api/source-files/:id/ai-reading`): the card says that a page image goes to the model provider, the proposal is refused when the operator has not allowed AI reading (**M-7**), and the route checks the same switch again. Links the background search finds are not announced: they appear where the document is, and nothing out of the blue is worth a notification there.

**M-22 — A link can be inspected and changed after it was made; the same checks apply, and the history is the owner's.** **P2, P6, P7, P12.** `GET /api/share-links/:id` and `PATCH /api/share-links/:id` are owner routes (a link that is not theirs is a 404). The detail shows the settings, the documents the link resolves to *now* (through `listForShare`, so a document since set aside is not listed), the countries it was opened from (worked out on the server in a file of address ranges, `geo.ts`, so the address is sent nowhere and not kept; the file is a public-domain download from GitHub, `geoip-update.ts`, fetched over https with no checksum to pin because the release is rebuilt daily, and refused unless it is of a plausible size and opens as a country database, so a bad one at worst gives wrong or no countries) and counts, and the latest opens with the shared document each opened, if any (collected from the server by the owner's device into the access log, **P7**; the id comes from the recipient's browser and proves nothing: the server accepts only an id's shape), the requests that asked to open it and a history of what happened to it (`share_link_events`: created, changed with the field and its old and new value, revoked, approved, denied). There is no token or digest to return (**P6**), and the history holds small values only: a scope change records document *counts*, never ids, titles or text, and a request's note is not in it. **A change goes through the creation checks**: `checkScope` is the one place a scope is validated for both (a scope that cannot be fully resolved is a 400, **P2**; a document that is not the owner's is the same 400 as one that does not exist, **M-5**), the options must be booleans, the language one of four, the expiry 1-30 days from now (so it extends or shortens), and an unknown key is a 400. A **revoked link cannot be changed** (409): revocation stays final. **Switching approval on drops the requests the link held**, so a browser approved under an earlier setting asks again (**M-19**); switching it off lets anyone read, as at creation. A change that alters what the copy holds, who may open it or when it ends is sent to the server by the owner's device at once (a new sealed copy, under a new key if approval changed); a recipient who already has the copy open keeps what they loaded until they reload. The change is made on the owner's device, so it needs the device open. A country is a guess from the visitor's connection (**S-9**) and is shown with a notice that it proves nothing. See `docs/architecture/data.md` **Share links**.

**M-21 — The chat can prepare changes but cannot make them; the person's Confirm is the only thing that does.** **P8, P12.** The owner's agent has `propose_*` tools (`chat/actions.ts`) for a share link, a note, a correction, tags, reviewed, a care link, revoking a link, merging duplicate doctors, tests, tags or providers, correcting a result's value, unit, range or date, changing an existing share link (its name, how long it works and which documents; never what it exposes: scans, approval and recipient questions are changed only by the owner, on the link's page), confirming an upload's grouping, reading pages again, turning a page or setting it aside, sorting a mixed upload (**M-23**, **M-24**), and moving one page of an upload into another of its documents, or out into one of its own (`propose_move_page`: the page and the document are named by number and label from `get_upload`, the card shows from where to where, and Confirm sends the ordinary `POST /api/pages/:id/move`, which checks ownership and that the file is not being read; `chat-notices.test.ts`), confirming or dismissing the connections the app suggested (`list_suggested_links` shows the unanswered ones across the archive, between documents that are shown, labelled K1…; `propose_decide_links` names them by those labels, checks each is still unanswered, and Confirm sends the ordinary `POST /api/document-links/state`; the app's one-sentence reason is copied from the documents, so it is shown as text and the prompt says it is not an instruction, **S-27**), and combining two documents of an upload into one (`propose_merge_documents`: every shown page of the second is moved to the end of the first by the same move route, one request each in order, then the first is read again through the ordinary extract route; the pages need not be adjacent, both documents must be the upload's, a document cannot be combined with itself, at most 60 pages; the card names both documents and the pages). **A tool never executes**: it validates its arguments against the limits of the route Confirm will call, names things only by labels the request handed out (so the model cannot name another user's record or invent an id; a label it was not given is refused), and returns a proposal. The reply carries it, the page shows it, and only the owner's Confirm sends requests from their authenticated browser to the ordinary routes, which check ownership, limits and visibility again. Two tests run the proposing tools against a store and assert that no row of any table but the conversation's was written, by draining the change log afterwards (`chat-actions.test.ts`: share link, note, tags, edit, reviewed; `chat-notices.test.ts`: move, turn, hide, combine, confirm the grouping, read again); the tests of the other tools check their own subject is unchanged until Confirm (`chat-actions.test.ts`, `regroup-apply.test.ts`), and each proposal's requests are run against the real routes. A test that every one of the twenty tools writes nothing does not exist yet: the regrouping tools (`propose_analyse_pages`, `propose_regroup`) are covered only by their own test. **The words next to Confirm are the page's, not the model's**: a proposal is data (ids, titles, values, before and after) rendered by the app in the person's language, so a model steered by a hostile document cannot describe a change as something milder than it is; the free text it does supply (a note, a field value, a label) is shown verbatim. **What the model cannot decide**: whether a share exposes scans, needs approval or lets the recipient ask (the card starts at the safe setting and the person chooses), and the owner can remove documents from a proposed share before confirming; it cannot propose more than 30 documents in a share, 20 in a bulk edit, 10 groups of duplicates, or more than five proposals for one question. **Duplicates**: two entries with different professional codes are different people and are never proposed together; tests with different units are flagged on the card; the merge is the owner's existing merge route and rename route, and the final form is written onto the kept entry only after the merges. **Not stored**: proposals live in the reply; the stored conversation holds the words only, so a reopened conversation offers nothing to confirm, and nothing the owner did not just see can be confirmed later. **What it does not do**: a document can still steer what the assistant proposes (**S-27**), which is why the proposal is shown in full and nothing is applied until Confirm; and the page, on the owner's open device, sends the requests, so a proposal cannot be confirmed from anywhere else. A share recipient's agent is built without any of these tools (`share-chat.test.ts`, `chat-actions.test.ts`).

**M-20 — A share recipient's question puts the shared documents, the owner's notes on them and the link's label in front of a model; the agent is held to the link in code.** **P2, P5, P8, P12.** Off unless the owner ticked `allow_chat` for that link and `SPINE_CHAT` is not `off`; a link without it answers `POST /api/share/:link/chat` with the same 404 as a scan the link does not allow. It sits behind the live link and scope resolution (**P2**); the recipient's own browser answers it from the sealed copy, and what the server sees of it is the pass it issues and the relay's count of calls. **What leaves the host** for the configured chat provider (with its residency refusals): the question, up to six earlier turns the page sends, the shared documents' headlines, and what the tools return for them: summary cards, the owner's notes, results with reference ranges, doctors and field values; never page text or scans (the same content a recipient already sees on the page, but now also at the provider, which is why the owner's checkbox says so), and, where embeddings are on, the words of the question to the embedder for the meaning search; and **the link's label**, the owner's own words, as quoted context (control characters and quotes removed, 120 characters, and the prompt says it is text, not an instruction). **Scope is code, not prompt**: the agent reads the owner's store, so every tool is held to the documents `listForShare(link)` returned for this request. Search results are cut to them before they are ranked together (the keyword and meaning queries themselves run over the owner's store on the device, and what is not shared is dropped before anything is shown or sent; a keyword's candidates are limited to 500 before that cut), the test list and a test's series are built from them alone (`share-tests.ts`, also what the trends routes use), a document opens only by a label the request gave, and the document the recipient has open (`document_id`) is used only if it is in that list. Anything outside is indistinguishable from nothing (`share-chat.test.ts` puts a second document with its own test and a unique word beside the shared one and checks that no tool output, and nothing the model was sent, mentions it). **The care chain is not offered to the agent**: links between documents are the owner's, and the only share route that returns them is the connections route of **M-28**, which the agent does not call, so the recipient's agent has no `get_connected_documents` and the open document's sections leave out `chain`. **The model is told who is asking**: a separate system prompt says the asker is a recipient and not the patient, to speak of "the patient", to treat only the shared documents as existing, and to give no diagnosis or treatment advice. **Bounds**: the route runs in the recipient's browser, so a limit there would bind nobody; what bounds spend by a leaked link is the relay's daily allowance for the share (`SPINE_RELAY_SHARE_DAILY_CALLS`, default 200 model calls, counted for `share:<id>` apart from any account) and the pass limit of 30 a minute per source. A question of 1,000 characters, at most six earlier turns, five rounds of tools (the owner's has eight), 12,000 characters a result, 120,000 a question and 90 seconds. **Nothing is stored**: no conversation, no history; the earlier turns come from the page, so a recipient can only shape their own conversation (they could write the same text as a question), and a failure's log line carries the link id and no medical text. Without a model that takes tools the route answers 409; there is no fixed-pipeline fallback for recipients. **What it does not do**: it does not stop a recipient from learning from the shared documents what the shared documents say (that is the point), a hostile document can still steer an answer (**S-27**), and revoking the link ends it at once. **Streaming**: `stream: true` sends the reply as lines (`routes/ndjson.ts`, shared with the owner's chat), after every refusal has been made as an ordinary status; the text shown while it is written is a draft with no citations, and a recipient who leaves aborts the model call. The owner's own chat is unchanged (**M-18**).

**M-19 — Approving a share link's visitor is a decision about a browser, not a person.** **P2, P5, P6, P7, P8.** A link made with `require_approval` has no key in its address. The visitor's browser makes a key pair, keeps the private half for the tab, and asks (`POST /api/shared/:id/access-request`, the server holds the request and tells the owner by mail when it has a mailer, with no label and no note in the mail). The owner decides at `POST /api/share-requests/:id/decision` from a signed-in session, never from a `GET`, so a mail scanner that follows the mailed link approves nothing; the owner's device answers the server with the share key wrapped to that browser's public key, which is all an approval is, and a denial wraps nothing. Approving a request on a link that has ended is refused, and switching approval on again drops the held requests and changes the key, so an earlier approval stops opening anything (**M-22**). A person who holds the approved browser holds the link, stated. The request flood is bounded by the per-source limit (**S-31**), the per-link limit and the cap of five waiting. What the earlier design did (a cookie held as `sha256`, `approvalFor` on every data route) is gone with the server-side links: a recipient's routes run in their own browser and cannot be a control against them.

**M-18 — A question sends the question, what is on screen and what the agent reads; the answer is a reading, not advice; the agent can only read.** **P8, P12.** On unless `SPINE_CHAT=off`. The chat is a LangGraph agent that decides what to look up with seventeen read-only tools (`TOOL_KINDS` marks each `read` or `action`, and a test holds the reading ones to reading) and prepares changes with twenty `propose_*` tools that only return a proposal (**M-21**). What leaves the host for the configured chat provider (with its residency refusals) is the question, up to six earlier turns, a description of what the person is looking at, and what the tools return: summary cards, the owner's notes, results with values and reference ranges, and field values for documents it opens, and with each search result the shown documents it is confirmed to be linked to (title, type, provider and date, as a search line names a document; never to a share recipient's agent, **M-28**); never snippets, scans, ids or paths, and page text only through `read_pages` (below). **Page text, on request of the model**: `read_pages` returns the text that was read from named pages of one upload (at most 6 pages, 2,500 characters each, set-aside pages refused, the label from `list_uploads` so only the owner's own uploads can be named, owner's agent only: a recipient's agent is built without it and a test holds the exact list). It is the same text that already went to this provider when the pages were read and when a mixed upload was analysed (**M-24**), so it adds no new kind of content, but it does mean a question can send pages the person did not mention: the step is shown in the panel as its own line ("Reading the text of pages 12, 13 · the file's name", `hygiene` of the step kind `pages`, `chat-notices.test.ts`) and the text is marked as data, not instruction (**S-27**). It is the tool that lets the assistant decide where a page belongs from what it says instead of from summaries. **Scope is enforced in code, not asked of the model**: a tool takes the signed-in user's id from the graph's state (set by the route from the session, passed in no schema, so the model can neither see nor write it) and reads through the store (every statement filters by `user_id`) over the shown documents only, so another account's, a set-aside document and one in an unconfirmed upload are unreachable by any argument the model can choose; the model never handles an id, only labels this request handed it, and a label it was never given opens nothing. The one deliberate exception is the document the owner has open (and, on an upload's screen, that upload's documents, or an upload the owner asks about in a conversation the app began: **M-23**), which reaches the model even before the grouping is confirmed. **Bounded**: eight rounds of tool calls (five for a share recipient, **M-20**), 12,000 characters a result, 120,000 a question, 90 seconds, one question 1,000 characters, six turns of 1,500; a run that hits a limit is told to answer with what it has. (The route runs on the owner's device, so a per-minute limit there would bind nobody; what bounds the cost is the relay's daily allowance for the account, **S-35**.) **Untrusted text**: documents and tool results are copied from scans, so the system prompt says to ignore instructions in them; because the agent has no tool that writes, the worst a hostile document can do is steer an answer, which carries links to the documents it came from and is labelled a reading of the records. The screen description is pointers the core resolves itself on the device (`chat/screen.ts`): the page sends no document text. **Actions, when added, must not weaken this**: an action tool returns a proposal that ends the loop and is shown for the owner's confirmation, which calls the ordinary authenticated route; it never executes from the agent (`docs/architecture/ingestion.md` **Ask your records**). The answer cites labels that were shown to the model (others are dropped) and the prompt forbids diagnosis and treatment advice; the page says the answer is not medical advice. **Conversations are stored** (`chat_conversations`, `chat_messages`) so the owner has a history. What is kept is their questions and the answers, with the documents an answer cited (id, title, section): medical text, so it is handled as the documents are: every statement filters by `user_id` and a conversation that is not the caller's is a 404 in every route (`chat-history.test.ts`; on the device there is one user); the conversation the model continues is read from the store and the browser can only name it; they are deleted with the account and when the owner deletes them (one or all, from History); capped at 200 conversations and 200 messages in one; kept on the owner's device and saved to the vault sealed like the rest of the records; not exported; no share route reaches them. A failed question stores nothing, and neither does one the person stops. The agent runs on an empty archive too (the question may be about Spine itself, **M-42**): the question then reaches the provider though there is nothing of the records to send with it. **Streaming** (`stream: true`) changes how the reply travels, not what is sent or kept: the same checks run before the first byte, the text shown while it is written is a draft with no citations, and only the final reply (citations checked against what the model was shown) is stored. The route is owner only; a failure's log line carries no medical text.

**M-17 — Documents are held back until the grouping is confirmed, and what the owner edited is theirs.** **P12.** Every listing of the owner's documents, every share query and the vectors, links, trends and doctors' lists use one fragment (`VISIBLE`: not set aside and the upload's grouping confirmed), so an unconfirmed upload cannot reach a share recipient, the search or a model call (the links search takes its documents from the same listing). The upload and regrouping screens still list them, scoped to the signed-in user, and the confirm route answers 404 for an upload that is not theirs. The records of what the owner edited or removed (`owner_edited`, `removed_readings`) are per user, deleted with the document, the upload and the account, and never returned by a route.

**M-16 — Looking for links is egress of summary text, and a model's word is a proposal.** **P8, P12.** On unless `SPINE_LINKING=off`. When the data finds a candidate (shared test or doctor, closeness in time or, if on, in meaning), one call sends the *summary card* of the document and of up to six candidates (the same cards as **M-15**, with each doctor's role and the owner's notes, trimmed to 600 characters; not pages or scans) to the configured chat provider, which has the residency refusals of any chat call. With no candidate nothing is sent. The cards are copied from scans, so they are untrusted text: the prompt says to ignore instructions in them, the model's answer is validated by schema, a candidate label it did not send is dropped, and nothing it says writes anything but a `proposed` link that the owner must confirm; a request or follow-up whose dates run backwards is refused in code. Candidates and chains come from the signed-in user's own documents (set-aside ones excluded), every statement filters by `user_id`, a link is written only between two documents that are the user's, and any other id answers 404 (`linking.test.ts`). A dismissed pair is never offered to the model again, and a search replaces only the suggestions for pairs it judged again. **Repeats are not stored or shown** (`linking/reduce.ts`): every document is judged on its own, so a pair was judged from both sides and "same episode" was found between every pair of a group. A link is redundant when the pair already has one at least as informative (request, then follow-up, then same episode), or when it is "same episode" between documents that other links already join; a search adds only what is not redundant given the links that stand, the chain is drawn without the redundant ones, and `tidyLinks` (after each search, and so on "Look for links again") deletes the automatic ones. It never touches a link the owner made or a dismissed one (a decision), and a suggestion that repeats a confirmed link is the one that goes. Nothing leaves the device and no model is involved. The owner's notes also go, as context, with the text of a document being read again (**P8**); the extraction prompt tells the model to take no field, result or date from them and to ignore instructions in them. The links route is owner only. The one place a link reaches a share recipient is the connections route of **M-28**: confirmed links between documents the link shares, direction and kind only. Links are deleted with their documents and the account. The whole-archive export carries them (all states, so the owner's decisions survive) and a restore writes them back; a single document's export does not.

**M-15 — Embeddings are egress of summary text, and vectors are as private as the text.** **P8, P12.** Off unless `SPINE_EMBEDDINGS=vertex`. On, the *summary card* of each document (title, type, provider, date, summary, doctors, a few key fields, test names; not the pages, notes or scans) and the words of a meaning search go to Vertex at the stated endpoint, region and project, through the relay, which has the same refusals as for the chat model (no default endpoint; a Google API key in its environment stops its startup); a failure's message carries the status, never the text. A vector can be turned back into much of the text it came from, so it is treated as the text is: stored per user and scoped by the store (**P12**), deleted with the document and the account, left out of exports, and returned by no route (asserted in `similarity.test.ts`). Vectors are compared only within the model that made them. Related documents and search results come from the signed-in user's own documents only (set-aside ones excluded); the one thing offered to a share recipient is a list of the shared documents that read alike or share a test or doctor (**M-28**), computed in the recipient's browser, from a share copy that holds the vectors of the shared documents only (numbers, never text: `slice-policy.ts`). A document's card is built from its stored data, so what is embedded is what the owner has already reviewed or edited.

**S-26 — What an imported export says is believed.** An export is not signed, so a restored document's title, summary, fields, results and `reviewed` flag are whatever the file says, as if the owner had edited them. Someone who hands a person a crafted zip can put plausible but false values in their archive, which then appear in trends and share links. They cannot reach another account, run code or read anything, and nothing is decided from the content, but a person should import exports only from themselves or from a source they trust. Not built, and the obvious step: import everything as unreviewed (so it passes through Review) when the export did not come from this instance, which needs the export to be signed or to carry the instance's identity.

**S-27 — A hostile document can steer its own translation and reading.** Text in a PDF (a forwarded report, a clinic's mail) goes to the model in extraction and in translation, and a page can contain instructions. The model has no tools and cannot read or change anything else, so the effect is bounded to that document's own extracted values, title and translation, and to the tags and test names it suggests, which the Library lets the owner tidy. A translation is checked to be about as long as its original, which stops a document turning it into a long output. Not preventable by checking; the owner reviews what is read.

**S-28 — Nothing limits how much one account stores.** The server limits an account's vault to `SPINE_VAULT_MAX_MB` (default 5120) and an object to `SPINE_VAULT_MAX_OBJECT_MB` (default 100); writing and deleting objects are limited to 600 a minute per source (`routes/vault.ts`), and reading them has no limit beyond the session's. Fine for a household instance; an `open` registration instance should set the quota to what its disk can bear before it is public.

**S-29 — One request downloads the whole archive.** The whole-archive export is built on the owner's device from what it already holds, so the server has nothing to export. What a stolen session can take is the sealed vault, which opens only with the master password.

**S-30 — A share link's page costs more the more it shares.** The recipient's browser resolves the link's documents on every request, so the cost is the recipient's own, not the server's; the server serves one sealed copy. A link covering a very large archive is slower to open, not unsafe.

### Closed

Fixed; the control is in [Controls in place](#controls-in-place).

**S-31 — The per-source rate limits could be bypassed with an `X-Forwarded-For` header** (**High**, **P5**). Fastify was built with `trustProxy: true`, which believes the *leftmost* entry, and nginx set the header with `$proxy_add_x_forwarded_for`, which appends the real peer to whatever the client sent, so a client chose its own `req.ip` and with it every limiter keyed on the source (login, second factor, signup, recovery, the share and approval routes, the recipient's chat) and the source in the application log. Reproduced against Fastify 4.29.1: `trustProxy: true` gave `9.9.9.9` for `X-Forwarded-For: 9.9.9.9, 203.0.113.7`, and `trustProxy: '127.0.0.1'` gave `203.0.113.7`. Now both ends are fixed, so either alone is enough: nginx overwrites the header with `$remote_addr` in both locations (`spine.conf`), and Fastify trusts only the loopback proxy (`trust-proxy.ts`, used by `index.ts` and the test harness). `auth.test.ts` sends a forged leftmost entry and asserts the limiter keyed on the address the proxy appended. Behind a proxy that is not on the host (the Docker Compose setup, `docs/self-host.md`), `SPINE_TRUSTED_PROXIES` adds that proxy's address to the list; a range wider than /8 or a word like `true` stops startup, since that would hand clients the choice again (`trustedProxies()` in `trust-proxy.ts`, tested in `config.test.ts`).

**S-32 — Dependencies carried known advisories and nothing checked them** (**Medium to High**). On 2026-10-18 `npm audit --omit=dev` reported 1 critical, 6 high and 1 moderate (`proxy-addr`, `fastify` 4.29.1, `@fastify/static`, `@fastify/busboy`, `find-my-way`, `fast-uri`, `brace-expansion`, `uuid`). Fastify moved to 5 with `@fastify/cookie` 11, `multipart` 10, `rate-limit` 11, `session` 11 and `static` 10, and `uuid` to 14; the suite, the typecheck and a boot of the real server (`/api/auth/me`, the share shell, the app) pass, and `npm audit --omit=dev` is clean for server and web. The build now stops on a high or critical advisory (`install.sh -b` runs `audit_dependencies`; `SPINE_SKIP_AUDIT=1` skips it for an offline build) and so does CI. **Residual**: the advisory database needs the network, so an offline build checks nothing; advisories published later are found at the next build, not before; `npm audit` without `--omit=dev` still lists development-only packages. **What the build runs on is pinned, too** (2026-10-25): one lockfile at the root fixes every package, and `npm ci` is what the images and both pipelines run (a fresh lockfile once moved Rollup and the device's worker stopped starting, which is why); the Node base image of `Dockerfile` and `relay.Dockerfile`, Caddy in `compose.yaml`, and the CI containers (Node, gitleaks at the version the GitHub job downloads, semgrep) are pinned by the digest of their multi-architecture index, so a rebuild is the same system. Semgrep's rules are fetched live and cannot be pinned. Moving a pin is a deliberate change: read the new digest from the registry, build both images and run the checks.

**S-33 — A stolen session cookie was the whole account, for 30 days** (**Medium**, **P13**). Now a sign-in is a row the owner can see and end, and the cookie alone is good for hours: **M-27**. **Residual, accepted**: malware on the owner's machine, or an adversary-in-the-middle proxy, still gets a working session until it goes idle (24 hours by default) or is ended; the password is asked again only before the server's own sensitive calls (account deletion, passkeys, credentials), not before reading; the records are on the device, which opens only with the master password, so a stolen cookie alone reaches ciphertext and account settings, not records. Device-bound session credentials are not built (no browser support to rely on yet); a session is not tied to an address or a user agent, because those change legitimately (a phone moving between networks) and the first would lock people out.

**S-34 — Passwords were checked for length only** (**Medium**, **P13**). `checkPasswordPolicy` (`passwords.ts`) now also refuses a password that is a common word or keyboard run from a list held in the source, those joined or with up to three letters after them ("Password2024!", "P@ssw0rd12345", "qwertyuiop12"), a repeated or sequential run, and one that contains the part of the account's address before the `@` (at signup). The master password's check runs on the device (`web/src/crypto/password-policy.ts`, **M-34**); `checkPasswordPolicy` serves the CLI and an account with no vault. `password-policy.test.ts`. **Residual**: it is a short list and a pattern check, not a breach check; a password that is long, unusual and already in a breach passes. A lookup against a breach service would be egress (**P8**), so it would be an opt-in k-anonymity query; not built. The server's message stays English like every server message.

**S-35 — Nothing bounded what the models cost in total** (**Low**). `llm/budget.ts` counts every model request (every task call through `invokeValidated`, and each round of the chat agent, owner's and recipient's) against one allowance per UTC day on that device, `SPINE_LLM_DAILY_CALLS` (the server passes it to devices with the other model settings; default 5000, `0` for no ceiling, a bad value gives the default); past it a call throws `ModelBudgetError` before it reaches the provider, the owner's chat answers 429 with the reason, a recipient's answers the usual 502, and the log says so once and again as the day passes 80%. `core/src/__tests__/model-budget.test.ts`. **Residual**: the count is kept in the store's `usage` under the name `instance` (the same repository the relay counts in; whether it survives a restart is the configured store's property). On a device it is the device's own count, kept in its in-memory database and not saved with the records, so each device has its own allowance and a reload starts it again; the bound that holds across devices is the relay's daily allowance per account and per share (**M-35**); embedding requests are not counted (one short text each); the ceiling is a guard rail, and the provider's own budget alert is the control that cannot be restarted away. A large bulk import can use a real share of 5000, so raise it before one.

**S-25 — Readers of uploaded files had no resource limits** (**Low**). `pdfimages`, `pdftoppm` and `sharp` had no time limit, and `pdfimages` writes every image on a page, so a file built with huge declared images could hold an upload forever or fill the temporary directory. The server parses no file now (**S-24**), so the time limits on poppler and `sharp` apply only where the Node tests run them. What still holds on the device: a photo declaring over 120 million pixels is refused rather than decoded (`MAX_PHOTO_PIXELS`), and a doctor's name, specialty and clinic are cut at 120 characters and a professional code over 24 is not a code (`MAX_DOCTOR_TEXT`, `MAX_CODE_LENGTH`; they come from stamps, signatures and the model, all of which a sender controls). `__tests__/stamps.test.ts`, `trends-doctors.test.ts`.

**S-1 — Share scoping failed open** (**High**, **P2**). A `tag` scope with no `scope_value` skipped every branch of the scope chain and returned everything (215 documents on a running instance). `share-scope.ts` is now the one place a scope is resolved: creation rejects what it cannot resolve, and the read path re-resolves the stored row, so older rows fail closed.

**S-2 — No rate limit on `/api/auth/login`** (**High**, **P5**). Now a per-source limit (the plugin) plus an instance-wide cap (ours, because the plugin applies only its first hook per request). Per-source runs first, so an address that has spent its budget stops consuming the instance-wide one.

**S-3 — `SESSION_SECRET` fell back to a repo-published value** (**High**, **P3**). `config.ts` validates it before anything binds an interface or opens the database, reporting every problem at once; `install.sh -s` runs the same check so a bad `.env` fails at deploy, not in a restart loop.

**S-4 — Share tokens stored in plaintext** (**Medium**, **P6**). Fixed by hashing, then removed: a share has no token any more. It is named by a random id and opened with a key that is never sent to the server (**M-36**), so there is nothing in the database or in a log that opens one.

**S-5 — No CSP, `Referrer-Policy` or `Permissions-Policy`** (**Medium**). All set, plus `object-src`, `frame-ancestors`, `base-uri`, `form-action`. `script-src 'self'` needs no exception for scripts but carries `'wasm-unsafe-eval'` for libsodium, PDF.js and the SQLite engine (WebAssembly; **M-34**). `Permissions-Policy` turns off every feature the app does not use and leaves `camera=(self)` for the scan screen. `style-src` carries `'unsafe-inline'` because React writes inline style attributes; inline styles cannot execute script.

**S-6 — `tag` scopes broken by double JSON encoding** (**Medium**, **P2**). Creation stored `JSON.stringify(value)` and the read path compared it unparsed, returning nothing. One module now serialises and parses.

**S-7 — The scope test could not fail** (**Medium**, **P10**). An `|| true` in the assertion. Links are now created through the real route and the returned id sets compared exactly, which also catches a scope returning *more* than it should.

**S-8 — Responses carried internal columns, server paths and live tokens** (**Low**). `SELECT *` sent absolute paths and, once multi-user arrived, `user_id` to share recipients and `file_path`/checksums from `GET /api/source-files`. Every query now lists explicit columns, and `response-shape.test.ts` scans whole responses for forbidden keys and absolute paths.

**S-10 — Failed logins unrecorded** (**Low**). Failures and successes are logged with the source address; the password never is.

**S-11 — No automated backup** (**Low**, **P11**). `spine-backup.timer` daily, `Persistent=true` so a Pi that was off catches up. `VACUUM INTO` for the database, because copying the file under load is unsafe in WAL mode. **The vault is mirrored too** (stage 5; the server keeps no originals or page images): the sealed objects under `data/vault/<user>/` are the only copy of a person's records, and the database holds just their metadata, so a snapshot without them restores an empty account. Objects are overwritten under the same id, so the mirror copies on a different size or a newer time and drops what the vault deleted (inside a user's directory only: a missing `data/vault` cannot empty the backup); it runs after the snapshot, because an object's file is written before its row. It is ciphertext, and account deletion removes the backup's copy with the live one. `data/shares/` is left out on purpose, since a copy of a revoked share would outlive its revoke. Retention `SPINE_BACKUP_KEEP`, default 7, never below one. **This protects against corruption and mistakes, not against losing the disk**: it writes beside `data/` by default. `SPINE_BACKUP_DIR` pointed at removable or network storage makes it offsite, and that path must also be in `ReadWritePaths`.

**S-12 — Request-body keys interpolated into SQL** (**High**). `PATCH /api/documents/:id` built its `SET` clause from `Object.keys(req.body)`, and a key like `user_notes = (SELECT token FROM share_links LIMIT 1), provider` appended SQL while keeping the parameter count valid. Handlers now pass a patch object and the store maps it to columns.

**S-13 — Fastify bound `0.0.0.0` while trusting `X-Forwarded-*`** (**Medium**, **P9**). On a home LAN port 3000 was reachable, bypassing nginx's rate limit and making `X-Real-IP` attacker-controlled. It binds `127.0.0.1` unless `SPINE_HOST` says otherwise.

**S-14 — `/share/` received none of the security headers** (**Medium**). nginx inherits `add_header` from an outer level only if the inner level declares none of its own, and the `/share/` location sets two. The block is repeated inside the location, with a comment that both copies change together.

**S-15 — `GET /share/:token` returned JSON** (**Medium**). The SPA fallback excludes `/share/`, so this route alone answers a recipient's URL, and it returned `{"ok":true}` instead of the documents. It serves the app shell as `text/html` now (`shareShellRoutes` in `routes/shared.ts`), and a plain page, status 410, for a link that does not exist (the page says itself when a copy it opens has ended). The visit is noted when the page opens the sealed copy (**P7**).

**S-18 — No way to delete a user** (**Low**). `npm run cli -- delete-user <email> --yes` removes the account, every row it owns, its vault objects and shares and the backup's copy of the vault, and says what it removed; without `--yes` it only reports. Database snapshots already taken still hold the rows until retention prunes them. A deleted user's sessions end on their next request.

## Review: translation, export and import, sharing, the library

This review is kept as it was written, before the records moved to the device: where it says a route or the server does something with a record, read the numbered entries above, which are current (the export, for instance, is built on the device, not by a route the server runs). A review of what was added with translation, zip export and import, the recipient's pages and trends, and the Library, read for what each could be made to do beyond its purpose: authorisation and scoping, input handling, resource use, what changes state, what leaves the host, and injection. Method: each new route, store method and page was read with the question "what does a hostile or careless caller get", and the findings were fixed with a test (`audit.test.ts` and the tests named below) or recorded as accepted gaps above.

**Found and fixed**

- **R-1 (Medium) — A zip could start every file at once.** A request with hundreds of PDFs, or an export with many files, began reading or restoring each immediately: poppler, OCR and model calls, and their cost, all at the same time, on a Pi. Reading and restoring now go through a queue that works on two files at a time and says `queued` meanwhile (`ingestion/jobs.ts`).
- **R-2 (Medium) — Any file could be written up to the zip limit.** Raising the request limit to 2 GB for zips applied to every upload, so 2 GB of something that is then refused as "not a PDF" was written first. The limit is now chosen from the file's first bytes: 200 MB unless it is a zip (`saveStream`).
- **R-3 (Low) — A write after the limit.** The stream writer wrote one more chunk after it had stopped keeping a file, which threw. Writes are now explicit and stop at the limit.
- **R-4 (Low) — A recipient's read changed the owner's record.** The first translation of a document with no recorded language saved the language the model found, from a public route. Public reads now change nothing; the owner's next visit records it, and moves the stored translation to its new digest instead of translating again.
- **R-5 (Low) — The manifest was looser than the data it fills.** Free text could stand in for a date, a document could carry 200 tags, a test name kept its case, and the whole could be 200 MB. Dates must be in the app's form, tags are at most 50 a document, the test name is lower-cased, documents and pages are capped in all, and the manifest is at most 64 MB.
- **R-6 (Low) — Tags could split.** The model's wording and a typed "Cardiology" were different tags. Every source now goes through one cleaning (`cleanTag`), the model is given the person's tags to prefer, and the Library merges what is left.

**Checked and found sound**

- **Another user's data.** Every new store method takes the acting user and filters by it; tags, providers and tests cannot be read, renamed, merged or removed by id or name across accounts (404), exports of another account's document are a 404, and a restore writes only rows for the acting user. `management.test.ts`, `archive.test.ts` and `isolation.test.ts`.
- **The zip as a path.** Entries are read by name and never extracted to a name the zip gives; the stored file's path is made by the server; a manifest that names `../../etc/passwd` finds no such entry; an entry named `manifest.json` used as a file is not a PDF.
- **The zip as a size.** The device's reader refuses an entry whose declared size is over the cap and cuts a larger one at the size it declared; the Node tests' reader counts bytes as they stream (**M-14**); an encrypted or damaged entry fails that file, not the request.
- **What a manifest can name.** No user, no id, no path; every id is made on import; doctors from a manifest are matched into the directory the way a read doctor is, filling blanks and never overwriting; the restore is one transaction.
- **The recipient's reach.** Trends are built from the shared documents' own results and filtered to their ids (a newer value in an unshared document appears nowhere), set-aside documents are excluded as everywhere, and a tag removed from under a link makes it share nothing, not more (`audit.test.ts`). The recipient's page links only to the same link's pages, never to the owner's directory.
- **Cross-site requests.** The export is built on the device and saved from it, not fetched from the server; the session cookie is `SameSite=Strict`, so another site cannot make the browser send it to the server's routes.
- **Headers and markup.** The export filename is built from letters, digits and dashes only; no new page renders HTML from data (React text only; the one `dangerouslySetInnerHTML` is the two-factor QR code, made in the browser by the `qrcode` library from the otpauth address).
- **Egress.** Translation sends text only, is listed in the egress table and can be switched off; export and restore send nothing.

**Left as gaps:** S-26 (an imported export is believed), S-27 (a hostile document steers its own reading), S-28 (no upload quota), S-29 (the archive is one download), S-30 (the cost of a very large share).

## Review: attacks on sign-in and access, and on agent-built software

Reviewed 2026-10-18, after the chat, share-approval, recipient-chat, chat-action, notice, regrouping, attachment and matching work (the milestones "Chat takes actions" and "Two-stage reading" in the history). Two questions: which attacks on sign-in and access are common now, and what is specific to software built with a coding agent and to software that contains an agent. Method: the sources below for the attack classes; then for each class a check against the code, and for each recent feature a read of its section in this document against the code and tests. **Checked** means a command was run or a file read in this review (the unit suite passed: 71 files, 1,262 tests; `npm audit`; a reproduction of S-31); it does not mean a real browser or the real model was driven, and nothing here was tested by an outside party.

### Sources

- OWASP Top 10:2025 [A07 Authentication Failures](https://top10.owasp.org/2025/A07_2025-Authentication_Failures): credential stuffing and password spraying, brute force, default credentials, session ids in the URL or kept across login, weak recovery, missing or ineffective MFA, no invalidation at logout; prevention is MFA, a check against the worst and breached passwords, identical failure messages, rate limiting with alerting, a fresh session id.
- [Session cookie theft bypasses MFA](https://thehackernews.com/expert-insights/2026/04/session-cookie-theft-you-showed-your-id.html) and [pass-the-cookie defences](https://cside.com/blog/cookie-theft-session-hijacking-and-how-to-stop-pass-the-cookie-attacks): infostealers and adversary-in-the-middle phishing take the post-login cookie; the structural answer is a session bound to a device key (Device Bound Session Credentials).
- OWASP [Top 10 for LLM Applications 2025](https://www.gravitee.io/blog/owasp-top-10-for-llm-applications-2025-a-practical-guide): prompt injection, sensitive information disclosure, supply chain, improper output handling, excessive agency, system prompt leakage, vector and embedding weaknesses, misinformation, unbounded consumption.
- OWASP [Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026) (list as summarised by [HUMAN](https://www.humansecurity.com/learn/blog/owasp-top-10-agentic-applications/); the full text was not available to read): goal hijack, tool misuse, identity and privilege abuse, agentic supply chain, unexpected code execution, memory and context poisoning, insecure inter-agent communication, cascading failures, human-agent trust exploitation, rogue agents.
- Indirect prompt injection in the wild: [Unit 42 (March 2026) and Google (April 2026) as reported](https://www.radware.com/cyberpedia/prompt-injection/): hidden instructions in pages, PDFs, mail and shared documents, and the "lethal trifecta" of private data, untrusted content and a way to communicate out.
- Code written by agents: [vulnerabilities in public AI-generated code](https://arxiv.org/pdf/2510.26103), [security degradation over refinement rounds](https://arxiv.org/pdf/2506.11022) (critical findings up 37% after five rounds), [security-related AI pull requests](https://arxiv.org/pdf/2604.19965). The classes that recur: injection, path traversal, weak randomness, missing authentication or authorisation, hard-coded secrets, insecure defaults.

### Attack classes against sign-in and access

| Attack | Where Spine stands |
|---|---|
| Credential stuffing, password spraying | Argon2id, identical answer and time for an unknown email (**M-3**), per-source and instance-wide limits. The per-source limit keys on the address nginx saw (**S-31**, fixed) and common or patterned passwords are refused (**S-34**, fixed; a breached unusual one still passes). Optional TOTP (**S-20**) is the real defence and is not required. |
| Brute force of the second factor | Per user 5 per ten minutes, pending login dropped after five, replay blocked (**M-12**). Holds, because the per-user limit does not depend on the source. |
| Account enumeration | Signup, forgot and reset answer identically; the residual timing difference is stated (**M-6**). Sound. |
| Session fixation | New session id at login and at the second step; password change ends other sessions (**M-4**). Sound. |
| Session theft, pass-the-cookie, adversary-in-the-middle | **Reduced (S-33, M-27)**: 24 hours idle and 14 days in all, a list the owner can end, the password asked again before the server's sensitive calls, mail on a new browser. A stolen cookie still works until idle or ended. `HttpOnly`, `Secure`, `SameSite=Strict` and the CSP stop web-side theft only. |
| Password reset poisoning (a forged `Host` header in the mailed link) | Closed by design: links are built from `SPINE_DOMAIN`, never from the request (`core/src/config.ts` `publicUrl`). Tokens are hashed, single-use, in the fragment, spent by `POST` (**M-11**). Sound. |
| Mail scanner or link prefetch spends or approves something | Verification and reset are `POST`; share-request approval is a `POST` from a signed-in session (**M-19**). Sound. |
| Rate-limit bypass by header spoofing | **Closed (S-31)**. Reproduced, fixed at nginx and in Fastify, tested. |
| MFA fatigue, SIM swap, SMS fallback | Not applicable: TOTP only, no push, no SMS, no email-code fallback. The fallback is recovery codes, then the operator (**M-12**). |
| Attacker enrols their own authenticator | **Accepted (S-22)**; enabling or disabling two-factor now ends the other sign-ins and mails the account (**M-27**), so it is noticed. |
| Leaked share link | The key is in the address fragment, never sent to the server; expiry, revocation, optional owner approval of each browser, the server's access notes (**M-19**, **M-22**, **M-36**). Sound within its stated limits. |
| Insecure direct object reference between users | The structural control (**P12**, **M-1**) and `isolation.test.ts` as a second user. The class most often found in agent-written code, and the best defended here. |
| Vulnerable or malicious dependency | **Closed for today (S-32)**: Fastify 5, audit clean, build and CI gate. New advisories arrive at the next build. |
| Server-side request forgery, command injection, path traversal | The server fetches no user-supplied URL and runs no program on a user's file (poppler, sharp and `pdfsig` exist only for the Node tests; the device reads files with browser libraries, **S-24**); zips are never extracted to a name they choose (**M-14**). SQL identifiers come from a whitelist (**S-12**). Sound; **S-24** is accepted. |

### Attacks on the agent features

| Risk (OWASP) | Where Spine stands |
|---|---|
| Prompt injection, direct and indirect (LLM01, ASI01 goal hijack) | A scanned document, a forwarded PDF or a translation can carry instructions (**S-27**). Held to: no tool writes, an action tool returns a proposal the owner confirms with the words drawn by the page (**M-21**), the model's answers to the linking and grouping tasks are proposals (**M-16**, **M-24**), prompts say text is data. Not preventable by checking, bounded by design. |
| Excessive agency, tool misuse (LLM06, ASI02) | `TOOL_KINDS` holds every tool `read` or `action`, a test fails otherwise, a tool takes labels and never an id or a user, and caps on rounds, characters and time (**M-18**). Sound. |
| Identity and privilege abuse (ASI03) | The user id comes from the session into the graph's state, never from an argument the model writes; the recipient's agent is built without the owner's tools and held to `listForShare` in code (**M-20**). Sound; the one deliberate widening, **M-23**, is for the owner's own unconfirmed upload. |
| Data exfiltration through output (LLM05, "lethal trifecta") | The page renders the model's text as React elements with no image and no arbitrary link (checked: `Markdown.tsx` writes none; citations become links to the owner's own documents), and the CSP has `img-src 'self' blob:` and `connect-src 'self'` plus the relay's address only, so a markdown image to another host cannot load and a script could reach no other host to send data to. The first leg is the document, the second the owner's data, and the third (a way out) is closed. Sound. |
| Sensitive information disclosure (LLM02) | Egress is enumerated and switchable (**P8**); the recipient's chat sends the shared documents' cards, notes and the link's label, which is stated beside the checkbox (**M-20**). Sound. |
| Vector and embedding weaknesses (LLM08) | Vectors are per user, behind the store, never exported or returned (**M-15**). Sound. |
| Unbounded consumption (LLM10, ASI08 cascading failures) | The relay's daily allowances per account and per share and the core's own ceiling (**S-35**); there is no agent-to-agent hop. |
| Human-agent trust exploitation (ASI09) | The risk is that the owner presses Confirm on what a hostile document made look reasonable. Mitigated by showing every proposal in full from data, starting security options at the safe setting, and capping a proposal's size (**M-21**). A person can still be wrong; there is no stronger control short of removing the feature. |
| Memory and context poisoning (ASI06) | Stored conversations are history only: the model sees them with citation markers stripped, but a past answer that a hostile document steered is in it. Bounded by the same limits as the first row; conversations can be deleted. Accepted with **S-27**. |
| Unexpected code execution, supply chain (ASI05, ASI04) | No model output is executed or evaluated. Dependencies: **S-32**. No vendor package outside `server/src/llm/adapters/`, and `core` imports no native library (`boundary.test.ts`). |

## Multi-user

The requirements multi-user put on the design. All are implemented; the controls they produced are in [Controls in place](#controls-in-place).

**M-29 — Documents are read after the owner confirms the grouping, so the text goes to the provider once, for the grouping that was approved.** **P8, P12.** Nothing about egress is new: the same page text goes to the same provider, with the same refusals (**M-8**), for the same extraction. What changed is when. Before, an upload was parsed, grouped and every document read in one run, and a grouping the owner then fixed by hand sent the changed documents' text again ("Done"). Now the pipeline stops after the pages and the proposed grouping (an upload of exactly one page is the exception: it has no grouping to check, so the pipeline starts `read-upload.ts` for it, confirming, with the same text, refusals and egress) (`needs_reading = 1` on each document; no title, summary, fields, results, tags, doctors, stamps or signatures), and `POST /api/source-files/:id/grouping/confirm` starts `read-upload.ts`, which reads each marked document once, files the doctors named by stamps (images, so only with the switch, **M-7**) and digital signatures, and only then confirms the grouping, so a document is never visible half-read (**M-17**). The confirm route answers 202 while it runs and 200 when nothing is left to read (an older upload, a restored one); it takes the owner's session and the upload must be theirs; one reading runs per upload (`isReadingPages` is true meanwhile, so a move, a split or a regrouping answers 409). Marking is done by the core, not trusted from the page: a move, a split, a join, a page set aside and a regrouping each set `needs_reading` on the documents they touched, and `POST /api/source-files/:id/extract` on an unconfirmed upload reads nothing and marks. What the assistant sees: `get_upload` says "NOT READ YET" for such a document and its prompt says to judge the grouping by its pages (**M-23**, `read_pages`). **Failure**: a model that cannot read any document fails the reading with the upload still unconfirmed; one that cannot read some leaves them marked, and the rest proceed. The marker, a number, is part of the owner's own document record (`documents.needs_reading`); it is set to 0 in a share copy (`slice-policy.ts`), so no share carries it, and the documents of an unconfirmed upload are not shared. `chat-notices.test.ts` (the two stages), `pipeline.test.ts`.

**M-31 — Files that are converted on arrival are decoded by libraries that read what a stranger could craft.** **P5, P8.** HEIC (`heic-convert`, WebAssembly), a Word document (a zip read through `ZipReader`, one entry of at most 30 MB, at most 2,000 entries, never extracted to a path) and a text file (at most 2 MB) are turned into a JPEG or a PDF (`ingestion/convert.ts`). A decoder fault is caught and the file refused as `not_pdf`; the decoder runs in the owner's own browser (in the core's Web Worker, sandboxed by the browser), with its memory bound by the 200 MB upload limit, so a hostile HEIC can spend that person's memory and time but not reach the server or another account. The text taken from a Word document is escaped nowhere because it is never interpreted: it goes onto a PDF page as text. Nothing leaves the host for a Word or text file (the text parser reads it); a HEIC is a photo and needs `SPINE_MULTIMODAL_ENABLED` like any. **Not covered**: macros and embedded objects are ignored, not scanned; a HEIC is decoded once at upload, so a decoder CVE is reachable by any file the owner adds (`npm audit` gates the build, **S-32**).

**M-44 — A private instance lets in only the accounts its administrator approves.** **P3, P4.** `SPINE_REGISTRATION=approval` lets anyone ask for an account (consent given and recorded as for `open`), which is stored with `users.approved = 0` and holds no session: the login answers 403 `awaiting_approval` only to the right password (so an unknown address and a wrong password are still indistinguishable), and `maySignIn` in `session-auth.ts` (verified and approved) is asked by `authenticate`, the second step, a passkey sign-in and a device's enrolment, so no other door opens it. The administrator approves with `npm run cli -- approve-user` or, if the signed-in account's own address is in `SPINE_ADMIN_EMAILS`, from the account page (`/api/admin/accounts`, approve needs a recent password; the list and every action are refused to anyone else whatever the request carries). A request is refused by deleting it (an approved account is never touched by that route). With no mailer nothing is sent and approval stands for confirming the address, so a sign-up form cannot be used to send mail to a third party; with one, the address is confirmed as well and approval is mailed once. A sign-up for a taken address is answered exactly like a new one. `SPINE_INSTANCE=private` marks the deployment as private on the front page, the sign-in page and `/trust`, and stops the server starting with `open` signup. **Not covered:** it labels and gates account creation; it does not make the code or the app private, which stay open source under the AGPL, and a waiting account still costs a database row (the sign-up is rate limited like `open`'s). Existing accounts are approved (the column defaults to 1).

**M-45 — Plans and payment: the server knows which plan an account has, never a card, and a limit is enforced where the server can see it.** **P1, P3, P8.** `SPINE_BILLING=on` (refused with `SPINE_INSTANCE=private`, and refusing to start without every Paddle setting, `billing/config.ts`) gives accounts a plan. **What is kept** (`subscriptions`, `ai_usage`, `billing_events`): which plan, the provider's customer and subscription ids, when it renews or ends, how much AI reading was used in the period (a number), and the ids of the messages already applied; no card, address or name. A person pays on Paddle's checkout, served from an origin of its own (`checkout/`) so that Paddle's script never runs where the records are open; the server only creates the transaction (`createCheckout`) and, later, opens Paddle's customer portal. **Paddle tells the server by signed messages** (`POST /api/billing/webhook`): the signature is HMAC-SHA256 over `<ts>:<raw body>` under the destination's secret, compared in constant time, with a five-minute window on the timestamp (`verifySignature`), over the body exactly as sent (a scope of its own keeps the raw text); a message that fails is 401 and changes nothing. A message names a user only by the id Spine put in the transaction's custom data, or by ids already linked; a *subscription* message that cannot be placed is answered 409 so the provider sends it again (a purchase message that cannot be placed is ignored, since its subscription message follows), one for an account that is gone is ignored, and one older than what is known is ignored (they can arrive out of order). **Where limits are enforced** is only where the server sees the work: the relay checks that the plan includes a task and has allowance left before a call and charges the measured size after it succeeds (`billing/gate.ts`, the size of the request the relay received, not a number the device claims); vault writes use the plan's size (`vaultBytesFor`), a sealed share the plan's live count and approval mode (`routes/shared.ts`). A modified client can still use what runs only on its own device (the timeline, search, export): those are free in practice and not gated. A share's recipient is held to the owner's plan for features and counted against the share's daily calls, not the owner's allowance. **Plans:** a subscription is to Premium or to the family plan, which is whatever its prices say (`planOfItems`; a message listing no price keeps the plan it had); the family plan has six people, letting others in, and a reading allowance three times Premium's, shared by them all. **Not covered:** several calls in flight can overshoot an allowance by a few, bounded by the relay's daily count; the cost weights are first guesses (`taskCost`); the founding price can be taken by a few more than 500 when purchases are started together, and is honoured; a refund or chargeback is applied only when Paddle's message says so. An account with a running Paddle subscription that is not set to end cannot be deleted until it is cancelled (a plan the operator granted does not hold it). The counts of sign-ups and shares opened (`metrics`) are a number a day under a name and are never joined to an account; the waitlist is an address and a day. Nothing is deleted when a plan ends.

**M-46 — The sealed bytes are in an object store the server reaches, and a bucket holds exactly what the file system did.** **P1, P8, P11.** The vault's objects and a share's copies go through one port (`server/src/objects/`, chosen by `SPINE_OBJECTS`): files under `DATA_DIR` (default), or a Google Cloud Storage bucket reached as the process's own identity (no key file, so nothing to leak or rotate; the role is `objectAdmin` on that bucket). **What is stored does not change:** ciphertext under keys built only from ids the server has already checked against a fixed alphabet (`vault-files.ts`, `shared-files.ts`), and a store refuses any key with a segment that is empty, `.` or `..`, so an id cannot reach outside its place; the filesystem adapter also resolves the path and refuses one outside the data directory. **Failure is visible (S9):** a bucket that cannot be reached throws and is never taken for "no such object" (a read of an object the database lists would otherwise answer 404 and a device would think it lost data); a write is tried a few times on a server error or a rate limit; when a vault write fails after its row was made, the row is withdrawn and the device is told 503 `storage`, so it refetches the list instead of finding an object that cannot be read. Deleting an account removes the vault's files first and its rows after, and a failure of the files stops it; a share's rows go before its files (`eraseFor`, then `removeShare`), so a failure there leaves sealed bytes nothing refers to, which the next sweep of ended shares does not find. **Residency** is the bucket's location, which the operator sets when making it and checks in the console (`docs/deployment-gcp.md`); this code cannot see it. **Backup:** `backup.ts` mirrors files only; for a bucket the backup is its versioning or soft delete, and a lifecycle rule must expire old versions or an erased account's ciphertext outlives the retention the privacy notice states. **Not covered:** nothing here checks the bucket's location, public-access prevention or versioning; an object written and then lost to a crash between the write and the row cannot be told from one never written (the vault's row is made first and withdrawn on a failed write; a share's row is made first and not withdrawn, so a failed write leaves a share that answers not found until the owner's device publishes it again).

**M-47 — The emergency card is opened without being asked, and says so before it is turned on.** **P1, P5, P8.** (FR-EMG, CR-EMG-01.) The owner writes a short card (`core/src/emergency.ts`: name, birth, blood type, allergies, conditions, medications, up to five contacts, notes, each bounded; nothing is taken from the documents). It is kept with the records (`emergency_cards`, synced, never in a share, not exported) and turned on from the owner's device, which seals it under a fresh key (`sealPart`, bound to the bundle's id and the part `card`) and sends it as a bundle of kind `card`: **no end of its own, one for each person the account keeps records for (at most ten), at most 64 KB, outside the plan's share limits so it is on every plan, never waiting for approval** (`PUT /api/shared/:id` with `x-spine-kind: card`). The key is in the address after the `#` (the QR code's content) and in the owner's records; the server never has it, so it holds ciphertext it cannot open, as for a share (**M-36**). Anyone who has the whole address reads the card, with no account and no question; that is the feature, and the page that turns it on says so before it does, and again that a card already seen may have been copied. **The routes** (all the owner's, run on their device): `GET` and `PUT /api/emergency`, `POST` and `DELETE /api/emergency/publish`, `POST /api/emergency/reviewed`, `POST /api/emergency/replace` and `POST /api/emergency/take-over` (after a promotion, **M-51**); at the server `PUT /api/shared/:id` with `x-spine-kind: card`, `POST /api/shared/:id/review` and the public `POST /api/shared/:id/opened`. **Every opening is counted and told**: the viewer posts `opened` once the card has opened in the browser; the server keeps the time and the country (never the address) until the owner's device collects them into the card's scan list, bumps a daily count (`card_opened`), and mails the owner at most once in fifteen minutes per card (`cardOpenedMail`: it names no record, and a test holds the wording clear of clinical words). The rate is per process, so several instances may send a second mail. **Turning it off** revokes the bundle and deletes its sealed bytes at the server and forgets the address and key in the owner's records; a new card gets a new id and key. **The offline code** holds the card as plain text (up to 800 bytes, the most urgent first, and a count of what did not fit), so a phone with no network reads it and the server is not involved at all; it can therefore not be turned off, counted or mailed about, and the page says that before it shows it. **Yearly review:** the card records when it was last sent or said to be still right (`emergency_cards.reviewed_at` on the device; `shared_bundles.reviewed_at` at the server, which sees only that date and `reminded_at`, never the card). A card that is on and unreviewed for a year is flagged in the app (`review_due`), and the server mails the owner (`remindCardReviews`, at start and hourly; `cardReviewMail`, neutral, no clinical word, a test holds it) once, and again a year later if still untouched; saving the card, sending it again or "It is still right" starts the year over. With no mailer only the in-app flag exists. It never turns a card off: an old card is flagged, not broken. **Replacing a lost code:** `POST /api/emergency/replace` turns the old bundle off first (a lost card must stop opening before anything else; if that fails nothing changes), then sends the card under a new id and key; if the second step fails the card is left off and the page says so. The old address answers 410 from that moment, and the page that opens it says the card is not available. **The offline code cannot be replaced** (it is the card, as text): the page says it cannot be turned off or counted where the code is offered, and that it cannot be replaced in the section for a lost card. **Official details:** the owner may keep numbers that identify them (a national identification number, health insurance, a passport or card number, organ donor, or one of their own) with the card, in the same sealed record, and put each on the card by ticking it; **none is on the card unless ticked**. Everything that leaves the device or reaches paper is built from `publicCard(card)`, which drops the details not ticked: the sealed card, the offline code's text and the printed copy; tests hold that a detail that is off is in neither the sealed card nor the offline text (`emergency.test.ts`); the printed copy is made from the same function and the browser check looks at what is ticked on it, not at what is off. Turning one on later is sent on the next save. The page says, where they are added, that anyone who reads the card reads what is ticked. **Printed copy:** a bank-card-sized (85.6 × 54 mm) front and back made from the same public card, with the code on the back (the online one if the card is on, else the offline one); the lines of the card (Allergies, Medicines and so on) are English, as the offline code's are, so it reads the same anywhere, while its title and the sentence on the back are in the language of the page. **What the card is not:** it is the owner's own text, with a line on the card that it was written by its owner and is to be checked, and nothing on it is produced or checked by a model. **Not covered:** a code on a wallet or a fridge is read by whoever holds it; the viewer's key is in the address bar for a moment and in the tab's session storage so a reload still opens it; an owner who loses a device does not lose the card's key, which is in their synced records and shown on their other devices (a lost *device* is not a lost *card*: the code to replace is for the printed card); a card's text is not translated (only the labels around it are).

**M-48 — An account can keep records for more than one person, each under a key of their own, and the plan decides how many.** **P1, P12.** (FR-PRF-01.) The vault always had profiles (`profile` objects, one profile key each, sealed under the account key, **M-34**); the device now lets an account have several. **What is separate:** each person's records are their own database on the device (`startCore` per profile), their own sealed objects under their own key (a wrapped key is bound to the profile's id, so it does not open as another's; `crypto.test.ts`), their own search, share links and emergency card. Opening another person saves the first (`close`, which refuses with `unsaved` rather than drop changes), starts the core on the other's objects, and the page starts its screens over (`PROFILE_CHANGED`, the chat and guide providers are remounted), so nothing of the first person stays on screen; the master password is not asked again, since the account key is already held. **What is not separate:** the account key opens every profile, so anyone with the account's password or recovery kit opens all of them (delegating one profile to another account, with its own key, is **M-49**); the server sees how many profiles exist (it counts `profile` objects to enforce the plan) and nothing in them; the sealed copy kept in the browser is one scope per profile (**M-43**); the choice of which person to open is remembered per account in `localStorage` as an opaque id. **The plan:** `profiles` in `billing/plans.ts` (trial six, free one, Premium one), checked at the vault route when a profile object is created, answered 402 `plan_required`; a person already made is never removed when a plan ends, only a new one is refused. **Editing:** the owner can correct a person's name and a child's birth date (`VaultSession.updateProfile` opens the record, changes it and seals it again under the same key, so nothing else in the vault changes; a device that changed it first makes the second a conflict); a person let in cannot write the record. **Not built:** removing a person (removing means deleting every object under their profile; until then the account can be deleted). **Cards:** an account's emergency cards (**M-47**) are one for each person, at most ten.

**M-49 — Another account can be let into one profile with a code, and ending it replaces the profile's key.** **P1, P12.** (FR-PRF-02, TR-CRY-06, TR-CRY-07.) **The routes:** `POST /api/delegations/invites` and `DELETE /api/delegations/invites/:id` (the owner), `POST /api/delegations/claim` and `PUT /api/delegations/:id/key` (the one let in), `GET /api/delegations`, `POST /api/delegations/:id/state` (pause or resume), `POST /api/delegations/:id/revoke` (the password asked again), `DELETE /api/delegations/:id` (leaving), `POST /api/vault/profiles/:id/rotate`, and `/api/delegated/:grant/objects…`. **The invitation:** the owner's device seals the profile key under a key a one-time code makes (the same eighty-bit code as device enrolment, **M-41**, with its own derivations: an id, a key and a proof) and leaves it with the id and a hash of the proof (`profile_invites`); the code is told to the other person, by voice or in a link whose fragment never reaches a server, and is never sent. It works once, for a week, for someone other than the owner, who shows the proof; at most ten wait at a time. **The grant:** the claimant opens the profile key with the code and seals it to their own account's public key (a sealed box); that is what the grant holds (`delegations.wrapped_key`), and only that account's private half opens it. The server sees which account may reach which profile, its role and when; never a key. **Reaching it:** `/api/delegated/:grant/objects…` are the vault's own handlers (`listObjects`, `getObject`, `putObject`, `deleteObject`) with the profile fixed, on the owner's vault: the grant must be the caller's and active; a delegate sees and writes only objects of that profile, never the profile record, and only a *guardian*, or the person themselves (the `self` role of **M-50**), writes (a *viewer* is refused with 403 `read_only`); what is written counts against the owner's vault and plan. **Ending it:** the owner revokes (password asked again), then the owner's device replaces the profile's key (`rotateProfile`): a new key, every data key of the profile sealed under it, the profile record sealed again, and the new key sealed to each person still let in, sent as one step that the server accepts only if it names exactly the profile's live objects and the grants still held (the new profile record is stored first and the rest changes in one transaction; if the database step then fails, the old profile record is put back, so the profile is never left sealed under a key the database does not hold); the owner's other sign-ins end so no device goes on writing under the old key. **What that does:** what the former delegate holds (the old key) opens no object as it is stored now, which `vault.e2e.test.ts` shows. **What it does not:** content they already read, or copied, cannot be recalled; a delegate who kept the *data keys* they once opened could still open the old bodies they also kept. **Plan:** `delegation` (trial yes, free and Premium no; the family plan yes); accepting needs no plan. **Not covered:** a viewer's edits on their own device are refused at the server and the page does not disable editing: what it shows is the notice that the latest changes are not saved yet (`check:app` joins as a reader and tries a change); a share link or emergency card made from a profile you were let into belongs to your account, not the owner's, and the owner's other devices cannot update it; an account that deletes itself takes its grants and invitations with it, and those it was let into stop opening; the grant's role cannot be changed after the fact (end it and invite again); no mail tells a delegate their access ended (the people list changes).

**M-50 — A child's profile is kept by a guardian, carries a sealed birth date, and the child gets an account of their own only from sixteen, at the guardian's invitation.** **P1, P12.** (FR-FAM, CR-FAM-01, CR-FAM-03.) A child's profile is an ordinary profile (**M-48**) whose record, sealed under the profile key, also holds `kind: child` and a birth date; the server never sees either, so every age rule runs on the device (`core/src/family.ts`: sixteen for an account of their own, GDPR Art. 8 and Romania's age; eighteen for the records being their own). A *co-guardian* is a `guardian` grant (**M-49**); a child's *own account* is a grant with the role `self`, which reads and writes as a guardian does, may be held by one account only, and is offered by the page only when the child has a birth date and is sixteen or more: **the guardian making the invitation is the consent**. The role is not checked by the server (it cannot know the age), so this is a rule of the page and of the owner's device, not a control against an owner who sends the request by hand; what it protects is the guardian from a mistake, and the child from a prompt they should not get. The plan (`profiles`, `delegation`) decides how many children and whether others can be let in. **A wrong date** is corrected by the owner and takes effect at once on the owner's devices (and on a guardian's at their next sign-in); a `self` grant that already exists is not ended if the corrected date makes the child younger than sixteen: the owner ends it if that was the point. **Not covered:** CR-FAM-03, whether some of a child's records may be hidden from their guardians before eighteen, is for the lawyer and nothing here hides one (a teenager with an account of their own sees what the guardian sees); a guardian who is also the owner can end the teen's access and re-invite, as any owner can; nothing stops a profile whose record has no birth date from being given a `self` grant if it is a profile of an adult.

**M-51 — At eighteen the person a profile is of can take it into their own vault, under a new key, and everyone else's access waits for their choice.** **P1, P12.** (CR-FAM-02, TR-CRY-07.) The person's own account holds a `self` grant (**M-50**). **Promotion** (`POST /api/delegations/:id/promote`, the password asked again, five a ten minutes) is one step the person's device makes: a new profile key under *their* account key, every data key of the profile and the profile record sealed under it, and the new key sealed to the public key of every other account that had the profile. The server accepts it only if the grant is the caller's, active and `self`, the objects named are exactly the profile's live ones in the old owner's vault, and the grants named are exactly the others held; then, in one transaction (`DelegationRepository.promote`, SQLite and Postgres, both vaults locked in one order), each object is copied into the person's vault with its new key and sequence, the old rows become tombstones (so the old owner's devices drop them), the other grants move to the person as owner and become `paused` with the new key sealed to their holder, the person's `self` grant ends and the profile's invitations are cancelled. The sealed files are copied across before anything changes, so a failure of that changes no record (copies already made stay in the new vault, nothing refers to them), and the old files are removed after the commit (a failure there leaves stray sealed bytes nothing refers to, logged). **What this gives:** the old owner's account holds no live row, no file and no usable key for the records (tombstone rows remain, so its devices drop them); a guardian's access is paused, not ended, with the new key already sealed to them, so the new adult resumes it with one click (**M-49**'s controls) or ends it, which replaces the key again; nothing is refused for what a plan holds (the person's account may hold more people or bytes than its plan, as after a downgrade). The old owner is mailed. **What it does not:** the age is not checked by the server, which cannot know it (the page offers the step from eighteen; the person is the one who takes it, which is the consent CR-FAM-02 asks for, and a guardian cannot do it for them: only the `self` grant can); what a guardian already read or copied cannot be recalled; the old owner's account keeps the share links it made of the profile until it revokes them, and **an emergency card published for the profile is taken over by the new owner**: its record moved with the profile, and right after the promotion the person's device asks the server to move the card's bundle to their account (`POST /api/shared/:id/take`, `shared.take`), allowed only to an account holding a `promoted` grant (the person's own grant, ended by the promotion) from the bundle's owner and naming the bundle's id, which is unguessable and known to them only from the records they took; the printed code goes on working and is theirs to replace or turn off, and the scans and requests for it move with it. If that call fails the old owner's account still owns the bundle and the page can repeat it (`POST /api/emergency/take-over`); a card's id could in principle be named by a promoted person who learned it otherwise, to take a card of the old owner's that is not their profile's, which the unguessable id and the key make no easier than having the code; a child with no account of their own stays with the guardian after eighteen until they are invited as themselves (the page says so). **The question for the lawyer** (CR-FAM-03) of records a teenager may hide from their guardians before eighteen is not answered by this.

**M-43 — The device keeps a sealed copy of the vault's objects, so opening the records again does not fetch everything.** **P1, P5, P8.** Opening the vault after a reload fetched and opened every snapshot part and segment again, and the cost grew with the archive. The core now keeps, in IndexedDB (`web/src/crypto/sealed-cache.ts`, database `spine-sealed`, one scope per profile), the sealed objects it fetched or wrote, and reads them from there (`VaultSession`'s `get`, with `useCache`). **What is kept is exactly what the server holds**: the sealed body and the key it is sealed under, which only the account's keys open. No record's text, no key, no master key and no plaintext is ever written to the browser's storage; the records are still in memory only (**M-34**). What a person with this browser's storage learns is that there are objects, how many and how large, which the server holds and knows already. **Only objects written once are kept** (a segment, a snapshot part, a file): the index and the profile are read from the server every time, so a copy can never be stale or hide another device's change. **A copy is never trusted**: it is opened with the same authenticated decryption as a fetched object, bound to its id and kind, and one that does not open (damaged, or from another vault) is dropped and the object is fetched. A full listing of the vault drops what it no longer holds. **Bounded and best effort**: about 300 MB for an account, the least recently used go first, one object over a quarter of that is not kept, and any failure (a private window, a full disk, storage the browser cleared, as Safari does after a week unused) is a miss and turns the copy off for that visit; the app works with none. **Cleared at sign-out and when the account is deleted** (`clearSealedCache`, called by `api.auth.logout` after the vault is locked and by `api.account.remove`). **Residual:** a browser closed without signing out keeps it until the next sign-out, and a session ended from another device or by expiry does not clear it, because nothing runs on the device then; the copy is ciphertext, no weaker than the server's own, but a person who shares a browser should sign out. **Not done:** the copy is not encrypted a second time, because it already is; the page's file reads are unchanged (a page image is fetched ahead of its request, asynchronously, without a copy in memory beyond the file layer's). Tests: `web/src/e2e/vault.e2e.test.ts` (a read from the copy asks the server nothing; a damaged copy is not trusted; the index is never kept; a listing and a removal drop copies), `web/src/core/persist.test.ts`, `check:app` (a reload fetches no segment, signing out removes the database).

**M-32 — A share link can name episodes, and what it shares follows the episodes.** **P2, P12.** `scope: 'episode'` takes up to 50 episode ids; creating or changing a link accepts only ids that are the owner's **confirmed** episodes (one answer for "not yours", "not confirmed" and "does not exist", **M-5**, in `checkScope`), and the read path re-resolves the stored value (`share-scope.ts`, **P2**). `documents.listForShare` reads the documents of those episodes **when the copy is built** (at creation and at each refresh, about 15 seconds after the owner's records change while the device is open, **M-36**), through `VISIBLE` (a document set aside is not shared) and only while the episode is still confirmed and the owner's: an episode since dismissed or removed shares nothing from the next refresh, and a document added to a shared episode is shared from then on, which the creation form says. Episode ids are never returned to a recipient, and an episode's title (the owner's own words) is not part of any public route. `episodes.test.ts` covers growth, dismissal, a stranger's episode, an unconfirmed one and a missing one.

**M-33 — A passkey is a second way to sign in, and is both factors at once.** **P1, P5, P13.** `routes/passkeys.ts`: WebAuthn through `@simplewebauthn/server`, relying party = the host of `SPINE_DOMAIN` (`passkeys.ts`), attestation `none`, **user verification required** at registration and at every sign-in, resident keys required (so no account name is asked or leaked). Only the public key, a counter, the authenticator's transports, whether it is synced between devices, a name, two times and, for a passkey that opens the vault, a sealed copy of the account key are kept (`user_passkeys`, deleted with the account); the credential id is unique across accounts. **Sign-in** is two public calls, both rate limited per source and instance-wide: `/api/auth/passkey/options` makes a challenge and regenerates the cookie session, which carries it; `/api/auth/passkey/login` takes it out of the session **before** verifying (one try, five minutes), checks origin, relying-party id, user verification, signature and that the counter has not gone back (a cloned key), refuses an unknown key or an account whose address is unconfirmed with one answer, regenerates the session again and calls `startSession`, mailing a new browser. It is therefore the **second place a session is issued** (`second-factor.test.ts` guards the list) and it does not ask for a code, because user verification makes the passkey possession and the person together; an account with two-factor sign-in on can still be entered with the password route only through its code. **Managing** them: add and remove need a session and the password typed in the last ten minutes (`requireRecentAuth`), adding is limited to ten, both are mailed (so a stolen cookie cannot quietly add its own way in), a passkey of another account is a 404. **Not covered**: a lost device is handled by removing the passkey from another one, by the operator's `disable-2fa` and `reset-link` (the vault then opens with the master password or the recovery kit); there is no attestation check of the authenticator's make; a synced passkey (iCloud Keychain, Google Password Manager) is as safe as that account is. **Opening the vault** (stage 5 addition): a passkey whose authenticator supports the PRF extension can also open the vault. The device makes a key from the PRF output, seals the account key under it and sends only that (`PUT /api/auth/passkeys/:id/vault-key`: signed in, password typed lately, mailed; a sealed value of the right shape; one's own passkey); the server stores it as ciphertext on the passkey's row, returns it with that passkey's sign-in, and never receives the PRF output, which the browser removes from the ceremony before sending it. The extension is asked for at registration. Removing the passkey, or turning the option off, removes the sealed copy; a copy that no longer opens (a vault made again after an erase) falls back to the master password. Tests: `passkeys.test.ts`, `crypto.test.ts`, and `npm run check:app` with Chrome's virtual authenticator.

**M-41 — A new device is let in by one that is signed in, with a one-time code and no master password typed on it (TR-CRY-05).** **P1, P5, P8, P13.** Closes the "enrol from a signed-in device" gap. The signed-in device (`web/src/components/AddDevice.tsx`, `web/src/crypto/enrolment.ts`) makes a code of 80 random bits (sixteen characters of the recovery key's alphabet and two check characters), derives from it an id and a key (BLAKE2b then `crypto_kdf`; the id cannot be run back to the code), seals the account key under that key with the call a passkey's PRF output uses, and leaves the sealed key at the server under the id (`POST /api/enrol/offer`, `routes/enrolment.ts`, table `device_enrolments`). **The code is never sent to the server**, which holds an id and ciphertext: opening it would take a guess of 2^80, and the offer lasts ten minutes. The new device (`pages/Pair.tsx`) asks with the id (`POST /api/enrol/request`) and is given a token only it holds; the owner's device, polling, sees what asked (its browser as it reported itself and the country, from where it was) and approves or refuses (`POST /api/enrol/decision`); only then can the asking browser collect the sealed key with a sign-in (`POST /api/enrol/claim`), once. **What keeps it safe:** one offer per account, a new one replaces the old; the first browser to ask takes it and no other can; making an offer and deciding need the password typed lately (`requireRecentAuth`), so a stolen cookie cannot let in a device; a leaked or photographed code is not enough, because the owner must approve the browser that asked and is told what it is; the offer is void when the password changes (`auth_version`) or the account goes; an unknown, used, expired or taken id answers the same; each public step is rate limited per source and for all; the account is mailed. **The sign-in is the third place a session may start** (`startSession`, guarded in `second-factor.test.ts`): it asks for no second factor because the approving device passed it, and it is **not** taken to have typed the password (`passwordTyped: false`), so the server's sensitive routes (account deletion, passkeys, another offer) ask for it on that device. **Residual:** the approval is a person looking at a browser name and a country, so a person tricked into approving a code an attacker showed them lets the attacker in (the card says to approve only what was started just now on a device in hand); on the device the records are open without the password having been typed, as after a passkey unlock, so the checks that are always satisfied there (the whole-archive export, a share link with scans) ask for nothing more; the new device holds the keys in memory only, so a reload asks for the password or a passkey. Tests: `server/src/__tests__/enrolment.test.ts`, `web/src/crypto/enrolment.test.ts`, and `check:app` (a third browser is let in).

**M-42 — Helping a person start shows fixed text and keeps only what was shown; the assistant can explain Spine from the same text.** **P8, P12.** The chat's welcome, the tips and the Get started list (`docs/architecture/ingestion.md` **Helping a person start**) call no model to be shown: the answers about Spine are fixed text in `core/src/help.ts`, written into a conversation by `POST /api/chat/help` (owner route, a 404 for a conversation that is not theirs, off with `SPINE_CHAT=off`) and stored like any message (**M-18**). What the app remembers is `guide_marks`: a key of the app's, how many times it was shown, when, and when it was put away; no medical text. It is a table of the records (`user_id` on every statement, saved to the vault sealed, synced between the owner's devices, in `REPLICATED`), listed in `SLICE_NEVER` so no share holds it, and not exported. `GET /api/guide` reads the owner's own uploads and share links to say how far they have got, and returns counts only. `explain_spine` is a read tool that returns that fixed text and nothing of the records; a recipient's agent is built without it. The texts make claims about the controls in this file (the server holds sealed pieces, a link's key is after the `#`, the relay stores nothing), so a change to one of those changes `help.ts` too; the sentences that name the server are in `hygiene.test.ts`'s reviewed list.

**M-40 — The web app is sealed at build: integrity on the page, and a list of every file's hash that anyone can compare with a build of their own.** **P1, P13.** `web/scripts/seal-build.mjs` ends `npm run build`: it puts `integrity="sha384-…"` on each script and stylesheet `index.html` loads, writes `hashes.txt` (SHA-256 of every file, sorted, `sha256sum -c` format, `index.html` included so the attributes are compared too) and fails the build if a built file names the folder it was built in. The same commit builds to the same files (`./scripts/check.sh repro`, a CI job, builds twice and compares), and `scripts/verify-build.mjs <site> [web/dist]` compares a site's files with its own list and with a build you made ([docs/verify-build.md](docs/verify-build.md)). **What it does not do:** an operator who serves a different page writes the attributes too, and the page cannot check itself, so the protection is a check someone runs from outside against the commit the operator names; a swap served only to one visitor is not seen by anyone else's check. The worker, the WebAssembly files and lazily loaded chunks are outside what a subresource-integrity attribute covers (the content security policy and `hashes.txt` are what cover them). The app shows the commit it was built from (written in at build time from git, so it is part of the hashes), and `/trust` explains the check to a reader who is not technical, including what it cannot promise; that page is in the bundle, not in the operator's editable legal texts. An official release (a `v*` tag, `.github/workflows/release.yml`) is built by GitHub's runner and its `hashes.txt` and tarball carry a signed attestation of the commit, which `scripts/deploy-check.sh` verifies against the build on the server; a personal deploy is unsigned and says `-dirty` if the tree was not clean. Requirements `TR-CLI-02`.

**M-39 — The demo: the app with the sample records, in the visitor's browser, with no account, and where the operator allows it a few files of the visitor's own.** **P1, P5, P8, P12.** Try the demo on the front page (`pages/Landing.tsx`) starts the device's core with no vault (`startDemo` in `web/src/core/core.worker.ts`, `startCore(undefined, {}, { shares: false })`) and loads the sample records into it through the restore path (`POST /api/demo`, answered by that core, no model). There is no account, session or vault behind it, so it creates nothing at the server and saves nothing anywhere: the records live in the worker's memory and are gone on a reload, when the visitor leaves (`device.lock`), or when they go to sign in or sign up (`NotInDemo` in `App.tsx` ends it first, so the device's core is never the demo's and an account's at once). The chat, translation, linking and embeddings are off in that core's settings, and there is no share host, so every owner share route answers 503 (`no_share_host`); the page leaves out Scan, Share links, Account and Read again (`NOT_IN_DEMO`, `inDemo={false}`). **Files of the visitor's own** are possible only with `SPINE_DEMO_UPLOADS=on` (default off) and a relay. Then `GET /api/demo-relay/config` (public) gives the core the same model settings an account's gets, with the chat, translation, linking and embeddings off and the demo's limits (`SPINE_DEMO_MAX_UPLOADS`, 3; `SPINE_DEMO_MAX_PAGES`, 5), and `POST /api/demo-relay/token` (public, 10 a minute per address) a ten-minute pass for `demo:<address>`, the address as an HMAC under the relay secret, so the relay learns no IP. The upload screen asks the visitor to agree to the health data in their files being processed before it offers a file (Art. 9(2)(a); nothing records the agreement, since nothing of the visitor is kept); `demo/limits.ts` then refuses a file past the limit (`demo_limit`) and any zip (`demo_zip`), and the pipeline reads, stores and keeps only the first pages of a file, the original cut to them too. **Those limits run in the visitor's browser and bind only a visitor who leaves the page alone.** The bound is the relay's count (`createRelay`'s `spend`): a demo call counts against its address (`SPINE_RELAY_DEMO_DAILY_CALLS`, 40 a day) and against every demo address together (`SPINE_RELAY_DEMO_TOTAL_DAILY_CALLS`, 400 a day), apart from accounts and shares; `0` allows none. An address is not a person (a shared network is one; a visitor with many addresses is many), so the total is the operator's real ceiling on what the demo costs. **Keeping them:** "Create an account to keep them" (or "Sign in to keep them" where registration is the operator's) takes the sample records out of the demo, exports what is left, and holds that zip in this browser's IndexedDB (`web/src/demo-carry.ts`), **unencrypted, on the visitor's own device**, for a day at most; once they are signed in with the records open, `DemoCarryOver` offers it, restores it through the ordinary upload (no model call), and deletes it once every file is restored, or when they discard it. Nobody else's records are involved, and the sample records are invented (`core/src/demo/records.ts`). `check:app` opens the demo with no account and sees the records, finds the camera not offered and nothing of the records at the server, and finds the demo gone after a reload; then it agrees, uploads a 7-page file and sees only its first 5 pages judged by the model, reaches the limit after three files, finds that none of it went to the vault, a share or the account routes, keeps them, signs in to a new account, adds them with no model call, and finds them there after a reload. **M-38 — Several devices on one account: records travel as sealed changes (syncing, after stage 5 of the encryption redesign).** **P1, P12.** The device holds the only readable copy, so it does not lose a change quietly: changes taken out of the log are kept until the vault has them, a failed save is retried and shown on the page, and locking or signing out over unsaved changes is refused unless the person chooses to lose them (`persist.ts` `unsent`, `boot.ts` `close`, tests in `persist.test.ts` and `boot.test.ts`). The device no longer saves its database as pieces of a file. Every write to a records table is noted by a trigger as a change of one row; a save turns the notes into **changes** (`{table, key, row or null, clock}`, a hybrid logical clock that sorts as text and is stamped on the server's time, `store/sync.ts` holds the rules for every store, `store/sqlite/changes.ts` is SQLite's part), seals them as one **segment** (`log` object, `core/persist.ts`) and never rewrites an object. Other devices find new segments by listing the vault, open them and apply them; **the newest change to a row wins** and a deletion is a change, so two devices that edit different rows keep both edits and two that edit one row agree on the later one. A device folds the segments it has applied into a **snapshot** (sealed `bundle` parts) named by the index (the one object written over, with the sequence number it was read at); the segments it folded are deleted and a device that was away loads the new snapshot over what it has (the same rule, so nothing is lost). What the server sees is what it saw before: object ids, kinds, sizes, sequence numbers and times; a segment's size and time say how much the person did and when. **Things that would make devices collide, and what is done**: keys that were the engine's counter (tags, the share log) are random numbers; the tags a new account starts with have the same key on every device; a tag or doctor made on two devices with the same name becomes one (the later arrival is kept as another name for the first and the rows that point at it are redirected); anything else that must be unique (a page's place in an upload) goes to the newer change. Rows that point at a row that never arrived or was deleted are removed after a merge. The search index is rebuilt from the records after changes arrive, and is not synced. **The change form names tables and columns, not an engine's pages**, and the share copy and the saved snapshot are the same form, so the store behind them can change. A vault of a kind this version does not know is refused and left untouched; there was no release with the earlier kind (a database file in pieces), so no conversion is kept. **The clock** is the server's, not the device's: every answer from the vault carries a `Date` header, the device takes its difference from its own clock (the reading of the quickest round trip, ignored if under five seconds) and stamps changes on that (`store/sync.ts`, `observeServerClock`), so a device with a wrong clock does not win edits it should not. **Residual**: a change is stamped when it was written, not when it was sent; the server's clock is trusted as the one all devices share (the offset follows a device whose clock is set or jumps; it is read right before changes are stamped; a write is never stamped later than the present; with the vault out of reach nothing is stamped), so what is left is a clock that steps while the device is out of reach, which can stamp a write too late by at most the time since it was written; a conflict between two edits to different fields of one row keeps both fields (each column goes to its newest write; a change names the columns it wrote, `Change.c`, and a change without it, as every change made before this was, is of the whole row), but a deletion against a concurrent edit is still decided for the whole row, and the columns an edit did not name come back with the values the editing device saw; a tag or doctor merged from two devices keeps two different keys for one name (each device redirects the other's); the owner's page does not refresh itself, it says another device made changes and offers a reload. Tested by `changes.test.ts` (two stores that write and exchange), `persist.test.ts` (segments, snapshots, a device that was away, files), `boot.test.ts` (starter tags once, a deleted tag stays deleted, an unknown vault kind refused) and `npm run check:app` (two browsers on one account remove different tags at the same time and both end with both removals).

**M-37 — The server serves no route that reads or writes a record (stage 5 of the encryption redesign).** **P1, P2, P12.** `server/src/index.ts` registers the account (`auth`, `totp`, `sessions`, `accounts`, `own-account`, `passkeys`), the vault, the relay's pass, the trust anchors (`trust-anchors`), the sealed shares (`shared`) and the address a recipient is given (`shareShellRoutes`: `GET /share/:id`, the app shell for a share that exists, a plain 410 page otherwise, no record read), and **nothing else**: the routes for documents, uploads, export, similarity, links, episodes, the sample records, chat, share links, tags, trends and doctors are not served, so the server neither accepts a record in plaintext nor writes originals or page images to its disk. Those route files stay in the repository because the device's core runs them (`web/src/core/boot.ts`) over the store it holds; the tests register them, so they hold the code the device runs. **No test enumerates what the real server registers**: the smoke test (`server/scripts/smoke-entrypoints.mjs`) starts the built server and checks one records route is not found (`GET /api/documents`), and `npm run check:app` works against the real server with them absent and finds no readable record text in its files; the test app of the server's tests registers more than the server does, so `isolation.test.ts` lists that app, not the server. A new route that handles a record goes in the device's core, never in `index.ts`. **The server's database has no table for a record**: it is made from `schema-accounts.ts` alone (the server's store is a type of its own, `AccountsStore`, made by `createAccountsStore` from `schema-accounts.ts`, so server code cannot reach a record: there is no repository to call. `server/src/store.ts` `useAccountsStore()` is called first by every entry point, and a process that does not has no store at all (`getAccountsStore()` fails); the device and the test setup files (`core/src/testing/use-records-store.ts`, `use-accounts-store.ts`) make the store that holds records. `boundary.test.ts` fails if the server's own code calls `getStore` or `createStore`), the repositories of records refuse to be used there, and `accounts-scope.test.ts` lists its tables; the device builds the accounts' and the records' schema (`schema-records.ts`). `npm run test:accounts` runs the account, session, vault, share and relay tests on that database with a test app that registers, by hand in `helpers/app.ts`, the routes `index.ts` registers and no route of a record; a route added to `index.ts` and not to that helper would not be tested there. **Left**: an older `spine.db` made with all the tables keeps them until it is deleted, and nothing has been audited. The backup (**S-11**) holds the vault's ciphertext.

**M-36 — Encrypted share links: a copy the server cannot open (stage 4 of the encryption redesign).** **P1, P2, P6, P7, P8, P12.** A link is no longer a row the server resolves at read time. The **owner's device** makes a copy of what the link shares, built in a store of its own and sent as **changes** (the form records travel in between devices, **M-38**; not a database file) (`store/sqlite/slice.ts`, an **allow-list**: each table names the columns that are copied, every other column stays empty, so the owner's e-mail, file names and paths, word boxes, doctors' professional codes, the app's reasons for a link between documents, notes the owner did not share, and any table not named are out; page text and snippets only if the recipient may ask questions, page images only if scans are allowed; `slice.test.ts` looks at every table of a copy built from records that include things that must stay out), seals it with XChaCha20-Poly1305 under a **random share key** (context bound to the share's id and the part's name, `core/share/keys.ts`), and sends it to the server (`PUT /api/shared/:id`, page images as numbered sealed files beside it). **The key is in the address after the `#`**, which a browser does not send to a server (a check in `npm run check:app` asserts no request the server saw contained it, and the page takes it out of the address bar after reading it). **Approval mode**: the address has no key. The visitor's browser makes an X25519 key pair and asks (`POST /api/shared/:id/access-request` with the public key); the owner's device collects the request (`GET /api/shared/events`, acknowledged once), and on approval **seals the share key to that public key** (libsodium sealed box) and sends only that (`POST /api/shared/requests/:rid/decision`); the visitor's browser polls, opens it with its private key (kept in that tab's session storage) and then reads the copy. A leaked link opens nothing; a copied link is useless in another browser. Changing the approval setting, or what a link holds, publishes again, and the approval setting changes the key, so an address handed out earlier stops opening. **The server** (`routes/shared.ts`, tables `shared_bundles`, `shared_requests`, `shared_opens`, files under `<data>/shares/<id>/`) stores sealed bytes and these facts: when it ends, whether it needs approval, sizes. It ends a share at its time (a read of an ended one, an hourly sweep, and at start) and on revoke by **deleting the files and forgetting every wrapped key** immediately; the row stays 30 days so a late visitor is told it ended. **A page already open on the link** holds the copy it opened, and what it showed was seen; it asks the server again every half minute and when the tab comes back to the front, and once the link has ended it closes the copy (its core stops, the key is forgotten) and says so, so nothing more is read, translated or asked from it. A page altered to skip that check keeps what it already decrypted, which no revocation can take back, and can use the model only until its last pass ends. Limits: `SPINE_SHARE_MAX_MB` (100 a part), `SPINE_SHARE_MAX_TOTAL_MB` (1024), `SPINE_SHARE_MAX_LIVE` (50); a share lasts at most 31 days. The public routes are known only by the random id (36 characters), rate limited, and answer with metadata and sealed bytes; access requests are limited per source and per link, at most five wait at once, a note is cut and cleaned. **What visitors did** reaches the owner without the server learning what was read: the recipient's browser says it opened the link or a document (`POST /api/shared/:id/opened`, the id inside the sealed copy), the server keeps the time and the country (from the address, which it does not keep) until the owner's device collects it, and the owner's own records (not the server's) hold the log. A recipient who does not report is not logged: the log says what browsers said. **The recipient reads with the same route code** the server used (`publicShareRoutes`, run on the device by `LocalApp` over the copy, `core/boot-share.ts`), so scope and the rules of what is shown are unchanged (approval is the key handshake above, not a route); translations and questions go through the relay with a **pass for that share only** (`POST /api/shared/:id/relay-token`, two minutes and its own end time at most, counted against the share, `share:<id>` as the account; short because the relay cannot ask whether the link was revoked, so a pass already handed out works until it ends, and a revoked or ended link is refused the next one). **What a recipient holds**: the whole copy, in memory, readable with the browser's tools: the copy is the access, so it holds only what the link shares. **Live**: a link follows the owner's records for as long as it lasts. After the records change, a moment later (15 s) the owner's device builds each live link's copy again and sends it only if it would hold something different (a keyed hash of its content is kept beside the link's key, `share_link_keys.copy_digest`; `POST /api/share-links/refresh`), under the key it was made with, so a deleted document leaves a copy within about twenty seconds of a device that is open. A device that is closed does not refresh: until one is opened, a copy shows what it last held. A link that shares nothing any more is answered as not usable (it fails closed). **Not yet / residual**: the owner's device must be unlocked to approve a request and the mail only says someone asked; the log depends on the recipient's browser reporting; Anthropic cannot be used for a recipient's questions; nothing has been audited. (The earlier server-side share routes and tables are gone, **M-37**.) The server's own tests (`shared.test.ts`, `share-host.test.ts`, `slice.test.ts`, `isolation.test.ts`'s public-route list) and `npm run check:app` (owner makes a link, a stranger with no account opens it, the owner sees it was opened, revoke, approval) hold it.

**M-35 — The relay: where a device's model calls go (stage 2 of the encryption redesign).** **P1, P5, P8, P13.** A device cannot hold Spine's credential, so its model calls (reading a page, extraction, summaries, translation, linking, grouping, chat, embeddings) go to `server/src/relay/` with a pass from the Spine server. **The protocol is neutral** (`relay/protocol.ts`): the device names a task from `llm/tasks.ts` and sends LangChain messages (`POST /v1/task/<task>`; the agent also gets the tools' declarations and may stream, one JSON line a piece) or texts to embed (`POST /v1/embed`), and the relay runs them through its provider adapters (`server/src/llm/adapters/`, picked by the relay's own `SPINE_LLM_PROVIDER`: Vertex or Anthropic today), so a provider is one adapter file and the device never knows which answered. **The pass**: `GET /api/relay/token` (signed-in accounts only, `routes/relay.ts`) gives an HS256 token (the JWT shape, `relay/token.ts`, no library) for the account's id, valid ten minutes, signed with `SPINE_RELAY_SECRET` (at least 32 characters, shared with the relay and nothing else); `GET /api/relay/config` gives the device the settings it needs to behave as the server does (the `SPINE_LLM_MODEL(S)`, parser and feature switches, from an allow-list that holds nothing secret; the provider is set to `relay` and the endpoint to the relay's host; nothing of the real provider's project or region), and a 503 `no_relay` when the instance has none. **What the relay checks** (`relay/relay.ts`, `relay.test.ts`): a valid unexpired pass (401), a path that is one of the tasks or `/v1/embed` (404 for anything else), no query (400), a body that parses against the protocol's schema with message types human, ai, system or tool only (400), a model the relay was configured to offer (400), a body under 32 MB (413), and the account's daily allowance of calls, `SPINE_RELAY_DAILY_CALLS` (default 500; 429), counted in the `usage` repository of the store the relay is configured with (`SPINE_STORE`, `DATA_DIR`/`SPINE_DB_PATH`, chosen as the model provider is; table `model_usage`, a number a day per account), so it survives a restart and is shared by instances that reach the same store; with `SPINE_DB_PATH=:memory:`, the relay image's default, it is per process and one instance gives an exact count. A tool the device names is a declaration handed to the model, never run by the relay. Nothing the device sent besides the messages, its cookies and address included, reaches the provider. A Google API key in the relay's environment stops the Vertex adapter at start (the same residency rule as **M-8**). **What it does not do**: it **stores nothing and logs no content**: one line a call with the task, model, status, request size and time; a provider's own error text, which may quote what was sent, is not passed back (a refusal by the model is said as `blocked`). A test fails if a content word reaches a log line, and another if `relay.ts` imports anything but the protocol, the token check, the task and embedder types, the `UsageRepository` type, LangChain's message and chat-model types and Node's HTTP module. Cross-origin calls are allowed only from `SPINE_RELAY_ORIGIN`, and the page's content security policy names the relay (`connect-src 'self' <SPINE_RELAY_URL>`; `img-src` gained `blob:` for pictures held on the device). **What it can see**: everything that passes through it, in plaintext, because it ends the TLS connection; it is the one place outside the browser that does, together with the provider. Product text therefore says it does not store or log content, and never that it cannot see it; an enclave relay with attestation is a later step and is not built. A failure of the relay's operator (or of its provider credential) exposes what is in flight, not what is stored. **Device side**: `llm/adapters/relay.ts` (the `relay` provider: one client per task, and a chat model for the agent that sends each call to the relay), `embedding/adapters/relay.ts`, and `web/src/core/native/relay-auth.ts` (fetches and reuses passes; hooks set by the device). **Beside the server** (Compose's `relay` profile, `systemd/spine-relay.service`, `docs/relay.md`): the relay reads the server's `.env` for the settings they share and `relay.env` for the provider's credential, which the server process is never given; `SESSION_SECRET` and `BREVO_API_KEY` are removed from the relay's environment; it listens on loopback (`SPINE_RELAY_HOST`) behind its own hostname, and keeps its count in a file of its own. That separates two processes, not two operators: whoever runs the machine runs both the server that keeps the sealed vault and the relay that sees plaintext in flight. **Not yet**: the relay's quotas are shared only through a store every instance reaches (the SQLite adapter is a file; no networked adapter exists), the model-call budget (`SPINE_LLM_DAILY_CALLS`) is counted per device, and the provider's zero-retention checklist in the requirements is the operator's to do in the provider's console (`docs/relay.md`). `npm run check:app` runs a page against the real relay code with a stand-in model (`server/src/testing/stand-in.ts`), or with `SPINE_CHECK_REAL=1` against the configured provider on invented records.

**M-34 — The vault: keys and records the server cannot read (stage 1a of the encryption redesign).** **P1, P2, P3, P13.** `docs/crypto-design.md` is the plan and `docs/key-hierarchy.md` the public design; this is what is built. **On the device** (`web/src/crypto/`, libsodium): Argon2id over the master password with the account's random salt (64 MiB, 3 passes by default; the server refuses a cost under the OWASP minimum, `vault-keys.ts`), then two separate subkeys: the **master key**, which never leaves the device, and an **authentication value**, which is sent *in place of the password* and hashed again by the server's own argon2id, so the existing login, rate limits, second factor, passkey, reauth and session code are unchanged and the server cannot go from what it holds to the master key. A random **account key** is sealed under the master key and again under the **recovery key**; an X25519 pair has its private half sealed under the account key; a **profile key** is sealed under the account key; each object has a **data key** sealed under its profile key. Sealing is XChaCha20-Poly1305 with a random nonce and the object's kind and id (or the key's purpose) bound in as associated data, so a sealed value cannot be moved elsewhere and still open (`seal.ts`, tested). The **recovery kit** is 256 bits written as 56 base-32 characters (52 and a four-character check, so a typing error is caught), shown once before anything is sent, printable, and replaceable from the account page (the old one stops working). **On the server**: `vault_keys` (the salt, the cost, the account key sealed twice, the public key, the sealed private key, a change counter) and `vault_objects` (opaque id, owner, profile id, a coarse kind, change number, size, the sealed data key, a tombstone flag), with the ciphertext in `<data>/vault/<user>/<id>` (`vault-files.ts`, ids held to a safe alphabet because they reach the file system). `routes/vault.ts`: `POST /api/auth/kdf` (public, rate limited; an address with no vault gets a salt made from the address and `SESSION_SECRET`, so it does not say which addresses have accounts, except that an account made before the vault answers `vault: false`), `GET`/`PUT /api/vault/keys` (the first needs a session, making a vault needs the password typed lately and replaces the credential the server knew), `POST /api/vault/keys/rewrap` (a new master password or kit: the same account key under new wrappings, mailed, other sign-ins ended), and `GET`/`PUT`/`DELETE /api/vault/objects[/:id]` with optimistic concurrency (a write names the change number it last saw, 409 otherwise), a tombstone so other devices learn of a deletion, `SPINE_VAULT_MAX_MB` (5120) for an account and `SPINE_VAULT_MAX_OBJECT_MB` (100) for one object. **Sign-up** sends the derived value and the keys (`routes/accounts.ts`), no password and no policy check on the server; the master password's policy runs on the device (`password-policy.ts`, the rule the server used to apply). **Reset by email** can set a new credential but cannot reach the records: `POST /api/auth/reset/keys` hands a link holder the recovery-wrapped key (sealed, no use without the kit; the link is not spent), the device opens it with the kit and seals the same account key under the new password, and `POST /api/auth/reset` takes the new credential and keys; **without the kit** the only way on is `erase: true`, which removes every object and starts an empty vault, and the page says so first. A password cannot be set by reset or by the operator's `set-password` on an account that has a vault. The CSP gained `'wasm-unsafe-eval'` for libsodium's WebAssembly. **Not yet**: the unlocked keys live in page memory and are forgotten on reload (the page then asks for the master password, or a passkey that can open the vault, **M-33**), an account without a vault (one the operator made with `create-user`) signs in once with the password it was given and makes its vault then (the form sends the password as the credential for such an account; this stays, it is how an operator-made account starts), and nothing has been audited. `npm run check:app` drives the whole of it in a real browser. `vault.test.ts` (server) and `web/src/crypto/*.test.ts`, with `web/src/e2e/vault.e2e.test.ts` driving the device's code against the real routes, hold all of it.

**M-28 — A recipient sees the documents connected to a shared document, but only shared ones, only confirmed links, and nothing about how they were made.** **P2, P7, P8, P12.** `GET /api/share/:link/documents/:id/connections` goes through `openLink` like every share data route (live link, scope resolved or nothing served) and answers 404 for a document the link does not share. It returns two things. **Connected documents** (the owner's care chain, renamed in the interface): links in state `confirmed` whose *both* ends are in `listForShare(link)`; the walk (`sharedChainOf`) does not step through a document that is not shared, so a chain A, hidden, C shows nothing; it returns nodes (id, title, type, date, provider, as the list already shows) and edges as direction and kind only. A suggestion, a dismissed link, who made a link, the model's one-sentence reason and a confidence are never sent. **Similar documents**: `relatedTo(..., within)` with the shared ids applied *before* ranking, so a test or doctor in common, or closeness in meaning, ranks only shared documents; each result carries the fields the list already shows (id, title, type, date, provider) and reasons that are only a kind: the names of the shared tests or doctors in common (both documents already show them to the recipient), or "meaning"; no score and no tags. No card and no model call is involved beyond what already exists: the comparison is in memory, in the recipient's browser, over the vectors of the shared documents that the copy holds. **Writes nothing** (R-4; `share-connections.test.ts` compares the owner's links before and after). **What it does not do**: it does not hide that two shared documents are connected (that is the point); it does not show the owner that a link exists to something not shared; it adds no way for a recipient to create or confirm a link. The route runs in the recipient's browser over the copy; the tests register it on the server's test app, where it is on the public allow-list of `isolation.test.ts` with its reason. The recipient's chat is unchanged: its agent has no care-chain tool (**M-20**). **Naming**: the interface says "Connected documents" for confirmed links and "Similar documents" for the computed list; the code and this document keep "care chain" and "related" for the same things.

**M-27 — A sign-in is a row the owner can see and end; the cookie alone is not enough.** **P13.** Closes **S-33**. The cookie session's state is in the accounts database (**S-16**), and `user_sessions` (`user_id`, created, last seen, the browser's user agent and address as the connection reported them, which prove nothing) is what makes it valid: `authenticate` looks the row up on every request and signs the request out if it is gone, past the idle limit (24 hours, `SPINE_SESSION_IDLE_HOURS`) or past the absolute one (14 days, `SPINE_SESSION_DAYS`; values above 30 days and 90 days are cut, a bad value gives the default, never a longer session). `startSession` is the one function that assigns `session.userId`, called only by the two login steps (`second-factor.test.ts` fails on any other caller); logging out removes the row. The list (`GET /api/auth/sessions`) is the owner's, never carries a cookie or a token (a row's id is a random value that only names it), and `DELETE /api/auth/sessions/:id` and `POST /api/auth/sessions/end-others` end them; another user's row is a 404. A password change, a reset, and turning two-factor on or off end every other sign-in. **Asking again**: `POST /api/auth/reauth` takes the password and, with two-factor on, a current code; it limits guesses per user (5 in ten minutes) and per source, and sets a timestamp in the session. Within ten minutes of that (a fresh sign-in counts), the routes behind `requireRecentAuth` go through (account deletion, passkey add and remove, making a vault, changing a credential); otherwise they answer 403 `reauth_required` and the page opens a dialog and repeats the request. `GET /api/export` and a share link with `include_scans` are behind it too in the code, but they run on the device, where the check is always satisfied because the vault is open (`useRequestAuth` in `boot.ts`): a stolen cookie cannot run them, since without the master password there is no core to run them in, but an unlocked browser tab can. **Telling the owner** (only with a mailer, after the response, no clinical words, no address): a sign-in from a browser the account has not used (a random cookie, kept as `sha256` in `user_devices`; the first sign-in of an account tells no one), a password change or a replaced recovery kit, two-factor turned on or off, and a passkey added, removed or allowed to open the records, which is what makes **S-22** (an attacker enrolling their own authenticator) noticeable. What it does not do: it does not make a stolen cookie useless, only short-lived and visible (**S-33** residual).

**M-1 — Owner-scoped store layer.** **P12.** Every user-owned table has a `user_id`, and every statement in `store/sqlite/` filters by it. This is the device's store (and the tests'); the server's store holds accounts only (**M-37**). Handlers cannot write queries. There is no `find(id)` without a user, and a method called with no acting user throws.

What a method does with a record the caller does not own: a read returns nothing, an update or delete changes nothing, and a create that names such a record throws and inserts nothing. Routes check first and answer 404, never 403, so a record cannot be probed for.

Five exceptions, enumerated in `store/types.ts` so a sixth has to be argued for: `shareLinks.findLive`, `shareLinks.createRequest` and `listForShare` (scoped by the link's owner, never by a session); `logAccess` (how the owner's device records an open the server reported); `shared.*` (the public side of a sealed share, scoped by the share's random id and answering only metadata and sealed bytes); `maintenance.*` (boot-time work); and `users.*` (the identity layer: login must find a user before there is an acting user).

`__tests__/isolation.test.ts` runs as a second user against the first user's data across every route its test app registers and the methods of the upload, document, field, tag, page, share link and result repositories (the doctor, episode, link, chat, translation and embedding repositories are not listed in it), and fails when the search filter or the share ownership check is removed. Removing only the inner tag-owner check in the tag-scoped share query does *not* fail it, because the outer `d.user_id` already excludes other users' documents; that one is defence in depth.

**M-2 — Owner-aware full-text search.** The FTS index stays shared; results are filtered by joining back to `documents.user_id`. The index now also holds page text, values and doctor names (the most sensitive text in the system), so what makes it safe is that each row is built only from the owning user's rows and is only reachable through that join; a test searches for another user's page text, value and doctor name and finds nothing. Typed text is quoted, never passed as query syntax. Tested.

**M-3 — Credential storage.** **P13.** argon2id, 19 MiB / 2 passes / 1 lane (the OWASP minimum), per-hash salt, 12–256 characters. About 30 ms per hash on a laptop-class CPU; not yet measured on a Pi. An unknown email runs a dummy verification so it is neither faster nor different in answer.

**M-4 — Session invalidation on password change.** **P13.** `users.auth_version` is bumped on a change; a session carries the value it was issued under and is refused once it no longer matches. Every request re-resolves its session, so this takes effect on the next request. Login also issues a new session id.

**M-5 — Share creation verifies ownership of the scope.** A `document_ids` link naming a document the creator does not own is rejected at creation, with one message for "not yours" and "does not exist".

**M-6 — Login and registration throttling.** **P5.** Login: per source and instance-wide (S-2). Signup, resend, forgot and reset: per source **and per email address**, so they cannot be used to flood an inbox; the address limit is `rate-limit.ts`, because the Fastify plugin cannot stack two limiters on one route.

Signup is `SPINE_REGISTRATION=open` or `approval` (**M-44**), default `operator`; `open` with no mailer fails at startup (**P3**). Verification is mandatory: an unverified account gets no session, and the right password before confirming answers 403 with a code the page uses to offer a new link. A taken address is answered exactly like a new one — same body, same status, no mail — and its password is not touched. **Residual:** a new address does a few more database writes than a taken one, so the timing is close but not identical; the mail itself is sent after the response, which is the large part.

**M-7 — Explicit opt-in for image egress.** **P8.** `SPINE_PARSER` defaults to `text`, which sends nothing (as does `ocr`). The parsers that send page images, `multimodal` and `hybrid`, need a **second, separate switch**, `SPINE_MULTIMODAL_ENABLED=true`, and are refused at startup without it: in `config.ts`, and again in `createParser`, which decides whether an image can leave and does not rely on its caller. The second switch alone does nothing, so picking a parser never turns egress on by implication. Photos chosen together and made into one upload (`upload-photos`) follow the same rule: refused as a whole, with nothing kept, unless the switch is on, each is checked by its bytes, at most 40 are taken (the rest of the request is drained, not saved), and the temporary copies are removed whatever happens.

Signature stamps (`ingestion/signatures.ts`) are a second, smaller image egress under the same switch: each document's last page contributes at most four small pictures that look like a stamp (a doctor's name, specialty and code; no clinical content), never the page; nothing runs with the switch off, and a test asserts that no image is sent then. Each send is logged with the number of images.

The server logs, once at start, the settings it gives devices (`model settings given to devices`: provider, model, endpoint, embeddings, the parser and whether image egress is on); a device logs each batch of stamp images it sends and every page's route and the figures behind it (`page routed`) in the browser's console. In `hybrid`, an image is sent only for a page with **no text layer** that **local OCR could not read confidently**, never a page that has a text layer (a test asserts it). There is no LLM screening step: looking at an image to decide whether to send it is the same egress as sending it.

**A second route: reading again.** "Read page with AI" (on the document page) sends only that page's image through the same model parser, so the same switch applies and nothing new decides whether an image can leave. It acts only on the caller's own pages (a page of another upload, or another user's, is refused like one that does not exist), takes at most 200 a request, runs one reading per upload at a time, and asks first, naming the number of images and the destination. A page the model cannot read changes nothing. "Read whole document" (the same route with `strategy: "configured"`) reads a document's pages with the parser the operator configured, so it sends an image only when that parser does (`hybrid` for pages still without text, `multimodal` for every page) or when the upload is a photo, and the switch is required exactly then; with `text` or `ocr` it sends only the page text for extraction.

**Which provider matters.** Images go to `SPINE_LLM_PROVIDER`. The Anthropic adapter has no EU-only processing commitment, so a deployment with a residency requirement should enable this only on Vertex at an `eu` endpoint (M-8). The software cannot know your deployment has such a requirement, so it does not stop you.

The local screening ran on real files with real Tesseract and poppler.

**M-8 — Residency enforcement in the provider adapter.** **P8. Enforced as configuration.** The Vertex adapter (the relay's) requires `SPINE_LLM_ENDPOINT`, `SPINE_LLM_REGION` and `SPINE_LLM_PROJECT` to be stated — nothing defaults, so an instance cannot reach a global endpoint by omission — and the relay logs its resolved provider, model, endpoint and region once at startup (`relay ready`, `relay/serve.ts`; not run against a live relay) (the server logs the settings it gives devices).

The control that does the work: **construction fails if `GOOGLE_API_KEY`, `GEMINI_API_KEY` or `GOOGLE_GENAI_API_KEY` is present at all.** Reproduced against the installed `@langchain/google-vertexai`: with one set and an EU endpoint and region configured, the request goes to `https://aiplatform.googleapis.com/v1/publishers/google/models/<model>:generateContent` — the global host, with the configured endpoint dropped and no region in the path. In `@langchain/google-common`, an API key makes `connection.js` choose the "Express" platform, which hardcodes the global host. The same behaviour is reported for `@google/genai` ([gemini-cli#27984](https://github.com/google-gemini/gemini-cli/issues/27984)), so it is a class of bug across Google's client libraries. API keys are also blocked on standard Vertex endpoints and unsupported for Claude's `rawPredict`, so there is no legitimate reason for one to be set here.

**Deliberately not done:** asserting the shape of the outgoing URL. That encodes Google's URL scheme, means nothing for an Azure or Bedrock endpoint, and is bypassed by the API-key path, which is why the refusal above is the real control. Verify residency against the provider's request logs on first deployment; that works for any provider.

**M-9 — Per-user paths for sealed files.** `data/vault/<user>/` (`vault-files.ts`), so a filesystem mistake cannot cross users as easily as a query mistake. The server no longer writes originals (`data/originals/<user>/<year>/` was the earlier path); deleting an account removes the vault and shares, and does not look for an `originals` directory an older build left.

**M-10 — A migration runner: not needed yet.** `CREATE TABLE IF NOT EXISTS` adds new tables to an existing database but cannot add a column to an existing table. Multi-user and verification changed existing tables while the archive held no records, so they edited the schema files (`schema-accounts.ts`, `schema-records.ts`) directly; a database of an older shape is **refused at startup**, with a message saying how many uploads and documents it holds and whether it is safe to delete. TOTP (M-12) added new tables only, so it did not need a change. Document titles added a column to `documents`, again while the archive held no records; a database without it is refused the same way. **A change to an existing table that is not purely additive needs a runner first**, or an empty database. A new column with a default is added in place when the database is opened (`addColumnsInPlace`; `pages.hidden` was the first), and tested against a database made without it.

**M-11 — Account recovery and verification.**

- The token is a capability: 256 bits of CSPRNG output, only its **sha256 stored** (**P6**), spent by one atomic `UPDATE` so two simultaneous requests cannot both succeed. A newer one replaces an older one. Verification lasts 24 hours, reset one hour.
- It travels in the URL **fragment**, never sent to the server, so it stays out of nginx's access log and the Referer header; the page removes it from the address bar. It is spent by a `POST`, so a mail scanner following links cannot spend it.
- Using a reset link ends **all** the user's sessions (**P13**, as M-4) and confirms the address. It does not bypass two-factor (M-12).
- Requests answer identically whether or not the address has an account, and are rate limited (**P5**).
- A send failure is logged and the page says to request another link. It is not shown as an error, because an error only for addresses that exist would be a way to find them.
- The mail carries no medical content (**P8**): an address and a link, no attachment field, plain subjects, and a test that fails on clinical wording.
- Without a mailer, `npm run cli -- reset-link <email>` prints the same single-use link.

**M-12 — Second factor (TOTP).** **P13.** Optional per user (S-20).

- **Algorithm:** RFC 6238 — HMAC-SHA1, 6 digits, 30-second steps, written with `node:crypto` and checked against the RFC's test vectors. SHA-1 is what authenticator apps support, and HMAC-SHA1 is not weakened by SHA-1's collision problems. A code is accepted one step either side of now, for clock drift.
- **Seed:** 20 random bytes, stored **encrypted** (AES-256-GCM, key derived from `SESSION_SECRET` with HKDF, the user id as associated data, so a row copied to another account does not decrypt) — see S-21. Shown once, as a QR code and as text.
- **Enrolling** takes the password, then a first valid code, which proves the app works before two-factor is switched on. Until then the seed is inert and login is unchanged. Anyone holding the password can enrol (S-22).
- **Login is two steps.** The right password does **not** create a session for a user with two-factor: it starts a *pending* login in the session (user id, `auth_version`, five-minute expiry). Only a valid code turns that into a session, with a fresh id. As with an unverified address, only someone holding the right password learns the account has two-factor.
- **Guessing is throttled (P5).** Six digits is a million possibilities, so the second step is limited per source, **per user** (5 attempts per ten minutes, whatever the source), and the pending login is dropped after five wrong tries.
- **No replay.** The last accepted time step is stored; a code for that step or earlier is refused, so a code seen over a shoulder or in a log cannot be used again.
- **Recovery codes:** ten, shown once when enabled and when regenerated; 10 characters from a 32-letter alphabet (50 bits), **sha256 stored** (**P6**), each spent by one atomic `UPDATE`. They are accepted at the second step in place of a code, and using one is logged. Regenerating replaces all ten.
- **Changing it needs proof.** Disabling or regenerating codes takes the password *and* a current code. Enabling and disabling both bump `auth_version`, ending the user's other sessions (**P13**).
- **Lost phone and lost codes:** `npm run cli -- disable-2fa <email>`, run by the operator. That makes the operator the recovery path, which is the trust the operator already has.
- Deleting a user (S-18) removes the seed and the codes.


**M-13 — Translation is egress of text, and a public route can trigger it.** **P8.** A document is translated into the reader's language on demand: its title, summary, extracted field values (and labels the app has no name for), measurement names, doctors' specialties and the owner's notes go to the configured inference provider, as text, and the result is kept in `document_translations`, keyed by a digest of exactly what was sent, so an edit or a re-extraction changes the digest and the old translation is never served (moving a page changes it through the re-extraction the move asks for, not by itself). Nothing is sent for a document already in the reader's language, and `SPINE_TRANSLATION=off` stops the path: the endpoints answer `off` and the interface shows the original. Two things are new in the threat model. The owner's **notes** leave the device here (when this was written they went nowhere else; since then a re-reading, the links search and the chat send them too, **M-16**, **M-18**), which is why translation is listed in [ARCHITECTURE.md](ARCHITECTURE.md) and is on by default only because the text already goes to the same provider. And **a share recipient can cause a model call**: `GET /api/share/:link/documents/:id/translation` answers in the recipient's browser, from the copy. It is bounded like every share route: the link must resolve to a live link and the document to its scope (anything else is the same 404, **P2**), the language must be one of four (`ro`, `en`, `fr`, `de`), a document is translated **once per language** whatever the number of requests (concurrent ones share one call), the translation runs in the recipient's browser, so what bounds the cost is the relay's daily allowance for that share (**M-20**), and it **writes nothing to the owner's records**: the language the model finds for a document with none is recorded only when the owner opens it (**R-4**). The worst a holder of a link can do is have each document in scope translated into each of four languages, once. Translations are deleted with their document, with an upload's derived data and with the account (`OWNED_TABLES`). Server error messages stay English: only the web interface and the stored details are translated.

**M-14 — Import takes a file the user was given.** **P12.** A zip uploaded to the upload route is untrusted input twice: as an archive and as a Spine export. As an archive: it is opened with the device's zip reader (`fflate`; `yauzl` in the Node tests) and entries are read **by name and never extracted to a path the zip chooses**, so `../../x` is only a name; every entry is capped (200 MB each, 4 GB in all, 500 entries for a plain zip): the Node tests' reader counts the bytes as they arrive, and the device's refuses an entry whose declared size is over the cap and inflates it into a buffer of that declared size (checked with a zip that declared 10 bytes for 60 MB: the entry came out cut at 10 bytes, not larger), so a small zip cannot expand without limit; the device holds the whole zip in memory while it reads it, so what a browser can open is bounded by its memory long before 4 GB; the zip itself is not kept; and the work a zip brings (restoring or reading each file) is queued two at a time, so a request with hundreds of files cannot start hundreds of rendering, OCR and model jobs at once (**R-1**). As an export: `manifest.json` (at most 64 MB, parsed into memory) is checked with zod, with a length or count limit on every string and list, dates in the app's own form, a cap on documents and pages in all, and a test name lower-cased, before anything is used, and a manifest of an unknown version is refused. **Nothing in it can name an owner, an id or a path**: every id is made on import, rows are written for the acting user through the store (**P12**), and the stored file is written to a path the server makes. The restored pages are made from the *file* with the device's renderer (PDF.js and canvas) as for any upload (**S-24**); the manifest supplies text, boxes and details, and a manifest that does not fit its file (a different page count, pages or ranges that do not exist) fails the whole file in one rolled-back transaction. Restoring calls no model and sends nothing off the host (**P8**). Exporting is the owner's own data, built on the owner's device as it is sent (no route on the server makes one); it never includes share links or their tokens, other users' rows, server paths or ids (a test asserts the owner's id and the data directory are absent from the manifest). The whole archive also carries the care-chain **links**, and an import is untrusted for them like the rest: a link names documents only by position in the manifest, the schema refuses a position that is not there, every id a link ends up with is one this restore made for this user, and the write goes through the store as them (`links.restore` checks both documents are theirs), so a manifest cannot point a link at anyone else's document. A restored link keeps the state the file gives it, as every other field of an export does: the file is the owner's own data, and restoring it does not itself confirm or dismiss anything. Version 2 of the manifest also carries what the owner keeps beside the documents (what was edited and removed, each doctor's source and printed code, the doctors' directory, every tag, merged test names, and the answers to "are these the same?"), under the same rules: every list is bounded, a doctor is named by position in `people` and the schema refuses a position that is not there, the headline columns an edit may name are a fixed enum, an answer names doctors by position and tags by name (never by an id), and everything is written for the acting user through the store; versions 1 and 2 are still read (version 3 adds the episodes and carries the doctors' directory whole), and a version above 3 is refused.

## Enforcement checklist

For any change touching routing, auth, share links, storage, providers or static serving:

- [ ] Does a new route land in a file with `requireAuth`? If public, is it justified here and on the allow-list in `isolation.test.ts`? (**P1**)
- [ ] Does a new table carry `user_id`, and does every statement on it filter by it? Does a new repository method take the acting user's id first? Is it inside `store/sqlite/`, the only place SQL or a driver import belongs? (**P12**)
- [ ] Is a new method exempt from taking a user id? Then it must be one of the five exceptions in `store/types.ts`, argued for there, not a fifth added quietly.
- [ ] Does a new query list explicit columns? `SELECT *` on a table with `user_id` sends it to the client, including to share recipients. (**S-8**)
- [ ] Can any share-link path return documents without a fully resolved scope? (**P2**) Does scope creation verify the creator owns everything it names? (**M-5**)
- [ ] Does any config read a secret with a `??` fallback, or ship a default an operator would not knowingly choose? (**P3**)
- [ ] Is medical content served by anything other than an authenticated handler — static mount, redirect, signed URL? (**P4**)
- [ ] Does a new nginx `location` set any `add_header`? If so it inherits none from the server level and must repeat the security headers. (**S-14**)
- [ ] Is every new unauthenticated endpoint rate limited at nginx or Fastify? (**P5**) The Fastify plugin applies only its first hook per request, so a second limit on one route has to be enforced separately (see S-2).
- [ ] Does anything new leave the host? Is it listed in [ARCHITECTURE.md](ARCHITECTURE.md), opt-in, and disableable? Do page images leave only through `readPage`, on a path that needs both switches — including any new button that triggers it? Can a public route cause a model call, and is it bounded (by language, by once-per-document caching and by a rate limit)? (**P8**, **M-7**, **M-13**)
- [ ] Does anything send text to a model that was not sent before (a new card, a new field)? Is it in the egress table and behind a switch? (**M-15**)
- [ ] Does anything put document content in front of a model on the owner's request (a question, a summary)? Is it chosen from the shown documents, sized, counted against the relay's allowance, owner only (or, for a share recipient, held to the link: **M-20**), and in the egress table? Does a new agent tool take a label rather than an id, read only through the store as the signed-in user, and never write? (**M-18**)
- [ ] Does a new query list the owner's documents? Does it use the one visibility fragment, so an unconfirmed upload or a set-aside document cannot leak into it, a share or a model call? (**M-17**)
- [ ] Does anything new write a record because a model said so? Is it only a proposal the owner decides on, and does code refuse what the data contradicts? (**M-16**)
- [ ] Does a request start work per item (files in a zip, documents in a list)? Is it queued and capped? (**R-1**)
- [ ] Does a public route write anything? It must not. (**R-4**)
- [ ] Does anything read a file or manifest a user was given? Is it read by name and never written to a path from it, size-capped as it is read, schema-checked, and does it mint every id itself? (**M-14**)
- [ ] Can a provider adapter fall back to a global endpoint, and is residency being asserted from a URL's shape rather than verified against request logs? (**P8**, **M-8**)
- [ ] Does anything outside `server/src/llm/adapters/` import a vendor package, or `core/src` a native library or a program? That is a review failure (`boundary.test.ts` fails first).
- [ ] Does anything widen the listening surface — a new bind address, an interface opened on a unit, a proxy header trusted from somewhere other than nginx? (**P9**, **S-13**)
- [ ] Does anything put document text, a summary, a field or an attachment into an email, or a subject or body that says anything clinical? (**P8**)
- [ ] Does a new way to obtain a session — login, reset, verification, any future SSO — go through the second factor for a user who has one? A path that issues a session directly is a bypass. (**M-12**)
- [ ] Is a limit keyed on `req.ip`? Then `trustProxy` must name only the proxy and nginx must overwrite `X-Forwarded-For`, or a client chooses its own key. (**S-31**)
- [ ] Does `npm audit --omit=dev` report anything high or critical? Does a dependency bump, or a new package, change what the lockfile resolves? (**S-32**)
- [ ] Does a new way of reading or exporting data in bulk, or of changing a credential, a second factor or a share's exposure, rely on the session alone? Should it ask for the password again? (**S-33**, **S-29**)
- [ ] Does a new model call count against the relay's daily allowance and the core's ceiling? (**S-35**)
- [ ] Does model output reach the page as anything other than text (an image, a link to another host, HTML)? The CSP stops the image, not the link a person clicks. (**M-18**)
- [ ] Does a share route return anything derived from links or similarity? Is every document in it in `listForShare(link)` *before* ranking or walking, and does it carry no reason, score, source or state? (**M-28**)
- [ ] Do tests drive the control through the real handler, with assertions that can actually fail? (**P10**)

## Operational response

**A share link is leaked or sent to the wrong person.** Revoke it from the Share Links page: the sealed copy is deleted on the server, so it takes effect at once, and anyone who already opened it may have copied what they saw. The link's page lists each time it was opened and from which country (**M-36**); the owner's device must be open to see that list and to revoke.

**A user's account may be compromised.** From the server:

1. Have the person change their password on a signed-in device (which re-wraps their keys and ends their other sessions, **M-4**), or, if they cannot sign in, send `npm run cli -- reset-link <email>` and have them use their recovery kit. `set-password` refuses an account that has a vault: a password chosen on the server would be a credential the person's device never sends. A reset without the recovery kit makes an empty vault, and says so first (docs/crypto-design.md). Someone who held the old master password could already have read and copied the records; changing it does not undo that.
2. `npm run cli -- disable-2fa <email>` if they use two-factor or might have had one added: someone with the old password could have enrolled their own authenticator (**S-22**), and neither a reset nor `set-password` removes it. The user can enrol again.
3. Revoke the share links they created from their device; those are independent of the password and survive a reset.

**The instance-wide secret may be compromised.** Rotate `SESSION_SECRET` in `.env` and `sudo systemctl restart spine-web`. This invalidates every session, which is the point. It also makes every enrolled authenticator seed unreadable (**S-21**): those users sign in with a recovery code and enrol again, or the operator runs `disable-2fa`.

**`spine.db` or the vault may have been exposed.** Neither holds a record: the database holds credential hashes (argon2id), wrapped keys and share metadata; the vault holds sealed objects. An attacker can try master passwords against the wrapped keys offline, so a weak password is the exposure: ask users to change theirs (their new password re-wraps the keys, but a copy of the old wrapped keys still opens with the old password). TOTP seeds are encrypted under a key that is in `.env`, not the database, but treat them as exposed too if `.env` was. Backup snapshots carry the same exposure. Sealed shares are not in the backup.

**Restoring.** Stop `spine-web`, copy a snapshot from the backup directory to `data/spine.db` and `data/vault/` back from the mirror, then start it again. Delete any stale `spine.db-wal` and `spine.db-shm` beside the restored file: a snapshot is already consistent, and an old sidecar would be applied on top of it. Shares are not restored (they were meant to end): the owner makes them again from their device.
