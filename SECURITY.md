# Security

Spine holds complete medical histories and exposes part of them to the public internet through share links. It is self-hosted, multi-user, and runs on hardware as small as a Raspberry Pi.

This document states the posture it is **supposed** to hold, records which controls actually exist, and lists the gaps between the two.

It is written to be enforced: every principle is phrased so a change can be judged against it, and every gap names the principle it violates. See [ARCHITECTURE.md](ARCHITECTURE.md) for the component and trust-boundary model.

> **Status.** Built and tested: multi-user accounts with every query scoped by owner,
> argon2id passwords, open signup with email verification, recovery links, optional TOTP
> two-factor, and hybrid parsing with image egress behind two switches. Every defect found
> so far is fixed or accepted ([Known gaps](#known-gaps)). Not yet exercised against a real
> provider: reading a page image. Nothing here
> claims compliance with any regulation. The 2026-10-18
> [review](#review-attacks-on-sign-in-and-access-and-on-agent-built-software) found six things (a forgeable client
> address, dependency advisories, a 30-day stolen-cookie window, a length-only password check, no model spend ceiling,
> no independent check on agent-written code) and fixed the first five; the sixth is open (**S-36**).

## Reporting a vulnerability

Email **alexandru@cocinda.net** with what you found, how to reproduce it, and which version or commit you ran. The same address is published at `/.well-known/security.txt` on a deployed instance ([RFC 9116](https://www.rfc-editor.org/rfc/rfc9116)). Please do not open a public issue for a vulnerability, and do not use a real person's records to demonstrate one: Spine holds medical data, so test against your own instance with invented records.

What to expect:

- An acknowledgement within 5 working days, and a first assessment (confirmed, not reproducible, or out of scope) within 15.
- A fix and a published advisory for anything confirmed, with credit if you want it. The default disclosure window is 90 days from the report, shorter if the fix ships sooner, longer only by agreement.
- No legal action against good-faith research that stays inside your own instance and accounts, does not read or change other people's data, and does not degrade a service for others.

In scope: this repository, and the hosted service run by the author. Out of scope: an instance run by someone else (report to its operator, who is the data controller, see below), denial of service by volume, and findings that need a compromised host or an operator who has chosen an unsafe setting the software warns about. Known and accepted gaps are listed under [Known gaps](#known-gaps); a new angle on one is welcome.

How the author handles a report, which is also the record the EU Cyber Resilience Act asks a manufacturer to keep:

1. Log it privately with date received, reporter, affected component and severity.
2. Reproduce it against a running instance, not by reading code (the method of the reviews below).
3. Fix it with a test that fails without the fix. Add or move the entry in [Known gaps](#known-gaps), and add the control to [Controls in place](#controls-in-place).
4. Publish an advisory on the repository with the affected versions, the fix, and what an operator must do (rotate a secret, revoke links). If users' data may have been exposed, follow the breach steps in [Operational response](#operational-response): the controller notifies the supervisory authority within 72 hours (GDPR Art. 33).
5. Check the dependency audit (`scripts/check.sh`) so a fixed advisory does not return.

For the hosted service the design is that the operator cannot read patient data ([docs/key-hierarchy.md](docs/key-hierarchy.md)); until that is built, the instance described in the rest of this document can.

## Distribution and who owns the risk

The primary deployment is the author's family. Others may self-deploy, or pay the author to set up an instance. In every case **the operator of an instance is the data controller for its contents and owns the risk.** The author is not a processor for other people's medical data.

Operators will not be security experts, so:

- Insecure configurations must be **unreachable by default**, not merely documented against. A default that works but is unsafe is a defect (**P3**).
- Anything that sends data off-host must be an explicit, reversible choice (**P8**).
- The software should refuse to start rather than run in a state the operator would not have chosen knowingly.

## What we are protecting

| Asset | Why it matters |
|---|---|
| Document text, summaries, extracted fields | Medical history. |
| Original scans (`data/originals/`) | Same, plus signatures, ID numbers, letterheads. |
| Page images | The full document rather than an extract — the most sensitive egress. |
| `data/spine.db` | All of the above, every user's credential hash, every live share token. |
| User credentials | Account takeover. Reused passwords make this worse than local. |
| Share tokens | Read access to a subset, with no account and no second factor. |

### Adversaries we design against

1. **Untargeted internet traffic** — scanners, credential stuffers, crawlers. Constant and automated. Reaches login, registration, and share URLs.
2. **Another user of the same instance.** New with multi-user and the boundary most easily broken by a careless change. A family member is not an attacker, but the control must hold regardless of intent — a query missing an owner filter leaks silently and nobody notices.
3. **A share-link recipient exceeding their scope** — a doctor, or whoever the link was forwarded to, reaching data outside what was shared.
4. **A leaked share link.** Forwarded email, shared screen, clinic browser history. Assume tokens leak eventually.
5. **An attacker who obtains `spine.db`** — stolen backup, misconfigured static mount, lost SD card.

### Explicitly out of scope

- **An operator with shell access to their own instance.** They can read the database. This is inherent to self-hosting and is stated plainly rather than designed around. It is also why there is no in-app admin role: no *application* path reads another user's records.
- An attacker with physical possession of the host, or root on it. Disk encryption is the host's job.
- Targeted attack on the chosen inference provider or on Let's Encrypt.

## Principles

A change that breaks one of these is a defect, whether or not a test catches it.

**P1 — Deny by default.** A route is private unless deliberately and visibly public. "Public" means living in a route file with no `requireAuth` preHandler, so **adding a route to the wrong file silently publishes it**. `isolation.test.ts` fails on any route that answers without a session and is not on its allow-list; every public route must be justified in this document.

**P2 — Scoping fails closed.** If a share link's scope cannot be fully resolved, return nothing. A missing, malformed or unrecognised scope is an error, never "return everything".

**P3 — No fallback secrets, no unsafe defaults.** The service must refuse to start rather than run with an absent, default or weak secret — one committed to the repo as a fallback is a published secret. Extended for self-hosting: any default an unaware operator would not have chosen is treated the same way.

**P4 — Medical content is served only by authenticated, auditable handlers.** Never a static file mount: `DATA_DIR` holds `spine.db` and the original scans, so a mount rooted there is one flag from publishing the archive.

**P5 — Every unauthenticated endpoint is rate limited.** Login, registration, share-token reads.

**P6 — Capability tokens and secrets are hashed at rest.** Possession of the database must not confer the ability to use the share links described in it.

**P7 — Every non-owner data access is logged.** Token, timestamp, source address, and the scope served. Append-only, and part of the backup set.

**P8 — Egress is minimal, enumerated, explicit and disableable.** The only third parties are the configured inference provider and, for account links, the mail provider. Four rules:

- Every egress path is listed in [ARCHITECTURE.md](ARCHITECTURE.md). A new one is a change to that document first.
- **Page images leaving the host requires an explicit opt-in**, and the deployment must be able to disable that path entirely and accept weaker OCR.
- **Residency is a property of the endpoint, not the model.** An adapter that can fall back to a global endpoint, or authenticate in a way known to ignore the configured location, is a defect.
- **Email carries no medical content — ever.** The mail path exists only for account recovery and verification: a recipient address and a single-use link. No document text, no summary, no extracted field, no attachment. This is what keeps a mail provider from becoming a processor of health data, and the mailer interface has no attachment parameter precisely so the capability cannot be reached. The subject and body say nothing clinical either. The sender name is the operator's choice: it can be the company or the product, which tells the provider and anyone seeing the inbox that the recipient uses that service, and no more. An operator who wants less visible than that picks a more neutral name.

**P9 — Least privilege at the OS layer.** Services run unprivileged with `ProtectSystem=strict`, `NoNewPrivileges`, write access narrowed to `data/`. There is no parser service any more: PDF text is read in the server process, so the old sidecar's unauthenticated, path-reading listener ([docs/sidecar.md](docs/sidecar.md)) no longer exists.

**P10 — Tests exercise the real path.** A control is untested unless the test drives it the way production does. A fixture that builds state directly, bypassing the handler that encodes it, proves nothing.

**P11 — Recoverable by design.** `data/spine.db` and `data/originals/` must be restorable. `data/pages/` is regenerable.

**P12 — Isolation is structural, not remembered.** Every read and write is scoped by owner **in the store layer**. A repository method that does not take an acting user id, or that can return a row the acting user does not own, is a defect. Route handlers must not be able to write queries, so isolation cannot be forgotten in one. The four exceptions are listed in **M-1**; the main one is a share-token read, scoped by the link's owner resolved from the token, never from a session.

**P13 — Credentials are stored with a memory-hard KDF and are never recoverable.** argon2id, per-user salt, parameters tuned to the host. No password in a log or error, and no reset path that reveals the old value. Changing a password invalidates that user's existing sessions. The one reversible secret is a TOTP seed, which has to be read back to check a code; it is encrypted at rest and is a recorded exception (**S-21**), and recovery codes and tokens are hashed. A second factor, where enabled, applies to every way of obtaining a session (**M-12**).

## Known gaps

Defects in the code as it stands. Severity: **High** = unauthorised access to medical data or account takeover. **Medium** = weakens a control or widens blast radius given a precondition. **Low** = hygiene and defence in depth.

One item is open (S-36, from the [2026-10-18 review](#review-attacks-on-sign-in-and-access-and-on-agent-built-software), which also found S-31 to S-35 and fixed them the same day); everything else is fixed or explicitly accepted, and the next review should expect to add to the list. The original findings were confirmed against a running instance, not inferred. [Closed](#closed) keeps the ids resolvable, since they are cited from [ARCHITECTURE.md](ARCHITECTURE.md).

### Open

**S-36 — Code written with an agent is checked by the tests the same agent wrote** (**Low to Medium**, process, **P10**). The studies behind the [2026-10-18 review](#review-attacks-on-sign-in-and-access-and-on-agent-built-software) find that AI-written code carries the usual classes (missing authorisation, injection, weak randomness, hard-coded secrets, unsafe defaults) at a rate that rises, not falls, with more refinement rounds, and that a model reviewing its own output shares its blind spots. This codebase's answer is structural (the store takes the user id, one visibility fragment, a route allow-list test, response-shape scans), and it has held. **Partly closed**: `scripts/check.sh` runs the typecheck, the tests, `npm audit` (high and critical fail), `gitleaks` on the tree and its history, and `semgrep` (TypeScript, Node.js and security-audit rules) on `server/src` and `web/src`; `.github/workflows/ci.yml` and `.gitlab-ci.yml` run the same, and `install.sh -b` runs the audit. **First run, locally on 2026-10-18**: gitleaks found one hit, a fixed `SESSION_SECRET` in the integration-test setup (a throwaway for an in-memory database, never a deployment's); it is now random per run and the historical hit is listed in `.gitleaksignore` with the reason. Semgrep found eight: one real (`createDecipheriv('aes-256-gcm')` without an explicit tag length in `totp.ts`; the tag was already sliced to 16 bytes, but the length is now stated, so a shorter forged tag is refused), six false positives of an Express rule (`direct-response-write`) on `reply.send(object)`, which Fastify serialises as JSON, with the only HTML sent being a constant page and the built app shell (excluded by name in `check.sh`, with that reasoning beside it; re-check if a route sets `text/html`), and one in a test that asserts a `<script>` string is returned as text. Tests are not scanned. **Still open**: the GitLab pipeline has not run (no remote yet); there is no second human reader on a change to auth, scoping or a prompt; and the integration tests (`npm run test:integration`) have been run against the real model once. Needed: push, confirm the pipeline passes, and a human read of every diff that touches the checklist's first dozen items.

### Accepted

**S-9 — The audit log trusts `X-Real-IP`.** `public-share.ts` reads the header before the socket address. Correct behind nginx, forgeable if Fastify were reachable directly, which would poison the only record of who read what. Acceptable while **P9** holds, and since S-13 it does: Fastify binds loopback, so only the proxy can set the header.

**S-16 — Sessions live in memory.** Restarting the server signs everyone out, and sessions are not shared between processes. Fine for one process; a second would need a shared store.

**S-17 — The instance-wide login cap can lock everyone out.** 50 failed logins in ten minutes from anywhere stops all logins for the rest of the window, including the owner's. That is the trade for throttling a distributed guess; the per-source limit runs first so one noisy host does not spend it alone. Existing sessions are unaffected.

**S-19 — nginx's access log holds raw share tokens.** `/share/<token>` and `/api/share/<token>/documents` are in the path, so `spine.access.log` records every live token, and hashing them in the database (S-4) does not help against someone who can read the log. Verification and reset links avoid this with a URL fragment; share links cannot without changing how recipients open them. Rotate the log, keep it readable by the operator only, and revoke links that matter. A link with scans now makes many more requests that carry the token (one per page image), so the exposure in the log is larger. A scan also shows what extraction drops on purpose, the patient's ID number and phone, so "include scans" is a decision to make per link, and it is off by default.

**S-20 — Two-factor is optional.** Each user turns TOTP on for their own account (M-12); an instance cannot require it, so on an `open` instance a user who never enables it is protected by their password alone. A `SPINE_REQUIRE_2FA` switch is the obvious next step; it is not built.

**S-21 — The TOTP key derives from `SESSION_SECRET`.** A TOTP seed has to be read back to check a code, so unlike a password it cannot be hashed; it is encrypted at rest under a key derived from `SESSION_SECRET`. Someone holding both `.env` and the database could generate valid codes (they could also forge sessions, so this adds nothing new). **Changing `SESSION_SECRET` makes every enrolled seed unreadable**, so authenticator codes stop working. Recovery codes still do (they are hashed, not encrypted), so each user can sign in, turn it off and enrol again; failing that, the operator runs `disable-2fa`.

**S-22 — Whoever has the password can enrol their own authenticator.** Enrolment needs the password and a session, nothing else. An attacker who has both can switch two-factor on with their own app and lock the owner out: a reset link and `set-password` do not remove it. That is denial rather than disclosure (holding the password already exposed the archive), and the operator's `disable-2fa` undoes it. Not built, and the obvious fix: email the account when two-factor is turned on or off, so a lock-out is noticed.

**M-30 — Editing the doctors of a document keeps how each is tied to it.** **P12.** `PATCH /api/documents/:id` with `doctors` replaces the document's list, as before, but a doctor who stays keeps where they were read (text, a stamp, a signature) and the code the document printed for them, which the clash question of **M-26** depends on. The page sends the directory entry's id with a row the owner chose from the directory (a searchable list, `Combobox`); the route accepts it only as a hint (it must be the user's own entry, found through the store, and the name's key must still match), then uses exactly that entry, so a spelling-neutral edit stays the same person even when another doctor shares the name. A name that is not an entry makes a new one with no code (the code belongs to the person, not to the name), and `new: true` makes another person even though the name is held. Two people can share a name: `doctors.key` is an identity (`ion popescu`, `ion popescu#2`), not the name, so the unique index and the schema are unchanged; reading a name picks the namesake with no code, then the oldest, and a professional code that differs is still only asked about (**M-26**), except in a restore, whose codes are exact. Renaming on the Doctors page no longer refuses a name another entry has. The owner's pages now show the entry's code; a share recipient's list never carries it. `document-edit.test.ts`.

**S-23 — A doctor read from a document is a label, not a proof.** Text, a stamp and a digital signature all name a doctor, and anyone who can get a file into the archive (a forwarded PDF, a clinic's mail) can make one say anything. A signature is checked for being intact. **Chain check**: with `SPINE_TRUST_ANCHORS_DIR` naming certificates (`.pem`, `.crt`, `.cer`, `.der`; served as `GET /api/trust-anchors`), the device also follows the certificates in the file from the signer to one of them, each link signed by the next, every certificate in date at the signing time and every issuer a CA (`signatures-cms.ts`, `signatures-cms.test.ts` with invented chains), and files the doctor as `verified_signature`; the document page says "Digital signature verified". Revocation (CRL, OCSP) is **not** looked up, because the lookup would tell a third party whose certificate was used, and the signing time is the one the file states, so a signer can claim a time. With no anchors, or a chain that does not reach one, a self-signed certificate naming a real doctor is still filed as that doctor, as a label. Nothing is decided from it (no scope, no access, no share); it puts a name in the owner's own directory, where Review can remove it and Duplicates can show it. A stamp or signature is not evidence of who wrote a document and the interface never says so.

**S-24 — Uploaded files are parsed by poppler and sharp in the web service's own process owner.** A memory-safety flaw in either would run as the `spine` user, with that user's access to `data/` and `.env`. The units drop privileges and make the system read-only, and every call has a time limit and a pixel limit (S-25), but there is no memory cap, no seccomp filter and no separate user for the readers. Keep poppler and the `sharp` package up to date; a stricter unit (`MemoryMax=`, `SystemCallFilter=`, a dedicated user) is the next step and is not built.

**M-26 — What an upload may have duplicated is put to the owner as questions; nothing is merged because a name looks alike.** **P12.** Reading an upload merges only what is exact: a doctor by the same name key (case, accents, titles and word order ignored) or the same professional code, a tag cleaned to the same form, a test by a remembered alias. Everything else is left as it was made and **asked about** (`matching/`, `GET /api/source-files/:id/matches`, drawn in the upload's report): for a doctor, a test, a tag and a clinic or laboratory that this upload introduced, compared with everything else held, the page asks "is this the same?" with the reason (the same surname and an initial; a longer form; differing only in punctuation or a company suffix; spelled almost the same; one begins with the other) and what helps decide (specialty, clinic, code; the units of a test, with a warning when they differ, since merging them would mix the values). **Yes** is the merge itself, made through the ordinary merge route into the entry that stays (the fuller doctor name, otherwise the one already held), so every check that route makes applies; **No** is remembered (`match_decisions`, per user, deleted with the account) and the pair is not asked again. Two doctors with different professional codes are never suggested together, two tests that sit in one document are never suggested, and a name told apart by a number or a lone letter ("Spital A", "Vitamin B6") is not suggested. **A code that differs**: the directory keeps one code per doctor and a name match leaves it as it is, so a document that prints another code used to be dropped silently; the code a document printed is now kept on the link (`document_doctors.printed_code`) and the difference is asked about (use the printed code, keep the directory's, or open the doctor: the schema allows one entry per name, so two people of one name cannot be told apart here). The questions are worked out when the report is shown, from the current state, so an answered or merged pair is not there. **What leaves the host**: nothing; this is all local string and directory comparison, with no model. It only suggests, from names: it cannot know that "Hb" is "hemoglobin", which is what the assistant's merge cards are for (**M-21**).

**M-25 — A file attached in the chat is the ordinary upload, tied to the conversation it came in, and reported there.** **P8, P12, M-7, M-9.** `POST /api/chat/attachments` (multipart; a `conversation_id` field sent before the files names the conversation, otherwise one is started) is not a second way to upload: it calls the same `acceptParts` as the Upload page (`ingestion/accept-parts.ts`), so the same checks apply to every file: the type is detected from the bytes and not the name, a photo is refused unless the operator allowed AI reading (**M-7**), the size caps, de-duplication by checksum, the zip limits (**M-14**), the original written under the owner's directory (**M-9**), and the same pipeline with the same egress (**P8**). What it adds is `source_files.chat_conversation_id`, so what happens to the file is reported in that conversation. A conversation that is not the owner's (or is full) is refused **before the first file is saved** (404/409, nothing written); the route is owner only and rate limited. The conversation holds the owner's message (the file names, kind `attachment`, drawn by the page) and, when reading ends, the app's report (kind `upload`, **M-23**), added to it and unread until seen, instead of starting a new conversation. The report now says what reading added: the doctors the upload introduced (a doctor is new if its directory entry was made while the upload was being read) and how many it found already there; pairs that may be one person, where one is new (the app never merges them itself: the owner confirms a merge card, **M-21**); the tests no other document has; and whether the pages look cut from mixed pages. That last is a cheap local look at the pages' own text with no model and nothing sent (**M-24** is the model-validated analysis, started by the owner pressing "Check the pages with AI", whose disclosure is beside the button). The names in the report are medical text and are stored with the conversation, so they are handled as conversations are (**M-18**): scoped by `user_id`, deleted with the account, not exported.

**M-24 — Sorting a mixed upload sends the pages' text to the model, once, because the owner confirmed it; the model proposes, the owner applies.** **P8, P12.** For a bulk export whose pages are side by side from many documents, `POST /api/source-files/:id/regroup/analyze` (the chat proposes it as a card; Confirm sends it) compares the pages on this server and then asks the configured model, per candidate group, whether those pages form one coherent document and, if not, how they divide (`judgeGrouping`, the `grouping` task, schema-validated; a label it makes up names no page we sent, and a page it leaves out is put back). **What leaves the host**: the text read from the pages of that one upload, a page or so each, to the chat provider with its residency refusals: the same text that already went to read the documents (**P8**, ARCHITECTURE.md Data egress), and, where `SPINE_EMBEDDINGS=vertex`, the pages' text to the embedding provider with the refusals of **M-15**. Never an image. It is bounded: at most 60 model calls for an upload, groups of at most 8 pages, 4 at a time, 6 analyses a minute, one at a time per upload, and nothing runs without the owner's confirmation. The page text is data, not instructions (the prompt says so), and a page that tries to steer the verdict can at most make a group look coherent, which is shown to the owner with the pages themselves. **The signals are ours, not the model's**: reference numbers, dates, "page 2 of 4" markers and word weights make candidates; the model validates; a group without a verdict is `unchecked`, and `uncertain` or `unchecked` groups are off by default on the card. **Nothing is changed by the analysis**: the plan (page ids, page numbers, a title, a verdict and a one-sentence reason; no page text) is stored per upload (`regroup_plans`, deleted with the upload, with a re-reading and when a regrouping is applied, since its page ids would no longer mean the same) and the app starts a conversation to say it is ready (**M-23**). **Applying** is `POST /api/source-files/:id/regroup`, an owner route that takes groups of page ids and validates them against the upload (a page of another upload or user is a 400/404, a page in two groups a 400; the upload must not be processing or being analysed), then in one transaction makes the new documents, moves what was read from a page with it, folds a document no group kept into where most of its pages went, numbers the pages again and marks the changed documents unreviewed. A group keeps the identity (and so the owner's edits) of a document only if each is at least half of the other. Pages not named stay where they were. The card then reads the changed documents again from their text (`/extract`, as after any regrouping). The thresholds are first guesses and the analysis logs counts (never text) to tune them from.

**M-23 — The app starts a conversation when an upload has been read; the assistant can then review it with the owner, and the documents of an unconfirmed upload reach it by that route.** **P8, P12.** When the pipeline finishes an upload (or fails) it writes a conversation of its own (`chat/notices.ts`, `origin = 'upload'`, unread until opened) whose one message is **not written by a model**: it is a fact about the upload stored as data the page draws in the owner's language, plus the same facts in English for the model to read when the owner replies. Nothing leaves the host to make it, and it is skipped when `SPINE_CHAT=off`. The failure message does not copy the reason the file failed (it can quote the file). Conversations are medical text and are handled as such: scoped by `user_id`, a 404 for anyone else's, deleted with the account, not exported (**M-18**); `GET /api/chat/unread` and `POST /api/chat/conversations/:id/read` are owner routes. When the owner replies in such a conversation, the upload named by the app's own notice is put on screen for the assistant (the browser does not send it), so "is this right?" has an answer. **The exception this widens**: **M-17** keeps the documents of an upload whose grouping is not confirmed away from the assistant, except the one document the owner has open and an upload's own screen. The tools `list_uploads` and `get_upload` add one more path: the documents of an upload the owner asks about, by label, for exactly the owner who is checking them. They are still the owner's own, through the store, by labels the request gave; they cannot be shared (a share needs documents *shown*, `resolve(…, shown)`) and the searches still do not find them. **What it can propose** on top of **M-21**: confirming the grouping (the ordinary route; documents then appear in the timeline, search, shares and are embedded, **M-17**) and reading pages again (`POST /api/source-files/:id/ai-reading`): the card says that a page image goes to the model provider, the proposal is refused when the operator has not allowed AI reading (**M-7**), and the route checks the same switch again. Links the background search finds are not announced: they appear where the document is, and nothing out of the blue is worth a notification there.

**M-22 — A link can be inspected and changed after it was made; the same checks apply, and the history is the owner's.** **P2, P6, P7, P12.** `GET /api/share-links/:id` and `PATCH /api/share-links/:id` are owner routes (a link that is not theirs is a 404). The detail shows the settings, the documents the link resolves to *now* (through `listForShare`, so a document since set aside is not listed), the addresses that read it with their country (looked up on this host in a file of address ranges, `geo.ts`, so the address is sent nowhere) and counts, and the latest reads with the shared document each opened, if any (from the access log, **P7**; a document is recorded only when the link really shares it, because its id comes from the recipient), the requests that asked to open it and a history of what happened to it (`share_link_events`: created, changed with the field and its old and new value, revoked, approved, denied). It never returns the token or its digest (**P6**), and the history holds small values only: a scope change records document *counts*, never ids, titles or text, and a request's note is not in it. **A change goes through the creation checks**: `checkScope` is the one place a scope is validated for both (a scope that cannot be fully resolved is a 400, **P2**; a document that is not the owner's is the same 400 as one that does not exist, **M-5**), the options must be booleans, the language one of four, the expiry 1-30 days from now (so it extends or shortens), and an unknown key is a 400. A **revoked link cannot be changed** (409): revocation stays final. **Switching approval on drops the requests the link held**, so a browser approved under an earlier setting asks again (**M-19**); switching it off lets anyone read, as at creation. A change applies on the next read of the link by anyone holding it: there is nothing cached. What an address shows is what the visitor's connection reported (**S-9**), shown with a notice that it proves nothing. See ARCHITECTURE.md **Share links**.

**M-21 — The chat can prepare changes but cannot make them; the person's Confirm is the only thing that does.** **P8, P12.** The owner's agent has `propose_*` tools (`chat/actions.ts`) for a share link, a note, a correction, tags, reviewed, a care link, revoking a link, merging duplicate doctors, tests, tags or providers, correcting a result's value, unit, range or date, changing an existing share link (its name, how long it works and which documents; never what it exposes: scans, approval and recipient questions are changed only by the owner, on the link's page), confirming an upload's grouping, reading pages again, sorting a mixed upload (**M-23**, **M-24**), and moving one page of an upload into another of its documents, or out into one of its own (`propose_move_page`: the page and the document are named by number and label from `get_upload`, the card shows from where to where, and Confirm sends the ordinary `POST /api/pages/:id/move`, which checks ownership and that the file is not being read; `chat-notices.test.ts`), confirming or dismissing the connections the app suggested (`list_suggested_links` shows the unanswered ones across the archive, between documents that are shown, labelled K1…; `propose_decide_links` names them by those labels, checks each is still unanswered, and Confirm sends the ordinary `POST /api/document-links/state`; the app's one-sentence reason is copied from the documents, so it is shown as text and the prompt says it is not an instruction, **S-27**), and combining two documents of an upload into one (`propose_merge_documents`: every shown page of the second is moved to the end of the first by the same move route, one request each in order, then the first is read again through the ordinary extract route; the pages need not be adjacent, both documents must be the upload's, a document cannot be combined with itself, at most 60 pages; the card names both documents and the pages). **A tool never executes**: it validates its arguments against the limits of the route Confirm will call, names things only by labels the request handed out (so the model cannot name another user's record or invent an id; a label it was not given is refused), and returns a proposal. The reply carries it, the page shows it, and only the owner's Confirm sends requests from their authenticated browser to the ordinary routes, which check ownership, limits and visibility again. `__tests__/chat-actions.test.ts` runs every tool against a store and asserts nothing changed, and runs each proposal's requests against the real routes. **The words next to Confirm are the page's, not the model's**: a proposal is data (ids, titles, values, before and after) rendered by the app in the person's language, so a model steered by a hostile document cannot describe a change as something milder than it is; the free text it does supply (a note, a field value, a label) is shown verbatim. **What the model cannot decide**: whether a share exposes scans, needs approval or lets the recipient ask (the card starts at the safe setting and the person chooses), and the owner can remove documents from a proposed share before confirming; it cannot propose more than 30 documents in a share, 20 in a bulk edit, 10 groups of duplicates, or more than five proposals for one question. **Duplicates**: two entries with different professional codes are different people and are never proposed together; tests with different units are flagged on the card; the merge is the owner's existing merge route and rename route, and the final form is written onto the kept entry only after the merges. **Not stored**: proposals live in the reply; the stored conversation holds the words only, so a reopened conversation offers nothing to confirm, and nothing the owner did not just see can be confirmed later. **What it does not do**: a document can still steer what the assistant proposes (**S-27**), which is why the proposal is shown in full and nothing is applied until Confirm; and the browser, not the server, sends the requests, so a proposal cannot be confirmed from anywhere but a signed-in session. A share recipient's agent is built without any of these tools (`share-chat.test.ts`, `chat-actions.test.ts`).

**M-20 — A share recipient's question puts the shared documents, the owner's notes on them and the link's label in front of a model; the agent is held to the link in code.** **P2, P5, P8, P12.** Off unless the owner ticked `allow_chat` for that link and `SPINE_CHAT` is not `off`; a link without it answers `POST /api/share/:token/chat` with the same 404 as a scan the link does not allow. It sits behind everything else a share read does: the live link, the approval gate (**M-19**), scope resolution (**P2**) and the access log (**P7**, each question is a logged read, not a view). **What leaves the host** for the configured chat provider (with its residency refusals): the question, up to six earlier turns the page sends, the shared documents' headlines, and what the tools return for them: summary cards, the owner's notes, results with reference ranges, doctors and field values; never page text or scans (the same content a recipient already sees on the page, but now also at the provider, which is why the owner's checkbox says so); and **the link's label**, the owner's own words, as quoted context (control characters and quotes removed, 120 characters, and the prompt says it is text, not an instruction). **Scope is code, not prompt**: the agent reads the owner's store, so every tool is held to the documents `listForShare(link)` returned for this request. Search is filtered to them before ranking (including the meaning search), the test list and a test's series are built from them alone (`share-tests.ts`, also what the trends routes use), a document opens only by a label the request gave, and the document the recipient has open (`document_id`) is used only if it is in that list. Anything outside is indistinguishable from nothing (`share-chat.test.ts` puts a second document with its own test and a unique word beside the shared one and checks that no tool output, and nothing the model was sent, mentions it). **The care chain is not offered to the agent**: links between documents are the owner's, and the only share route that returns them is the connections route of **M-28**, which the agent does not call, so the recipient's agent has no `get_connected_documents` and the open document's sections leave out `chain`. **The model is told who is asking**: a separate system prompt says the asker is a recipient and not the patient, to speak of "the patient", to treat only the shared documents as existing, and to give no diagnosis or treatment advice. **Bounds**: the route is public, so 10 questions a minute per source and 60 an hour per link (each is several model calls; this is also what bounds spend by a leaked link), a question of 1,000 characters, at most six earlier turns, five rounds of tools, 12,000 characters a result, 120,000 a question and 90 seconds, as for the owner. **Nothing is stored**: no conversation, no history; the earlier turns come from the page, so a recipient can only shape their own conversation (they could write the same text as a question), and a failure's log line carries the link id and no medical text. Without a model that takes tools the route answers 409; there is no fixed-pipeline fallback for recipients. **What it does not do**: it does not stop a recipient from learning from the shared documents what the shared documents say (that is the point), a hostile document can still steer an answer (**S-27**), and revoking the link ends it at once. **Streaming**: `stream: true` sends the reply as lines (`routes/ndjson.ts`, shared with the owner's chat), after every refusal has been made as an ordinary status; the text shown while it is written is a draft with no citations, and a recipient who leaves aborts the model call. The owner's own chat is unchanged (**M-18**).

**M-19 — Approving a share link's visitor is a decision about a browser, not a person.** **P2, P5, P6, P7, P8.** A link made with `require_approval` serves nothing until the owner approves the request of the browser that is reading it. A visitor opens `/share/:token` (the app shell, no data), the page asks `/meta` where this browser stands, and `POST /api/share/:token/access-request` records a request and gives the browser a random 256-bit cookie (`spine_share_visitor`, path `/api/share`, `HttpOnly`, `SameSite=Strict`, `Secure` in production) whose `sha256` is stored with the request (**P6**). Every data route (list, document, translation, trends, page images) asks `approvalFor` and answers 403 unless there is an `approved` request for **this link and this cookie**; a missing cookie, an unknown one, a pending, a denied or an approval for another link all read nothing (fail closed, **P2**). A refused read is logged (**P7**) but is not a view. The owner decides at `POST /api/share-requests/:id/decision` from a signed-in session (a request that is not theirs is a 404, as everywhere), never from a `GET`, so a mail scanner that follows the mailed link approves nothing; approving a request on a revoked or expired link is a 409, and an approval can be withdrawn. **Mail**: when a mailer is configured the owner is mailed once per browser, after the response, with a link to `/share-requests/:id` (it asks them to sign in first and returns them there). The mail carries no label, no note and no scope (the label is the owner's own words and may name a doctor or a condition; the note is a stranger's) and no share token (**P8**, `share-approval.test.ts` checks for clinical words and the token). With `SPINE_MAILER=none` the request waits on the Share links page and creating the link says so. **Bounds**: the route is public, so it is rate limited per source (10 a minute) and per link (10 an hour), at most five requests wait on a link at once (the cap is inside the `INSERT`), and the visitor's note (120 characters), browser name (200) and address are cut and stripped of control characters; they are shown to the owner as text with a notice that they prove nothing. **What this does not do**: it does not identify the visitor (the note and address are theirs to write), it does not stop someone who obtains the approved browser's cookie or uses that browser, and a cleared cookie means asking again. The cookie holds no secret about the owner. Approval lasts until the link expires (at most 30 days) or the owner withdraws it. The rows are deleted with the link's owner (`OWNED_TABLES`). Share links without the flag behave as before. See ARCHITECTURE.md **Share links**.

**M-18 — A question sends the question, what is on screen and what the agent reads; the answer is a reading, not advice; the agent can only read.** **P8, P12.** On unless `SPINE_CHAT=off`. The chat is a LangGraph agent that decides what to look up with five tools, all read-only (`TOOL_KINDS`, and a test holds it). What leaves the host for the configured chat provider (with its residency refusals) is the question, up to six earlier turns, a description of what the person is looking at, and what the tools return: summary cards, the owner's notes, results with values and reference ranges, and field values for documents it opens; never snippets, scans, ids or paths, and page text only through `read_pages` (below). **Page text, on request of the model**: `read_pages` returns the text that was read from named pages of one upload (at most 6 pages, 2,500 characters each, set-aside pages refused, the label from `list_uploads` so only the owner's own uploads can be named, owner's agent only: a recipient's agent is built without it and a test holds the exact list). It is the same text that already went to this provider when the pages were read and when a mixed upload was analysed (**M-24**), so it adds no new kind of content, but it does mean a question can send pages the person did not mention: the step is shown in the panel ("read pages 12, 13") and the text is marked as data, not instruction (**S-27**). It is the tool that lets the assistant decide where a page belongs from what it says instead of from summaries. **Scope is enforced in code, not asked of the model**: a tool takes the signed-in user's id from the graph's state (set by the route from the session, passed in no schema, so the model can neither see nor write it) and reads through the store (every statement filters by `user_id`) over the shown documents only, so another account's, a set-aside document and one in an unconfirmed upload are unreachable by any argument the model can choose; the model never handles an id, only labels this request handed it, and a label it was never given opens nothing. The one deliberate exception is the document the owner has open (and, on an upload's screen, that upload's documents, or an upload the owner asks about in a conversation the app began: **M-23**), which reaches the model even before the grouping is confirmed. **Bounded**: eight rounds of tool calls (five for a share recipient, **M-20**), 12,000 characters a result, 120,000 a question, 90 seconds, one question 1,000 characters, six turns of 1,500, 20 questions a minute; a run that hits a limit is told to answer with what it has. **Untrusted text**: documents and tool results are copied from scans, so the system prompt says to ignore instructions in them; because the agent has no tool that writes, the worst a hostile document can do is steer an answer, which carries links to the documents it came from and is labelled a reading of the records. The screen description is pointers the server resolves itself: the browser sends no document text. **Actions, when added, must not weaken this**: an action tool returns a proposal that ends the loop and is shown for the owner's confirmation, which calls the ordinary authenticated route; it never executes from the agent (ARCHITECTURE.md **Ask your records**). The answer cites labels that were shown to the model (others are dropped) and the prompt forbids diagnosis and treatment advice; the page says the answer is not medical advice. **Conversations are stored** (`chat_conversations`, `chat_messages`) so the owner has a history. What is kept is their questions and the answers, with the documents an answer cited (id, title, section): medical text, so it is handled as the documents are: every statement filters by `user_id` and a conversation that is not the caller's is a 404 in every route (`chat-history.test.ts`); the conversation the model continues is read from the store and the browser can only name it; they are deleted with the account and when the owner deletes them (one or all, from History); capped at 200 conversations and 200 messages in one; present in the database backup like everything else; not exported; no share route reaches them. A failed question stores nothing, and neither does one the person stops. **Streaming** (`stream: true`) changes how the reply travels, not what is sent or kept: the same checks run before the first byte, the text shown while it is written is a draft with no citations, and only the final reply (citations checked against what the model was shown) is stored. The route is owner only; a failure's log line carries no medical text.

**M-17 — Documents are held back until the grouping is confirmed, and what the owner edited is theirs.** **P12.** Every listing of the owner's documents, every share query and the vectors, links, trends and doctors' lists use one fragment (`VISIBLE`: not set aside and the upload's grouping confirmed), so an unconfirmed upload cannot reach a share recipient, the search or a model call (the links search takes its documents from the same listing). The upload and regrouping screens still list them, scoped to the signed-in user, and the confirm route answers 404 for an upload that is not theirs. The records of what the owner edited or removed (`owner_edited`, `removed_readings`) are per user, deleted with the document, the upload and the account, and never returned by a route.

**M-16 — Looking for links is egress of summary text, and a model's word is a proposal.** **P8, P12.** On unless `SPINE_LINKING=off`. When the data finds a candidate (shared test or doctor, closeness in time or, if on, in meaning), one call sends the *summary card* of the document and of up to six candidates (the same cards as **M-15**, with each doctor's role and the owner's notes, trimmed to 600 characters; not pages or scans) to the configured chat provider, which has the residency refusals of any chat call. With no candidate nothing is sent. The cards are copied from scans, so they are untrusted text: the prompt says to ignore instructions in them, the model's answer is validated by schema, a candidate label it did not send is dropped, and nothing it says writes anything but a `proposed` link that the owner must confirm; a request or follow-up whose dates run backwards is refused in code. Candidates and chains come from the signed-in user's own documents (set-aside ones excluded), every statement filters by `user_id`, a link is written only between two documents that are the user's, and any other id answers 404 (`linking.test.ts`). A dismissed pair is never offered to the model again, and a search replaces only the suggestions for pairs it judged again. **Repeats are not stored or shown** (`linking/reduce.ts`): every document is judged on its own, so a pair was judged from both sides and "same episode" was found between every pair of a group. A link is redundant when the pair already has one at least as informative (request, then follow-up, then same episode), or when it is "same episode" between documents that other links already join; a search adds only what is not redundant given the links that stand, the chain is drawn without the redundant ones, and `tidyLinks` (after each search, and so on "Look for links again") deletes the automatic ones. It never touches a link the owner made or a dismissed one (a decision), and a suggestion that repeats a confirmed link is the one that goes. Nothing leaves the host and no model is involved. The owner's notes also go, as context, with the text of a document being read again (**P8**); the extraction prompt tells the model to take no field, result or date from them and to ignore instructions in them. The links route is owner only. The one place a link reaches a share recipient is the connections route of **M-28**: confirmed links between documents the link shares, direction and kind only. Links are deleted with their documents and the account. Links are not in exports.

**M-15 — Embeddings are egress of summary text, and vectors are as private as the text.** **P8, P12.** Off unless `SPINE_EMBEDDINGS=vertex`. On, the *summary card* of each document (title, type, provider, date, summary, doctors, a few key fields, test names; not the pages, notes or scans) and the words of a meaning search go to Vertex at the stated endpoint, region and project, with the same refusals as the chat model (no default endpoint; a Google API key in the environment stops startup); the startup log says so, and a failure's message carries the status, never the text. A vector can be turned back into much of the text it came from, so it is treated as the text is: stored per user and scoped by the store (**P12**), deleted with the document and the account, left out of exports, and returned by no route (asserted in `similarity.test.ts`). Vectors are compared only within the model that made them. Related documents and search results come from the signed-in user's own documents only (set-aside ones excluded); the one thing offered to a share recipient is a list of the shared documents that read alike or share a test or doctor (**M-28**), computed on request from vectors that never leave the server. A document's card is built from its stored data, so what is embedded is what the owner has already reviewed or edited.

**S-26 — What an imported export says is believed.** An export is not signed, so a restored document's title, summary, fields, results and `reviewed` flag are whatever the file says, as if the owner had edited them. Someone who hands a person a crafted zip can put plausible but false values in their archive, which then appear in trends and share links. They cannot reach another account, run code or read anything, and nothing is decided from the content, but a person should import exports only from themselves or from a source they trust. Not built, and the obvious step: import everything as unreviewed (so it passes through Review) when the export did not come from this instance, which needs the export to be signed or to carry the instance's identity.

**S-27 — A hostile document can steer its own translation and reading.** Text in a PDF (a forwarded report, a clinic's mail) goes to the model in extraction and in translation, and a page can contain instructions. The model has no tools and cannot read or change anything else, so the effect is bounded to that document's own extracted values, title and translation, and to the tags and test names it suggests, which the Library lets the owner tidy. A translation is checked to be about as long as its original, which stops a document turning it into a long output. Not preventable by checking; the owner reviews what is read.

**S-28 — Nothing limits how much one account uploads.** The upload route has a per-file size limit (200 MB, or 2 GB for a zip, decided from the first bytes) but no request rate limit and no per-account quota, so a signed-in user, or someone holding a session, can fill the disk. This was true before zips; a zip makes one request larger. Fine for a household instance; an `open` registration instance should add a quota before it is public.

**S-29 — One request downloads the whole archive.** `GET /api/export` returns every document, note and page text. It needs a session, is rate limited (6 a minute) and cannot be started from another site (the session cookie is `SameSite=Strict`, and it is a download), but a stolen session can take everything in one step where before it would have had to walk the API. Two-factor protects the sign-in (**M-12**), not the session after it. Not built, and the obvious step: ask for the password again before an archive export.

**S-30 — A share link's page costs more queries the more it shares.** The recipient's list, document and trends routes resolve the link's documents on every request, and the trends names read each shared document's results. They are rate limited (120 a minute) and the work is bounded by the owner's own archive; a link covering a very large archive is slower to open, not unsafe.

### Closed

Fixed; the control is in [Controls in place](#controls-in-place).

**S-31 — The per-source rate limits could be bypassed with an `X-Forwarded-For` header** (**High**, **P5**). Fastify was built with `trustProxy: true`, which believes the *leftmost* entry, and nginx set the header with `$proxy_add_x_forwarded_for`, which appends the real peer to whatever the client sent, so a client chose its own `req.ip` and with it every limiter keyed on the source (login, second factor, signup, recovery, the share and approval routes, the recipient's chat) and the source in the application log. Reproduced against Fastify 4.29.1: `trustProxy: true` gave `9.9.9.9` for `X-Forwarded-For: 9.9.9.9, 203.0.113.7`, and `trustProxy: '127.0.0.1'` gave `203.0.113.7`. Now both ends are fixed, so either alone is enough: nginx overwrites the header with `$remote_addr` in both locations (`spine.conf`), and Fastify trusts only the loopback proxy (`trust-proxy.ts`, used by `index.ts` and the test harness). `auth.test.ts` sends a forged leftmost entry and asserts the limiter keyed on the address the proxy appended. Behind a proxy that is not on the host (the Docker Compose setup, `docs/self-host.md`), `SPINE_TRUSTED_PROXIES` adds that proxy's address to the list; a range wider than /8 or a word like `true` stops startup, since that would hand clients the choice again (`trustedProxies()`, tested in `config.test.ts`). The access log (**P7**) was never affected: it reads `X-Real-IP`, which nginx sets from `$remote_addr`.

**S-32 — Dependencies carried known advisories and nothing checked them** (**Medium to High**). On 2026-10-18 `npm audit --omit=dev` reported 1 critical, 6 high and 1 moderate (`proxy-addr`, `fastify` 4.29.1, `@fastify/static`, `@fastify/busboy`, `find-my-way`, `fast-uri`, `brace-expansion`, `uuid`). Fastify moved to 5 with `@fastify/cookie` 11, `multipart` 10, `rate-limit` 11, `session` 11 and `static` 10, and `uuid` to 14; the suite, the typecheck and a boot of the real server (`/api/auth/me`, the share shell, the app) pass, and `npm audit --omit=dev` is clean for server and web. The build now stops on a high or critical advisory (`install.sh -b` runs `audit_dependencies`; `SPINE_SKIP_AUDIT=1` skips it for an offline build) and so does CI. **Residual**: the advisory database needs the network, so an offline build checks nothing; advisories published later are found at the next build, not before; `npm audit` without `--omit=dev` still lists development-only packages.

**S-33 — A stolen session cookie was the whole account, for 30 days** (**Medium**, **P13**). Now a sign-in is a row the owner can see and end, and the cookie alone is good for hours: **M-27**. **Residual, accepted**: malware on the owner's machine, or an adversary-in-the-middle proxy, still gets a working session until it goes idle (24 hours by default) or is ended; the password is asked again only before the whole-archive export and a share that shows page images, not before reading. Device-bound session credentials are not built (no browser support to rely on yet); a session is not tied to an address or a user agent, because those change legitimately (a phone moving between networks) and the first would lock people out.

**S-34 — Passwords were checked for length only** (**Medium**, **P13**). `checkPasswordPolicy` (`passwords.ts`) now also refuses a password that is a common word or keyboard run from a list held in the source, those joined or with up to three letters after them ("Password2024!", "P@ssw0rd12345", "qwertyuiop12"), a repeated or sequential run, and one that contains the part of the account's address before the `@` (at signup). `password-policy.test.ts`. **Residual**: it is a short list and a pattern check, not a breach check; a password that is long, unusual and already in a breach passes. A lookup against a breach service would be egress (**P8**), so it would be an opt-in k-anonymity query; not built. The message stays English like every server message.

**S-35 — Nothing bounded what the models cost in total** (**Low**). `llm/budget.ts` counts every model request (every task call through `invokeValidated`, and each round of the chat agent, owner's and recipient's) against one allowance per UTC day, `SPINE_LLM_DAILY_CALLS` (default 5000, `0` for no ceiling, a bad value gives the default); past it a call throws `ModelBudgetError` before it reaches the provider, the owner's chat answers 429 with the reason, a recipient's answers the usual 502, and the log says so once and again as the day passes 80%. `model-budget.test.ts`. **Residual**: the count is kept in the store's `usage` under the name `instance` (the same repository the relay counts in; whether it survives a restart is the configured store's property, and the device's copy counts per device); embedding requests are not counted (one short text each); the ceiling is a guard rail, and the provider's own budget alert is the control that cannot be restarted away. A large bulk import can use a real share of 5000, so raise it before one.

**S-25 — Readers of uploaded files had no resource limits** (**Low**). `pdfimages`, `pdftoppm` and `sharp` had no time limit, and `pdfimages` writes every image on a page, so a file built with huge declared images could hold an upload forever or fill the temporary directory. Now: `pdfimages` and `pdfsig` stop after 60 s (`pdftoppm` after ten minutes); a page declaring over 120 million image pixels is not unpacked, and `sharp` refuses an image over that for both stamps and photos; the web unit has `PrivateTmp`, so stamp crops are not in a shared `/tmp`; a doctor's name, specialty and clinic are cut at 120 characters and a professional code over 24 is not a code (they come from stamps, signatures and the model, all of which a sender controls). `__tests__/stamps.test.ts`, `trends-doctors.test.ts`.

**S-1 — Share scoping failed open** (**High**, **P2**). A `tag` scope with no `scope_value` skipped every branch of the scope chain and returned everything (215 documents on a running instance). `share-scope.ts` is now the one place a scope is resolved: creation rejects what it cannot resolve, and the read path re-resolves the stored row, so older rows fail closed.

**S-2 — No rate limit on `/api/auth/login`** (**High**, **P5**). Now a per-source limit (the plugin) plus an instance-wide cap (ours, because the plugin applies only its first hook per request). Per-source runs first, so an address that has spent its budget stops consuming the instance-wide one.

**S-3 — `SESSION_SECRET` fell back to a repo-published value** (**High**, **P3**). `config.ts` validates it before anything binds an interface or opens the database, reporting every problem at once; `install.sh -s` runs the same check so a bad `.env` fails at deploy, not in a restart loop.

**S-4 — Share tokens stored in plaintext** (**Medium**, **P6**). The column holds `sha256(token)`, hashed in one place so both public routes use it. Plain SHA-256 is right because the input is 256 bits of CSPRNG output. Existing links kept working: the plaintext was in the row, and the two shapes are unambiguous (43 base64url vs 64 hex), so the boot rewrite is idempotent. A row matching neither is left alone and logged.

**S-5 — No CSP, `Referrer-Policy` or `Permissions-Policy`** (**Medium**). All set, plus `object-src`, `frame-ancestors`, `base-uri`, `form-action`. `script-src 'self'` needs no exception. `style-src` carries `'unsafe-inline'` because React writes inline style attributes; inline styles cannot execute script.

**S-6 — `tag` scopes broken by double JSON encoding** (**Medium**, **P2**). Creation stored `JSON.stringify(value)` and the read path compared it unparsed, returning nothing. One module now serialises and parses.

**S-7 — The scope test could not fail** (**Medium**, **P10**). An `|| true` in the assertion. Links are now created through the real route and the returned id sets compared exactly, which also catches a scope returning *more* than it should.

**S-8 — Responses carried internal columns, server paths and live tokens** (**Low**). `SELECT *` sent absolute paths and, once multi-user arrived, `user_id` to share recipients and `file_path`/checksums from `GET /api/source-files`. Every query now lists explicit columns, and `response-shape.test.ts` scans whole responses for forbidden keys and absolute paths.

**S-10 — Failed logins unrecorded** (**Low**). Failures and successes are logged with the source address; the password never is.

**S-11 — No automated backup** (**Low**, **P11**). `spine-backup.timer` daily, `Persistent=true` so a Pi that was off catches up. `VACUUM INTO` for the database, because copying the file under load is unsafe in WAL mode. Originals are immutable, so they get a forward-only mirror. `data/pages/` regenerates and is not copied. **The vault is mirrored too** (stage 5): the sealed objects under `data/vault/<user>/` are the only copy of a person's records, and the database holds just their metadata, so a snapshot without them restores an empty account. Objects are overwritten under the same id, so the mirror copies on a different size or a newer time and drops what the vault deleted (inside a user's directory only: a missing `data/vault` cannot empty the backup); it runs after the snapshot, because an object's file is written before its row. It is ciphertext, and account deletion removes the backup's copy with the live one. `data/shares/` is left out on purpose, since a copy of a revoked share would outlive its revoke. Retention `SPINE_BACKUP_KEEP`, default 7, never below one. **This protects against corruption and mistakes, not against losing the disk**: it writes beside `data/` by default. `SPINE_BACKUP_DIR` pointed at removable or network storage makes it offsite, and that path must also be in `ReadWritePaths`.

**S-12 — Request-body keys interpolated into SQL** (**High**). `PATCH /api/documents/:id` built its `SET` clause from `Object.keys(req.body)`, and a key like `user_notes = (SELECT token FROM share_links LIMIT 1), provider` appended SQL while keeping the parameter count valid. Handlers now pass a patch object and the store maps it to columns.

**S-13 — Fastify bound `0.0.0.0` while trusting `X-Forwarded-*`** (**Medium**, **P9**). On a home LAN port 3000 was reachable, bypassing nginx's rate limit and making `X-Real-IP` attacker-controlled. It binds `127.0.0.1` unless `SPINE_HOST` says otherwise.

**S-14 — `/share/` received none of the security headers** (**Medium**). nginx inherits `add_header` from an outer level only if the inner level declares none of its own, and the `/share/` location sets two. The block is repeated inside the location, with a comment that both copies change together.

**S-15 — `GET /share/:token` returned JSON** (**Medium**). The SPA fallback excludes `/share/`, so this route alone answers a recipient's URL, and it returned `{"ok":true}` instead of the documents. It serves the app shell as `text/html` now, and a plain page for a dead link. `view_count` moved to the data route; both routes still append to the access log (**P7**).

**S-18 — No way to delete a user** (**Low**). `npm run cli -- delete-user <email> --yes` removes the account, every row it owns, its originals, page images and its copy in the backup mirror, and says what it removed; without `--yes` it only reports. Database snapshots already taken still hold the rows until retention prunes them. A deleted user's sessions end on their next request.

## Review: translation, export and import, sharing, the library

A review of what was added with translation, zip export and import, the recipient's pages and trends, and the Library, read for what each could be made to do beyond its purpose: authorisation and scoping, input handling, resource use, what changes state, what leaves the host, and injection. Method: each new route, store method and page was read with the question "what does a hostile or careless caller get", and the findings were fixed with a test (`audit.test.ts` and the tests named below) or recorded as accepted gaps above.

**Found and fixed**

- **R-1 (Medium) — A zip could start every file at once.** A request with hundreds of PDFs, or an export with many files, began reading or restoring each immediately: poppler, OCR and model calls, and their cost, all at the same time, on a Pi. Reading and restoring now go through a queue that works on two files at a time and says `queued` meanwhile (`ingestion/jobs.ts`).
- **R-2 (Medium) — Any file could be written up to the zip limit.** Raising the request limit to 2 GB for zips applied to every upload, so 2 GB of something that is then refused as "not a PDF" was written first. The limit is now chosen from the file's first bytes: 200 MB unless it is a zip (`saveStream`).
- **R-3 (Low) — A write after the limit.** The stream writer wrote one more chunk after it had stopped keeping a file, which threw. Writes are now explicit and stop at the limit.
- **R-4 (Low) — A recipient's read changed the owner's record.** The first translation of a document with no recorded language saved the language the model found, from a public route. Public reads now change nothing; the owner's next visit records it, and moves the stored translation to its new digest instead of translating again.
- **R-5 (Low) — The manifest was looser than the data it fills.** Free text could stand in for a date, a document could carry 200 tags, a test name kept its case, and the whole could be 200 MB. Dates must be in the app's form, tags are at most 50 a document, the test name is lower-cased, documents and pages are capped in all, and the manifest is at most 64 MB.
- **R-6 (Low) — Tags could split.** The model's wording and a typed "Cardiology" were different tags. Every source now goes through one cleaning (`cleanTag`), the model is given the person's tags to prefer, and the Library merges what is left.

**Checked and found sound**

- **Another user's data.** Every new store method takes the acting user and filters by it; tags, providers and tests cannot be read, renamed, merged or removed by id or name across accounts (404), exports of another account's document are a 404, and a restore writes only rows for the acting user. `management.test.ts`, `archive.test.ts` and `isolation.test.ts`.
- **The zip as a path.** Entries are read by name and never extracted to a name the zip gives; the stored file's path is made by the server; a manifest that names `../../etc/passwd` finds no such entry; an entry named `manifest.json` used as a file is not a PDF.
- **The zip as a size.** Sizes are counted as they stream, per entry and in all, whatever the zip declares; an encrypted or damaged entry fails that file, not the request.
- **What a manifest can name.** No user, no id, no path; every id is made on import; doctors from a manifest are matched into the directory the way a read doctor is, filling blanks and never overwriting; the restore is one transaction.
- **The recipient's reach.** Trends are built from the shared documents' own results and filtered to their ids (a newer value in an unshared document appears nowhere), set-aside documents are excluded as everywhere, and a tag removed from under a link makes it share nothing, not more (`audit.test.ts`). The recipient's page links only to the same link's pages, never to the owner's directory.
- **Cross-site requests.** The export is a `GET` that returns a download; the session cookie is `SameSite=Strict`, so another site cannot make the browser send it.
- **Headers and markup.** The export filename is built from letters, digits and dashes only; no new page renders HTML from data (React text only; the one existing `dangerouslySetInnerHTML` is the server-made QR code).
- **Egress.** Translation sends text only, is listed in the egress table and can be switched off; export and restore send nothing.

**Left as gaps:** S-26 (an imported export is believed), S-27 (a hostile document steers its own reading), S-28 (no upload quota), S-29 (the archive is one download), S-30 (the cost of a very large share).

## Review: attacks on sign-in and access, and on agent-built software

Reviewed 2026-10-18, after the chat, share-approval, recipient-chat, chat-action, notice, regrouping, attachment and matching work (commits `f8365aa` to `185855f`). Two questions: which attacks on sign-in and access are common now, and what is specific to software built with a coding agent and to software that contains an agent. Method: the sources below for the attack classes; then for each class a check against the code, and for each recent feature a read of its section in this document against the code and tests. **Checked** means a command was run or a file read in this review (the unit suite passed: 71 files, 1,262 tests; `npm audit`; a reproduction of S-31); it does not mean a real browser or the real model was driven, and nothing here was tested by an outside party.

### Sources

- OWASP Top 10:2025 [A07 Authentication Failures](https://top10.owasp.org/2025/A07_2025-Authentication_Failures): credential stuffing and password spraying, brute force, default credentials, session ids in the URL or kept across login, weak recovery, missing or ineffective MFA, no invalidation at logout; prevention is MFA, a check against the worst and breached passwords, identical failure messages, rate limiting with alerting, a fresh session id.
- [Session cookie theft bypasses MFA](https://thehackernews.com/expert-insights/2026/04/session-cookie-theft-you-showed-your-id.html) and [pass-the-cookie defences](https://cside.com/blog/cookie-theft-session-hijacking-and-how-to-stop-pass-the-cookie-attacks): infostealers and adversary-in-the-middle phishing take the post-login cookie; the structural answer is a session bound to a device key (Device Bound Session Credentials).
- OWASP [Top 10 for LLM Applications 2025](https://www.gravitee.io/blog/owasp-top-10-for-llm-applications-2025-a-practical-guide): prompt injection, sensitive information disclosure, supply chain, improper output handling, excessive agency, system prompt leakage, vector and embedding weaknesses, misinformation, unbounded consumption.
- OWASP [Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026) (list as summarised by [HUMAN](https://www.humansecurity.com/learn/blog/owasp-top-10-agentic-applications/); the full text was not available to read): goal hijack, tool misuse, identity and privilege abuse, agentic supply chain, unexpected code execution, memory and context poisoning, insecure inter-agent communication, cascading failures, human-agent trust exploitation, rogue agents.
- Indirect prompt injection in the wild: [Unit 42 (March 2026) and Google (April 2026) as reported](https://www.radware.com/cyberpedia/prompt-injection/): hidden instructions in pages, PDFs, mail and shared documents, and the "lethal trifecta" of private data, untrusted content and a way to communicate out.
- Code written by agents: [vulnerabilities in public AI-generated code](https://arxiv.org/pdf/2510.26103), [security degradation over refinement rounds](https://arxiv.org/pdf/2506.11022) (critical findings up 37% after five rounds), [security-related AI pull requests](https://arxiv.org/pdf/2604.19965). The classes that recur: injection, path traversal, weak randomness, missing authentication or authorisation, hard-coded secrets, insecure defaults.

### Attack classes against sign-in and access

| Attack | Where Spine stands |
|---|---|
| Credential stuffing, password spraying | Argon2id, identical answer and time for an unknown email (**M-3**), per-source and instance-wide limits. The per-source limit keys on the address nginx saw (**S-31**, fixed) and common or patterned passwords are refused (**S-34**, fixed; a breached unusual one still passes). Optional TOTP (**S-20**) is the real defence and is not required. |
| Brute force of the second factor | Per user 5 per ten minutes, pending login dropped after five, replay blocked (**M-12**). Holds, because the per-user limit does not depend on the source. |
| Account enumeration | Signup, forgot and reset answer identically; the residual timing difference is stated (**M-6**). Sound. |
| Session fixation | New session id at login and at the second step; password change ends other sessions (**M-4**). Sound. |
| Session theft, pass-the-cookie, adversary-in-the-middle | **Reduced (S-33, M-27)**: 24 hours idle and 14 days in all, a list the owner can end, the password asked again before the whole export and before a link shows page images, mail on a new browser. A stolen cookie still works until idle or ended. `HttpOnly`, `Secure`, `SameSite=Strict` and the CSP stop web-side theft only. |
| Password reset poisoning (a forged `Host` header in the mailed link) | Closed by design: links are built from `SPINE_DOMAIN`, never from the request (`config.ts` `publicUrl`). Tokens are hashed, single-use, in the fragment, spent by `POST` (**M-11**). Sound. |
| Mail scanner or link prefetch spends or approves something | Verification and reset are `POST`; share-request approval is a `POST` from a signed-in session (**M-19**). Sound. |
| Rate-limit bypass by header spoofing | **Closed (S-31)**. Reproduced, fixed at nginx and in Fastify, tested. |
| MFA fatigue, SIM swap, SMS fallback | Not applicable: TOTP only, no push, no SMS, no email-code fallback. The fallback is recovery codes, then the operator (**M-12**). |
| Attacker enrols their own authenticator | **Accepted (S-22)**; enabling or disabling two-factor now ends the other sign-ins and mails the account (**M-27**), so it is noticed. |
| Leaked share link | Hashed token, expiry, revocation, optional owner approval of each browser, access log (**M-19**, **M-22**). The raw token is in nginx's log (**S-19**). Sound within its stated limits. |
| Insecure direct object reference between users | The structural control (**P12**, **M-1**) and `isolation.test.ts` as a second user. The class most often found in agent-written code, and the best defended here. |
| Vulnerable or malicious dependency | **Closed for today (S-32)**: Fastify 5, audit clean, build and CI gate. New advisories arrive at the next build. |
| Server-side request forgery, command injection, path traversal | The server fetches no user-supplied URL; poppler, sharp and `pdfsig` are called with server-made paths and time limits (**S-24**, **S-25**); zips are never extracted to a name they choose (**M-14**). SQL identifiers come from a whitelist (**S-12**). Sound; **S-24** is accepted. |

### Attacks on the agent features

| Risk (OWASP) | Where Spine stands |
|---|---|
| Prompt injection, direct and indirect (LLM01, ASI01 goal hijack) | A scanned document, a forwarded PDF or a translation can carry instructions (**S-27**). Held to: no tool writes, an action tool returns a proposal the owner confirms with the words drawn by the page (**M-21**), the model's answers to the linking and grouping tasks are proposals (**M-16**, **M-24**), prompts say text is data. Not preventable by checking, bounded by design. |
| Excessive agency, tool misuse (LLM06, ASI02) | `TOOL_KINDS` holds every tool `read` or `action`, a test fails otherwise, a tool takes labels and never an id or a user, and caps on rounds, characters and time (**M-18**). Sound. |
| Identity and privilege abuse (ASI03) | The user id comes from the session into the graph's state, never from an argument the model writes; the recipient's agent is built without the owner's tools and held to `listForShare` in code (**M-20**). Sound; the one deliberate widening, **M-23**, is for the owner's own unconfirmed upload. |
| Data exfiltration through output (LLM05, "lethal trifecta") | The page renders the model's text as React elements with no image and no arbitrary link (checked: `Markdown.tsx` writes none; citations become links to the owner's own documents), and the CSP has `img-src 'self'` and `connect-src 'self'`, so a markdown image to another host cannot load. The first leg is the document, the second the owner's data, and the third (a way out) is closed. Sound. |
| Sensitive information disclosure (LLM02) | Egress is enumerated and switchable (**P8**); the recipient's chat sends the shared documents' cards, notes and the link's label, which is stated beside the checkbox (**M-20**). Sound. |
| Vector and embedding weaknesses (LLM08) | Vectors are per user, behind the store, never exported or returned (**M-15**). Sound. |
| Unbounded consumption (LLM10, ASI08 cascading failures) | Per-route limits and an instance-wide daily allowance (**S-35**); there is no agent-to-agent hop. |
| Human-agent trust exploitation (ASI09) | The risk is that the owner presses Confirm on what a hostile document made look reasonable. Mitigated by showing every proposal in full from data, starting security options at the safe setting, and capping a proposal's size (**M-21**). A person can still be wrong; there is no stronger control short of removing the feature. |
| Memory and context poisoning (ASI06) | Stored conversations are history only: the model sees them with citation markers stripped, but a past answer that a hostile document steered is in it. Bounded by the same limits as the first row; conversations can be deleted. Accepted with **S-27**. |
| Unexpected code execution, supply chain (ASI05, ASI04) | No model output is executed or evaluated. Dependencies: **S-32**. No vendor package above `llm/adapters/` (reviewed in the checklist). |

**Not verified here:** that nginx and Fastify together behave as the configuration reads in a deployed instance (S-31 was reproduced against Fastify alone, with the header nginx would send); the real model's response to a hostile document; the sidecar and a real page image (still the status note above); whether each advisory in **S-32** is reachable. **Afterwards (same day):** S-31 to S-35 were fixed, each with tests, and S-36 was started with `scripts/check.sh` and a GitLab pipeline; the scanners ran locally and their findings are dealt with, the pipeline itself has not run.

## Multi-user

The requirements multi-user put on the design. All are implemented; the controls they produced are in [Controls in place](#controls-in-place).

**M-29 — Documents are read after the owner confirms the grouping, so the text goes to the provider once, for the grouping that was approved.** **P8, P12.** Nothing about egress is new: the same page text goes to the same provider, with the same refusals (**M-8**), for the same extraction. What changed is when. Before, an upload was parsed, grouped and every document read in one run, and a grouping the owner then fixed by hand sent the changed documents' text again ("Done"). Now the pipeline stops after the pages and the proposed grouping (`needs_reading = 1` on each document; no title, summary, fields, results, tags, doctors, stamps or signatures), and `POST /api/source-files/:id/grouping/confirm` starts `read-upload.ts`, which reads each marked document once, files the doctors named by stamps (images, so only with the switch, **M-7**) and digital signatures, and only then confirms the grouping, so a document is never visible half-read (**M-17**). The confirm route answers 202 while it runs and 200 when nothing is left to read (an older upload, a restored one); it takes the owner's session and the upload must be theirs; one reading runs per upload (`isReadingPages` is true meanwhile, so a move, a split or a regrouping answers 409). Marking is by the server, not trusted from the page: a move, a split, a join, a page set aside and a regrouping each set `needs_reading` on the documents they touched, and `POST /api/source-files/:id/extract` on an unconfirmed upload reads nothing and marks. What the assistant sees: `get_upload` says "NOT READ YET" for such a document and its prompt says to judge the grouping by its pages (**M-23**, `read_pages`). **Failure**: a model that cannot read any document fails the reading with the upload still unconfirmed; one that cannot read some leaves them marked, and the rest proceed. The marker, a number, is returned to the owner on the upload screen and nowhere else; no share route returns it (the documents of an unconfirmed upload are not shared). `chat-notices.test.ts` (the two stages), `pipeline.test.ts`.

**M-31 — Files that are converted on arrival are decoded by libraries that read what a stranger could craft.** **P5, P8.** HEIC (`heic-convert`, WebAssembly), a Word document (a zip read through `ZipReader`, one entry of at most 30 MB, at most 2,000 entries, never extracted to a path) and a text file (at most 2 MB) are turned into a JPEG or a PDF (`ingestion/convert.ts`). A decoder fault is caught and the file refused as `not_pdf`; the WebAssembly decoder runs inside the server process, with its memory bound by the 200 MB upload limit, so a hostile HEIC can spend memory and time but not reach the host. The text taken from a Word document is escaped nowhere because it is never interpreted: it goes onto a PDF page as text. Nothing leaves the host for a Word or text file (the text parser reads it); a HEIC is a photo and needs `SPINE_MULTIMODAL_ENABLED` like any. **Not covered**: macros and embedded objects are ignored, not scanned; a HEIC is decoded once at upload, so a decoder CVE is reachable by any signed-in user (`npm audit` gates the build, **S-32**).

**M-32 — A share link can name episodes, and what it shares follows the episodes.** **P2, P12.** `scope: 'episode'` takes up to 50 episode ids; creating or changing a link accepts only ids that are the owner's **confirmed** episodes (one answer for "not yours", "not confirmed" and "does not exist", **M-5**, in `checkScope`), and the read path re-resolves the stored value (`share-scope.ts`, **P2**). `documents.listForShare` reads the documents of those episodes **at read time**, through `VISIBLE` (a document set aside is not shared) and only while the episode is still confirmed and the owner's: an episode since dismissed or removed shares nothing, and a document added to a shared episode is shared from then on, which the creation form says. Episode ids are never returned to a recipient, and an episode's title (the owner's own words) is not part of any public route. `episodes.test.ts` covers growth, dismissal, a stranger's episode, an unconfirmed one and a missing one.

**M-33 — A passkey is a second way to sign in, and is both factors at once.** **P1, P5, P13.** `routes/passkeys.ts`: WebAuthn through `@simplewebauthn/server`, relying party = the host of `SPINE_DOMAIN` (`passkeys.ts`), attestation `none`, **user verification required** at registration and at every sign-in, resident keys required (so no account name is asked or leaked). Only the public key, a counter and a name are kept (`user_passkeys`, deleted with the account); the credential id is unique across accounts. **Sign-in** is two public calls, both rate limited per source and instance-wide: `/api/auth/passkey/options` makes a challenge and regenerates the cookie session, which carries it; `/api/auth/passkey/login` takes it out of the session **before** verifying (one try, five minutes), checks origin, relying-party id, user verification, signature and that the counter has not gone back (a cloned key), refuses an unknown key or an account whose address is unconfirmed with one answer, regenerates the session again and calls `startSession`, mailing a new browser. It is therefore the **second place a session is issued** (`second-factor.test.ts` guards the list) and it does not ask for a code, because user verification makes the passkey possession and the person together; an account with two-factor sign-in on can still be entered with the password route only through its code. **Managing** them: add and remove need a session and the password typed in the last ten minutes (`requireRecentAuth`), adding is limited to ten, both are mailed (so a stolen cookie cannot quietly add its own way in), a passkey of another account is a 404. **Not covered**: a lost device is handled by the operator's `set-password`/`disable-2fa` and by removing the passkey from another one; there is no attestation check of the authenticator's make; a synced passkey (iCloud Keychain, Google Password Manager) is as safe as that account is. **Opening the vault** (stage 5 addition): a passkey whose authenticator supports the PRF extension can also open the vault. The device makes a key from the PRF output, seals the account key under it and sends only that (`PUT /api/auth/passkeys/:id/vault-key`: signed in, password typed lately, mailed; a sealed value of the right shape; one's own passkey); the server stores it as ciphertext on the passkey's row, returns it with that passkey's sign-in, and never receives the PRF output, which the browser removes from the ceremony before sending it. The extension is asked for at registration. Removing the passkey, or turning the option off, removes the sealed copy; a copy that no longer opens (a vault made again after an erase) falls back to the master password. Tests: `passkeys.test.ts`, `crypto.test.ts`, and `npm run check:app` with Chrome's virtual authenticator.

**M-38 — Several devices on one account: records travel as sealed changes (syncing, after stage 5 of the encryption redesign).** **P1, P12.** The device no longer saves its database as pieces of a file. Every write to a records table is noted by a trigger as a change of one row; a save turns the notes into **changes** (`{table, key, row or null, clock}`, a hybrid logical clock that sorts as text, `store/sqlite/changes.ts`), seals them as one **segment** (`log` object, `core/persist.ts`) and never rewrites an object. Other devices find new segments by listing the vault, open them and apply them; **the newest change to a row wins** and a deletion is a change, so two devices that edit different rows keep both edits and two that edit one row agree on the later one. A device folds the segments it has applied into a **snapshot** (sealed `bundle` parts) named by the index (the one object written over, with the sequence number it was read at); the segments it folded are deleted and a device that was away loads the new snapshot over what it has (the same rule, so nothing is lost). What the server sees is what it saw before: object ids, kinds, sizes, sequence numbers and times; a segment's size and time say how much the person did and when. **Things that would make devices collide, and what is done**: keys that were the engine's counter (tags, the share log) are random numbers; the tags a new account starts with have the same key on every device; a tag or doctor made on two devices with the same name becomes one (the later arrival is kept as another name for the first and the rows that point at it are redirected); anything else that must be unique (a page's place in an upload) goes to the newer change. Rows that point at a row that never arrived or was deleted are removed after a merge. The search index is rebuilt from the records after changes arrive, and is not synced. **The change form names tables and columns, not an engine's pages**, and the share copy and the saved snapshot are the same form, so the store behind them can change. A vault of the earlier kind (a database file in pieces) is converted on its first unlock, and its pieces are removed. **Residual**: the clock is each device's own time, so a device with a wrong clock can win edits it should not (a change is stamped when it was written, not when it was sent); a conflict between two edits to different fields of one row keeps one whole row, not both fields; a tag or doctor merged from two devices keeps two different keys for one name (each device redirects the other's); the owner's page does not refresh itself, it says another device made changes and offers a reload. Tested by `changes.test.ts` (two stores that write and exchange), `persist.test.ts` (segments, snapshots, a device that was away, files), `boot.test.ts` (starter tags once, a deleted tag stays deleted, an earlier vault converted) and `npm run check:app` (two browsers on one account remove different tags at the same time and both end with both removals).

**M-37 — The server serves no route that reads or writes a record (stage 5 of the encryption redesign).** **P1, P2, P12.** `server/src/index.ts` registers the account (`auth`, `totp`, `sessions`, `accounts`, `own-account`, `passkeys`), the vault, the relay's pass, the sealed shares (`shared`) and the address a recipient is given (`shareShellRoutes`: `GET /share/:id`, the app shell for a share that exists, a plain 410 page otherwise, no record read), and **nothing else**: the routes for documents, uploads, export, similarity, links, episodes, the sample records, chat, share links, tags, trends and doctors are not served, so the server neither accepts a record in plaintext nor writes originals or page images to its disk. Those route files stay in the repository because the device's core runs them (`web/src/core/boot.ts`) over the store it holds; the tests register them, so they hold the code the device runs. **A test cannot say that the server does not register one**; `npm run check:app` does, since the page works against the real server with them absent and finds no readable record text in its files. A new route that handles a record goes in the device's core, never in `index.ts`. **The server's database has no table for a record**: it is made from `schema-accounts.sql` alone (`SPINE_STORE_SCOPE=accounts`, set by `index.ts`, the CLI and the backup), the repositories of records refuse to be used there, and `accounts-scope.test.ts` lists its tables; the device builds the accounts' and the records' schema (`schema-records.sql`). `npm run test:accounts` runs the server's tests on that database with only the routes `index.ts` registers, so they cannot drift from what runs. **Left**: an older `spine.db` made with all the tables keeps them until it is deleted, and and nothing has been audited. The backup (**S-11**) holds the vault's ciphertext.

**M-36 — Encrypted share links: a copy the server cannot open (stage 4 of the encryption redesign).** **P1, P2, P6, P7, P8, P12.** A link is no longer a row the server resolves at read time. The **owner's device** makes a copy of what the link shares, built in a store of its own and sent as **changes** (the form records travel in between devices, **M-38**; not a database file) (`store/sqlite/slice.ts`, an **allow-list**: each table names the columns that are copied, every other column stays empty, so the owner's e-mail, file names and paths, word boxes, doctors' professional codes, the app's reasons for a link between documents, notes the owner did not share, and any table not named are out; page text and snippets only if the recipient may ask questions, page images only if scans are allowed; `slice.test.ts` looks at every table of a copy built from records that include things that must stay out), seals it with XChaCha20-Poly1305 under a **random share key** (context bound to the share's id and the part's name, `core/share/keys.ts`), and sends it to the server (`PUT /api/shared/:id`, page images as numbered sealed files beside it). **The key is in the address after the `#`**, which a browser does not send to a server (a check in `npm run check:app` asserts no request the server saw contained it, and the page takes it out of the address bar after reading it). **Approval mode**: the address has no key. The visitor's browser makes an X25519 key pair and asks (`POST /api/shared/:id/access-request` with the public key); the owner's device collects the request (`GET /api/shared/events`, acknowledged once), and on approval **seals the share key to that public key** (libsodium sealed box) and sends only that (`POST /api/shared/requests/:id/decision`); the visitor's browser polls, opens it with its private key (kept in that tab's session storage) and then reads the copy. A leaked link opens nothing; a copied link is useless in another browser. Changing the approval setting, or what a link holds, publishes again, and the approval setting changes the key, so an address handed out earlier stops opening. **The server** (`routes/shared.ts`, tables `shared_bundles`, `shared_requests`, `shared_opens`, files under `<data>/shares/<id>/`) stores sealed bytes and these facts: when it ends, whether it needs approval, sizes. It ends a share at its time (a read of an ended one, an hourly sweep, and at start) and on revoke by **deleting the files and forgetting every wrapped key** immediately; the row stays 30 days so a late visitor is told it ended. Limits: `SPINE_SHARE_MAX_MB` (100 a part), `SPINE_SHARE_MAX_TOTAL_MB` (1024), `SPINE_SHARE_MAX_LIVE` (50); a share lasts at most 31 days. The public routes are known only by the random id (36 characters), rate limited, and answer with metadata and sealed bytes; access requests are limited per source and per link, at most five wait at once, a note is cut and cleaned. **What visitors did** reaches the owner without the server learning what was read: the recipient's browser says it opened the link or a document (`POST /api/shared/:id/opened`, the id inside the sealed copy), the server keeps the time and the country (from the address, which it does not keep) until the owner's device collects it, and the owner's own records (not the server's) hold the log. A recipient who does not report is not logged: the log says what browsers said. **The recipient reads with the same route code** the server used (`publicShareRoutes`, run on the device by `LocalApp` over the copy, `core/boot-share.ts`), so scope, approval and the rules of what is shown are unchanged; translations and questions go through the relay with a **pass for that share only** (`POST /api/shared/:id/relay-token`, its own end time at most, counted against the share, `share:<id>` as the account). **What a recipient holds**: the whole copy, in memory, readable with the browser's tools: the copy is the access, so it holds only what the link shares. **Live**: a link follows the owner's records for as long as it lasts. After the records change, a moment later (15 s) the owner's device builds each live link's copy again and sends it only if it would hold something different (a keyed hash of its content is kept beside the link's key, `share_link_keys.copy_digest`; `POST /api/share-links/refresh`), under the key it was made with, so a deleted document leaves a copy within about twenty seconds of a device that is open. A device that is closed does not refresh: until one is opened, a copy shows what it last held. A link that shares nothing any more is answered as not usable (it fails closed). **Not yet / residual**: the owner's device must be unlocked to approve a request and the mail only says someone asked; the log depends on the recipient's browser reporting; Anthropic cannot be used for a recipient's questions; the old server-side share routes and tables still exist until stage 5; nothing has been audited. The server's own tests (`shared.test.ts`, `share-host.test.ts`, `slice.test.ts`, `isolation.test.ts`'s public-route list) and `npm run check:app` (owner makes a link, a stranger with no account opens it, the owner sees it was opened, revoke, approval) hold it.

**M-35 — The relay: where a device's model calls go (stage 2 of the encryption redesign).** **P1, P5, P8, P13.** A device cannot hold Spine's credential, so its model calls (reading a page, extraction, summaries, translation, linking, grouping, chat, embeddings) go to `server/src/relay/` with a pass from the Spine server. **The protocol is neutral** (`relay/protocol.ts`): the device names a task from `llm/tasks.ts` and sends LangChain messages (`POST /v1/task/<task>`; the agent also gets the tools' declarations and may stream, one JSON line a piece) or texts to embed (`POST /v1/embed`), and the relay runs them through the same provider adapters the server uses (`llm/adapters/`, picked by the relay's own `SPINE_LLM_PROVIDER`: Vertex or Anthropic today), so a provider is one adapter file and the device never knows which answered. **The pass**: `GET /api/relay/token` (signed-in accounts only, `routes/relay.ts`) gives an HS256 token (the JWT shape, `relay/token.ts`, no library) for the account's id, valid ten minutes, signed with `SPINE_RELAY_SECRET` (at least 32 characters, shared with the relay and nothing else); `GET /api/relay/config` gives the device the settings it needs to behave as the server does (the `SPINE_LLM_MODEL(S)`, parser and feature switches, from an allow-list that holds nothing secret; the provider is set to `relay` and the endpoint to the relay's host; nothing of the real provider's project or region), and a 503 `no_relay` when the instance has none. **What the relay checks** (`relay/relay.ts`, `relay.test.ts`): a valid unexpired pass (401), a path that is one of the tasks or `/v1/embed` (404 for anything else), no query (400), a body that parses against the protocol's schema with message types human, ai, system or tool only (400), a model the relay was configured to offer (400), a body under 32 MB (413), and the account's daily allowance of calls, `SPINE_RELAY_DAILY_CALLS` (default 500; 429), counted in the `usage` repository of the store the relay is configured with (`SPINE_STORE`, `DATA_DIR`/`SPINE_DB_PATH`, chosen as the model provider is; table `model_usage`, a number a day per account), so it survives a restart and is shared by instances that reach the same store; with `SPINE_DB_PATH=:memory:`, the relay image's default, it is per process and one instance gives an exact count. A tool the device names is a declaration handed to the model, never run by the relay. Nothing the device sent besides the messages, its cookies and address included, reaches the provider. A Google API key in the relay's environment stops the Vertex adapter at start (the same residency rule as **M-8**). **What it does not do**: it **stores nothing and logs no content**: one line a call with the task, model, status, request size and time; a provider's own error text, which may quote what was sent, is not passed back (a refusal by the model is said as `blocked`). A test fails if a content word reaches a log line, and another if `relay.ts` imports anything but the protocol, the token check, the task and embedder types, the `UsageRepository` type, LangChain's message and chat-model types and Node's HTTP module. Cross-origin calls are allowed only from `SPINE_RELAY_ORIGIN`, and the page's content security policy names the relay (`connect-src 'self' <SPINE_RELAY_URL>`; `img-src` gained `blob:` for pictures held on the device). **What it can see**: everything that passes through it, in plaintext, because it ends the TLS connection; it is the one place outside the browser that does, together with the provider. Product text therefore says it does not store or log content, and never that it cannot see it; an enclave relay with attestation is a later step and is not built. A failure of the relay's operator (or of its provider credential) exposes what is in flight, not what is stored. **Device side**: `llm/adapters/relay.ts` (the `relay` provider: one client per task, and a chat model for the agent that sends each call to the relay), `embedding/adapters/relay.ts`, and `web/src/core/native/relay-auth.ts` (fetches and reuses passes; hooks set by the device). **Not yet**: the relay's quotas are shared only through a store every instance reaches (the SQLite adapter is a file; no networked adapter exists), the model-call budget (`SPINE_LLM_DAILY_CALLS`) is counted per device, and the provider's zero-retention checklist in the requirements is the operator's to do in the provider's console (`docs/relay.md`). `npm run check:app` runs a page against the real relay code with a stand-in model (`relay/stand-in.ts`), or with `SPINE_CHECK_REAL=1` against the configured provider on invented records.

**M-34 — The vault: keys and records the server cannot read (stage 1a of the encryption redesign).** **P1, P2, P3, P13.** `docs/crypto-design.md` is the plan and `docs/key-hierarchy.md` the public design; this is what is built. **On the device** (`web/src/crypto/`, libsodium): Argon2id over the master password with the account's random salt (64 MiB, 3 passes by default; the server refuses a cost under the OWASP minimum, `vault-keys.ts`), then two separate subkeys: the **master key**, which never leaves the device, and an **authentication value**, which is sent *in place of the password* and hashed again by the server's own argon2id, so the existing login, rate limits, second factor, passkey, reauth and session code are unchanged and the server cannot go from what it holds to the master key. A random **account key** is sealed under the master key and again under the **recovery key**; an X25519 pair has its private half sealed under the account key; a **profile key** is sealed under the account key; each object has a **data key** sealed under its profile key. Sealing is XChaCha20-Poly1305 with a random nonce and the object's kind and id (or the key's purpose) bound in as associated data, so a sealed value cannot be moved elsewhere and still open (`seal.ts`, tested). The **recovery kit** is 256 bits written as 56 base-32 characters (52 and a four-character check, so a typing error is caught), shown once before anything is sent, printable, and replaceable from the account page (the old one stops working). **On the server**: `vault_keys` (the salt, the cost, the account key sealed twice, the public key, the sealed private key, a change counter) and `vault_objects` (opaque id, owner, profile id, a coarse kind, change number, size, the sealed data key, a tombstone flag), with the ciphertext in `<data>/vault/<user>/<id>` (`vault-files.ts`, ids held to a safe alphabet because they reach the file system). `routes/vault.ts`: `POST /api/auth/kdf` (public, rate limited; an address with no vault gets a salt made from the address and `SESSION_SECRET`, so it does not say which addresses have accounts, except that an account made before the vault answers `vault: false`), `GET`/`PUT /api/vault/keys` (the first needs a session, making a vault needs the password typed lately and replaces the credential the server knew), `POST /api/vault/keys/rewrap` (a new master password or kit: the same account key under new wrappings, mailed, other sign-ins ended), and `GET`/`PUT`/`DELETE /api/vault/objects[/:id]` with optimistic concurrency (a write names the change number it last saw, 409 otherwise), a tombstone so other devices learn of a deletion, `SPINE_VAULT_MAX_MB` (5120) for an account and `SPINE_VAULT_MAX_OBJECT_MB` (100) for one object. **Sign-up** sends the derived value and the keys (`routes/accounts.ts`), no password and no policy check on the server; the master password's policy runs on the device (`password-policy.ts`, the rule the server used to apply). **Reset by email** can set a new credential but cannot reach the records: `POST /api/auth/reset/keys` hands a link holder the recovery-wrapped key (sealed, no use without the kit; the link is not spent), the device opens it with the kit and seals the same account key under the new password, and `POST /api/auth/reset` takes the new credential and keys; **without the kit** the only way on is `erase: true`, which removes every object and starts an empty vault, and the page says so first. A password cannot be set by reset or by the operator's `set-password` on an account that has a vault. The CSP gained `'wasm-unsafe-eval'` for libsodium's WebAssembly. **Not yet**: nothing the app stores is sealed (stage 1b moves the working database onto the device), passkeys cannot unlock the vault (a passkey sign-in gets a session; the vault asks for the password, PRF later), the unlocked keys live in page memory and are forgotten on reload, an account without a vault (one the operator made with `create-user`) signs in once with the password it was given and makes its vault then (the form sends the password as the credential for such an account; this stays, it is how an operator-made account starts), the web bundle carries libsodium (about 1 MB; to be split), and nothing has been audited or tried in a real browser. `vault.test.ts` (server) and `web/src/crypto/*.test.ts`, with `web/src/e2e/vault.e2e.test.ts` driving the device's code against the real routes, hold all of it.

**M-28 — A recipient sees the documents connected to a shared document, but only shared ones, only confirmed links, and nothing about how they were made.** **P2, P7, P8, P12.** `GET /api/share/:token/documents/:id/connections` goes through `openLink` like every share data route (live link, approval, scope, access log, 120 a minute) and answers 404 for a document the link does not share. It returns two things. **Connected documents** (the owner's care chain, renamed in the interface): links in state `confirmed` whose *both* ends are in `listForShare(link)`; the walk (`sharedChainOf`) does not step through a document that is not shared, so a chain A, hidden, C shows nothing; it returns nodes (id, title, type, date, provider, as the list already shows) and edges as direction and kind only. A suggestion, a dismissed link, who made a link, the model's one-sentence reason and a confidence are never sent. **Similar documents**: `relatedTo(..., within)` with the shared ids applied *before* ranking, so a test or doctor in common, or closeness in meaning, ranks only shared documents; reasons are the kind and the names of the shared tests or doctors (both documents already show them to the recipient), with no score and no tags or provider. No vector, no card and no model call is involved beyond what already exists: the comparison is in memory over vectors the server already holds. **Writes nothing** (R-4; `share-connections.test.ts` compares the owner's links before and after). **What it does not do**: it does not hide that two shared documents are connected (that is the point); it does not show the owner that a link exists to something not shared; it adds no way for a recipient to create or confirm a link. The route is on the public allow-list in `isolation.test.ts`, justified here. The recipient's chat is unchanged: its agent has no care-chain tool (**M-20**). **Naming**: the interface says "Connected documents" for confirmed links and "Similar documents" for the computed list; the code and this document keep "care chain" and "related" for the same things.

**M-27 — A sign-in is a row the owner can see and end; the cookie alone is not enough.** **P13.** Closes **S-33**. The cookie session is still in memory (**S-16**), and `user_sessions` (`user_id`, created, last seen, the browser's user agent and address as the connection reported them, which prove nothing) is what makes it valid: `authenticate` looks the row up on every request and signs the request out if it is gone, past the idle limit (24 hours, `SPINE_SESSION_IDLE_HOURS`) or past the absolute one (14 days, `SPINE_SESSION_DAYS`; values above 30 days and 90 days are cut, a bad value gives the default, never a longer session). `startSession` is the one function that assigns `session.userId`, called only by the two login steps (`second-factor.test.ts` fails on any other caller); logging out removes the row. The list (`GET /api/auth/sessions`) is the owner's, never carries a cookie or a token (a row's id is a random value that only names it), and `DELETE /api/auth/sessions/:id` and `POST /api/auth/sessions/end-others` end them; another user's row is a 404. A password change, a reset, and turning two-factor on or off end every other sign-in. **Asking again**: `POST /api/auth/reauth` takes the password and, with two-factor on, a current code; it limits guesses per user (5 in ten minutes) and per source, and sets a timestamp in the session. Within ten minutes of that (a fresh sign-in counts), `GET /api/export` and a share link with `include_scans` (creating it, or turning it on) go through; otherwise they answer 403 `reauth_required` and the page opens a dialog and repeats the request. **Telling the owner** (only with a mailer, after the response, no clinical words, no address): a sign-in from a browser the account has not used (a random cookie, kept as `sha256` in `user_devices`; the first sign-in of an account tells no one), a password change, and two-factor turned on or off, which is what makes **S-22** (an attacker enrolling their own authenticator) noticeable. What it does not do: it does not make a stolen cookie useless, only short-lived and visible (**S-33** residual).

**M-1 — Owner-scoped store layer.** **P12.** Every user-owned table has a `user_id`, and every statement in `store/sqlite/` filters by it. Handlers cannot write queries. There is no `find(id)` without a user, and a method called with no acting user throws.

What a method does with a record the caller does not own: a read returns nothing, an update or delete changes nothing, and a create that names such a record throws and inserts nothing. Routes check first and answer 404, never 403, so a record cannot be probed for.

Four exceptions, enumerated in `store/types.ts` so a fifth has to be argued for: share-token resolution and `listForShare` (scoped by the link's owner, never by a session); `logAccess` (the reader is unauthenticated); `maintenance.*` (boot-time work); and `users.*` (the identity layer: login must find a user before there is an acting user).

`__tests__/isolation.test.ts` runs as a second user against the first user's data across every route and every repository method, and fails when the search filter or the share ownership check is removed. Removing only the inner tag-owner check in the tag-scoped share query does *not* fail it, because the outer `d.user_id` already excludes other users' documents; that one is defence in depth.

**M-2 — Owner-aware full-text search.** The FTS index stays shared; results are filtered by joining back to `documents.user_id`. The index now also holds page text, values and doctor names (the most sensitive text in the system), so what makes it safe is that each row is built only from the owning user's rows and is only reachable through that join; a test searches for another user's page text, value and doctor name and finds nothing. Typed text is quoted, never passed as query syntax. Tested.

**M-3 — Credential storage.** **P13.** argon2id, 19 MiB / 2 passes / 1 lane (the OWASP minimum), per-hash salt, 12–256 characters. About 30 ms per hash on a laptop-class CPU; not yet measured on a Pi. An unknown email runs a dummy verification so it is neither faster nor different in answer.

**M-4 — Session invalidation on password change.** **P13.** `users.auth_version` is bumped on a change; a session carries the value it was issued under and is refused once it no longer matches. Every request re-resolves its session, so this takes effect on the next request. Login also issues a new session id.

**M-5 — Share creation verifies ownership of the scope.** A `document_ids` link naming a document the creator does not own is rejected at creation, with one message for "not yours" and "does not exist".

**M-6 — Login and registration throttling.** **P5.** Login: per source and instance-wide (S-2). Signup, resend, forgot and reset: per source **and per email address**, so they cannot be used to flood an inbox; the address limit is `rate-limit.ts`, because the Fastify plugin cannot stack two limiters on one route.

Signup is `SPINE_REGISTRATION=open`, default `operator`; `open` with no mailer fails at startup (**P3**). Verification is mandatory: an unverified account gets no session, and the right password before confirming answers 403 with a code the page uses to offer a new link. A taken address is answered exactly like a new one — same body, same status, no mail — and its password is not touched. **Residual:** a new address does a few more database writes than a taken one, so the timing is close but not identical; the mail itself is sent after the response, which is the large part.

**M-7 — Explicit opt-in for image egress.** **P8.** `SPINE_PARSER` defaults to `text`, which sends nothing (as does `ocr`). The parsers that send page images, `multimodal` and `hybrid`, need a **second, separate switch**, `SPINE_MULTIMODAL_ENABLED=true`, and are refused at startup without it: in `config.ts`, and again in `createParser`, which decides whether an image can leave and does not rely on its caller. The second switch alone does nothing, so picking a parser never turns egress on by implication. Photos chosen together and made into one upload (`upload-photos`) follow the same rule: refused as a whole, with nothing kept, unless the switch is on, each is checked by its bytes, at most 40 are taken (the rest of the request is drained, not saved), the route is rate limited, and the temporary copies are removed whatever happens.

Signature stamps (`ingestion/signatures.ts`) are a second, smaller image egress under the same switch: each document's last page contributes at most four small pictures that look like a stamp (a doctor's name, specialty and code; no clinical content), never the page; nothing runs with the switch off, and a test asserts that no image is sent then. Each send is logged with the number of images.

The startup log states the result (`imageEgress: true`, plus a warning naming the provider and endpoint); each image sent is logged, and every page logs its route and the figures behind it. In `hybrid`, an image is sent only for a page with **no text layer** that **local OCR could not read confidently**, never a page that has a text layer (a test asserts it). There is no LLM screening step: looking at an image to decide whether to send it is the same egress as sending it.

**A second route: reading again.** "Read page with AI" (on the document page) sends only that page's image through the same model parser, so the same switch applies and nothing new decides whether an image can leave. It acts only on the caller's own pages (a page of another upload, or another user's, is refused like one that does not exist), takes at most 200 a request, runs one reading per upload at a time, and asks first, naming the number of images and the destination. A page the model cannot read changes nothing. "Read whole document" (the same route with `strategy: "configured"`) reads a document's pages with the parser the operator configured, so it sends an image only when that parser does (`hybrid` for pages still without text, `multimodal` for every page) or when the upload is a photo, and the switch is required exactly then; with `text` or `ocr` it sends only the page text for extraction.

**Which provider matters.** Images go to `SPINE_LLM_PROVIDER`. The Anthropic adapter has no EU-only processing commitment, so a deployment with a residency requirement should enable this only on Vertex at an `eu` endpoint (M-8). The software cannot know your deployment has such a requirement, so it does not stop you.

**Not exercised:** no real page has been sent to a real provider; the image message was checked against both providers' request builders only. The local screening ran on real files with real Tesseract and poppler, though on rendered pages, not real handwriting.

**M-8 — Residency enforcement in the provider adapter.** **P8. Enforced as configuration.** The Vertex adapter requires `SPINE_LLM_ENDPOINT`, `SPINE_LLM_REGION` and `SPINE_LLM_PROJECT` to be stated — nothing defaults, so an instance cannot reach a global endpoint by omission — and the resolved provider, model and endpoint are logged once at startup.

The control that does the work: **construction fails if `GOOGLE_API_KEY`, `GEMINI_API_KEY` or `GOOGLE_GENAI_API_KEY` is present at all.** Reproduced against the installed `@langchain/google-vertexai`: with one set and an EU endpoint and region configured, the request goes to `https://aiplatform.googleapis.com/v1/publishers/google/models/<model>:generateContent` — the global host, with the configured endpoint dropped and no region in the path. In `@langchain/google-common`, an API key makes `connection.js` choose the "Express" platform, which hardcodes the global host. The same behaviour is reported for `@google/genai` ([gemini-cli#27984](https://github.com/google-gemini/gemini-cli/issues/27984)), so it is a class of bug across Google's client libraries. API keys are also blocked on standard Vertex endpoints and unsupported for Claude's `rawPredict`, so there is no legitimate reason for one to be set here.

**Deliberately not done:** asserting the shape of the outgoing URL. That encodes Google's URL scheme, means nothing for an Azure or Bedrock endpoint, and is bypassed by the API-key path, which is why the refusal above is the real control. Verify residency against the provider's request logs on first deployment; that works for any provider.

**M-9 — Per-user paths for originals.** `data/originals/<user>/<year>/`, so a filesystem mistake cannot cross users as easily as a query mistake. Asserted in the upload test.

**M-10 — A migration runner: not needed yet.** `CREATE TABLE IF NOT EXISTS` adds new tables to an existing database but cannot add a column to an existing table. Multi-user and verification changed existing tables while the archive held no records, so they edited the schema files (`schema-accounts.sql`, `schema-records.sql`) directly; a database of an older shape is **refused at startup**, with a message saying how many uploads and documents it holds and whether it is safe to delete. TOTP (M-12) added new tables only, so it did not need a change. Document titles added a column to `documents`, again while the archive held no records; a database without it is refused the same way. **A change to an existing table that is not purely additive needs a runner first**, or an empty database. A new column with a default is added in place when the database is opened (`addColumnsInPlace`; `pages.hidden` was the first), and tested against a database made without it.

**M-11 — Account recovery and verification.**

- The token is a capability: 256 bits of CSPRNG output, only its **sha256 stored** (**P6**), spent by one atomic `UPDATE` so two simultaneous requests cannot both succeed. A newer one replaces an older one. Verification lasts 24 hours, reset one hour.
- It travels in the URL **fragment**, never sent to the server, so it stays out of nginx's access log and the Referer header; the page removes it from the address bar. It is spent by a `POST`, so a mail scanner following links cannot spend it.
- Using a reset link ends **all** the user's sessions (**P13**, as M-4) and confirms the address. It does not bypass two-factor (M-12).
- Requests answer identically whether or not the address has an account, and are rate limited (**P5**).
- A send failure is logged and the page says to request another link. It is not shown as an error, because an error only for addresses that exist would be a way to find them.
- The mail carries no medical content (**P8**): an address and a link, no attachment field, plain subjects, and a test that fails on clinical wording.
- Without a mailer, `npm run cli -- reset-link <email>` prints the same single-use link.

**M-12 — Second factor (TOTP).** **P13.** Optional per user (S-20).

- **Algorithm:** RFC 6238 — HMAC-SHA1, 6 digits, 30-second steps, written with `node:crypto` and checked against the RFC's test vectors. SHA-1 is what authenticator apps support, and HMAC-SHA1 is not weakened by SHA-1's collision problems. A code is accepted one step either side of now, for clock drift.
- **Seed:** 20 random bytes, stored **encrypted** (AES-256-GCM, key derived from `SESSION_SECRET` with HKDF, the user id as associated data, so a row copied to another account does not decrypt) — see S-21. Shown once, as a QR code and as text.
- **Enrolling** takes the password, then a first valid code, which proves the app works before two-factor is switched on. Until then the seed is inert and login is unchanged. Anyone holding the password can enrol (S-22).
- **Login is two steps.** The right password does **not** create a session for a user with two-factor: it starts a *pending* login in the session (user id, `auth_version`, five-minute expiry). Only a valid code turns that into a session, with a fresh id. As with an unverified address, only someone holding the right password learns the account has two-factor.
- **Guessing is throttled (P5).** Six digits is a million possibilities, so the second step is limited per source, **per user** (5 attempts per ten minutes, whatever the source), and the pending login is dropped after five wrong tries.
- **No replay.** The last accepted time step is stored; a code for that step or earlier is refused, so a code seen over a shoulder or in a log cannot be used again.
- **Recovery codes:** ten, shown once when enabled and when regenerated; 10 characters from a 32-letter alphabet (50 bits), **sha256 stored** (**P6**), each spent by one atomic `UPDATE`. They are accepted at the second step in place of a code, and using one is logged. Regenerating replaces all ten.
- **Changing it needs proof.** Disabling or regenerating codes takes the password *and* a current code. Enabling and disabling both bump `auth_version`, ending the user's other sessions (**P13**).
- **Lost phone and lost codes:** `npm run cli -- disable-2fa <email>`, run by the operator. That makes the operator the recovery path, which is the trust the operator already has.
- Deleting a user (S-18) removes the seed and the codes.


**M-13 — Translation is egress of text, and a public route can trigger it.** **P8.** A document is translated into the reader's language on demand: its title, summary, extracted field values (and labels the app has no name for), measurement names, doctors' specialties and the owner's notes go to the configured inference provider, as text, and the result is kept in `document_translations`, keyed by a digest of exactly what was sent, so an edit, a re-extraction or a page reorder changes the digest and the old translation is never served. Nothing is sent for a document already in the reader's language, and `SPINE_TRANSLATION=off` stops the path: the endpoints answer `off` and the interface shows the original. Two things are new in the threat model. The owner's **notes** leave the host (they never did before; extraction sees only page text), which is why this is listed in [ARCHITECTURE.md](ARCHITECTURE.md) and is on by default only because the text already goes to the same provider. And **a share recipient can cause a model call**: `GET /api/share/:token/documents/:id/translation` is public. It is bounded the same way every public route is: the token must resolve to a live link and the document to its scope (anything else is the same 404, **P2**), the language must be one of four (`ro`, `en`, `fr`, `de`), a document is translated **once per language** whatever the number of requests (concurrent ones share one call), the route is rate limited (60 a minute), and it **writes nothing to the owner's records**: the language the model finds for a document with none is recorded only when the owner opens it (**R-4**). The worst a holder of a link can do is have each document in scope translated into each of four languages, once. Translations are deleted with their document, with an upload's derived data and with the account (`OWNED_TABLES`). Server error messages stay English: only the web interface and the stored details are translated.

**M-14 — Import takes a file the user was given.** **P12.** A zip uploaded to the upload route is untrusted input twice: as an archive and as a Spine export. As an archive: it is opened with `yauzl` and entries are read **by name and never extracted to a path the zip chooses**, so `../../x` is only a name; the size of every entry is counted as it is read and capped (200 MB each, 4 GB in all, 500 entries for a plain zip), whatever the zip declares, so a small zip cannot expand without limit; the zip itself is not kept; and the work a zip brings (restoring or reading each file) is queued two at a time, so a request with hundreds of files cannot start hundreds of poppler, OCR and model jobs at once (**R-1**). As an export: `manifest.json` (at most 64 MB, parsed into memory) is checked with zod, with a length or count limit on every string and list, dates in the app's own form, a cap on documents and pages in all, and a test name lower-cased, before anything is used, and a manifest of an unknown version is refused. **Nothing in it can name an owner, an id or a path**: every id is made on import, rows are written for the acting user through the store (**P12**), and the stored file is written to a path the server makes. The restored pages are made from the *file* with poppler/sharp as for any upload (**S-24**); the manifest supplies text, boxes and details, and a manifest that does not fit its file (a different page count, pages or ranges that do not exist) fails the whole file in one rolled-back transaction. Restoring calls no model and sends nothing off the host (**P8**). Exporting is the owner's own data on an authenticated, rate-limited route (6 archives, 30 documents a minute), built as it is sent; it never includes share links or their tokens, other users' rows, server paths or ids (a test asserts the owner's id and the data directory are absent from the manifest). The whole archive also carries the care-chain **links**, and an import is untrusted for them like the rest: a link names documents only by position in the manifest, the schema refuses a position that is not there, every id a link ends up with is one this restore made for this user, and the write goes through the store as them (`links.restore` checks both documents are theirs), so a manifest cannot point a link at anyone else's document. A restored link keeps the state the file gives it, as every other field of an export does: the file is the owner's own data, and restoring it does not itself confirm or dismiss anything. Version 2 of the manifest also carries what the owner keeps beside the documents (what was edited and removed, each doctor's source and printed code, the doctors' directory, every tag, merged test names, and the answers to "are these the same?"), under the same rules: every list is bounded, a doctor is named by position in `people` and the schema refuses a position that is not there, the headline columns an edit may name are a fixed enum, an answer names doctors by position and tags by name (never by an id), and everything is written for the acting user through the store; version 1 is still read, and a version above 2 is refused.

## Enforcement checklist

For any change touching routing, auth, share links, storage, providers or static serving:

- [ ] Does a new route land in a file with `requireAuth`? If public, is it justified here and on the allow-list in `isolation.test.ts`? (**P1**)
- [ ] Does a new table carry `user_id`, and does every statement on it filter by it? Does a new repository method take the acting user's id first? Is it inside `store/sqlite/`, the only place SQL or a driver import belongs? (**P12**)
- [ ] Is a new method exempt from taking a user id? Then it must be one of the four exceptions in `store/types.ts`, argued for there, not a fifth added quietly.
- [ ] Does a new query list explicit columns? `SELECT *` on a table with `user_id` sends it to the client, including to share recipients. (**S-8**)
- [ ] Can any share-link path return documents without a fully resolved scope? (**P2**) Does scope creation verify the creator owns everything it names? (**M-5**)
- [ ] Does any config read a secret with a `??` fallback, or ship a default an operator would not knowingly choose? (**P3**)
- [ ] Is medical content served by anything other than an authenticated handler — static mount, redirect, signed URL? (**P4**)
- [ ] Does a new nginx `location` set any `add_header`? If so it inherits none from the server level and must repeat the security headers. (**S-14**)
- [ ] Is every new unauthenticated endpoint rate limited at nginx or Fastify? (**P5**) The Fastify plugin applies only its first hook per request, so a second limit on one route has to be enforced separately (see S-2).
- [ ] Does anything new leave the host? Is it listed in [ARCHITECTURE.md](ARCHITECTURE.md), opt-in, and disableable? Do page images leave only through `readPage`, on a path that needs both switches — including any new button that triggers it? Can a public route cause a model call, and is it bounded (by language, by once-per-document caching and by a rate limit)? (**P8**, **M-7**, **M-13**)
- [ ] Does anything send text to a model that was not sent before (a new card, a new field)? Is it in the egress table and behind a switch? (**M-15**)
- [ ] Does anything put document content in front of a model on the owner's request (a question, a summary)? Is it chosen from the shown documents, sized, rate limited, owner only (or, for a share recipient, held to the link: **M-20**), and in the egress table? Does a new agent tool take a label rather than an id, read only through the store as the signed-in user, and never write? (**M-18**)
- [ ] Does a new query list the owner's documents? Does it use the one visibility fragment, so an unconfirmed upload or a set-aside document cannot leak into it, a share or a model call? (**M-17**)
- [ ] Does anything new write a record because a model said so? Is it only a proposal the owner decides on, and does code refuse what the data contradicts? (**M-16**)
- [ ] Does a request start work per item (files in a zip, documents in a list)? Is it queued and capped? (**R-1**)
- [ ] Does a public route write anything? It must not. (**R-4**)
- [ ] Does anything read a file or manifest a user was given? Is it read by name and never written to a path from it, size-capped as it is read, schema-checked, and does it mint every id itself? (**M-14**)
- [ ] Can a provider adapter fall back to a global endpoint, and is residency being asserted from a URL's shape rather than verified against request logs? (**P8**, **M-8**)
- [ ] Does anything above `src/llm/adapters/` import a vendor package? That is a review failure.
- [ ] Does anything widen the listening surface — a new bind address, an interface opened on a unit, a proxy header trusted from somewhere other than nginx? (**P9**, **S-13**)
- [ ] Does anything put document text, a summary, a field or an attachment into an email, or a subject or body that says anything clinical? (**P8**)
- [ ] Does a new way to obtain a session — login, reset, verification, any future SSO — go through the second factor for a user who has one? A path that issues a session directly is a bypass. (**M-12**)
- [ ] Is a limit keyed on `req.ip`? Then `trustProxy` must name only the proxy and nginx must overwrite `X-Forwarded-For`, or a client chooses its own key. (**S-31**)
- [ ] Does `npm audit --omit=dev` report anything high or critical? Does a dependency bump, or a new package, change what the lockfile resolves? (**S-32**)
- [ ] Does a new way of reading or exporting data in bulk, or of changing a credential, a second factor or a share's exposure, rely on the session alone? Should it ask for the password again? (**S-33**, **S-29**)
- [ ] Does a new model call have a rate limit and count against an instance-wide ceiling? (**S-35**)
- [ ] Does model output reach the page as anything other than text (an image, a link to another host, HTML)? The CSP stops the image, not the link a person clicks. (**M-18**)
- [ ] Does a share route return anything derived from links or similarity? Is every document in it in `listForShare(link)` *before* ranking or walking, and does it carry no reason, score, source or state? (**M-28**)
- [ ] Do tests drive the control through the real handler, with assertions that can actually fail? (**P10**)

## Operational response

**A share link is leaked or sent to the wrong person.** Revoke it from the Share Links page; `revoked` is checked on every read, so it takes effect immediately. Check `share_link_access_log` for that link's id to see whether and from where it was read.

**A user's account may be compromised.** From the server:

1. `cd server && npm run cli -- set-password <email>` prints a new password once and ends all of that user's sessions (**M-4**).
2. `npm run cli -- disable-2fa <email>` if they use two-factor or might have had one added: someone with the old password could have enrolled their own authenticator (**S-22**), and neither a reset nor `set-password` removes it. The user can enrol again.
3. Revoke the share links they created; those are independent of the password and survive a reset.

**The instance-wide secret may be compromised.** Rotate `SESSION_SECRET` in `.env` and `sudo systemctl restart spine-web`. This invalidates every session, which is the point. It also makes every enrolled authenticator seed unreadable (**S-21**): those users sign in with a recovery code and enrol again, or the operator runs `disable-2fa`.

**`spine.db` may have been exposed.** Share tokens are digests since **S-4**, so the links in it are not usable as-is; revoking them is still the cautious move if the raw tokens may have leaked by another route (an email, a screenshot, browser history). Credential hashes (argon2id) are exposed, so set a new password for every user with the CLI. TOTP seeds are encrypted under a key that is in `.env`, not the database, but treat them as exposed too if `.env` was. Document contents are disclosed. Backup snapshots are copies of the same database and carry the same exposure.

**Restoring.** Stop `spine-web`, copy a snapshot from the backup directory to `data/spine.db` (and `data/originals/` and `data/vault/` back from the mirror), then start it again. `data/pages/` regenerates on re-ingestion. Delete any stale `spine.db-wal` and `spine.db-shm` beside the restored file: a snapshot is already consistent, and an old sidecar would be applied on top of it.
